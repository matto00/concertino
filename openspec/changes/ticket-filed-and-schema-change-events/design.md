## Context

See proposal.md — Why. Two constraints from the live tree shape everything below; both were established during Setup's premise validation (`.concertino/runs/CON-190/evidence/premise-validation.md`) rather than assumed.

**The emitter is already strict, and its refusal placement is load-bearing.** CON-189/CON-187/CON-194 (merged as this change's base) refuse a `verdict` lacking `category`, a skeptic verdict lacking `gate`, and a stated `head_sha` that is not 40 hex chars — non-zero exit, no event appended. Critically, that validation sits *below* the CON-171 auditor-lease release, precisely so a refused auditor verdict cannot strand a Phase-4 teardown lease. Any new refusal this change adds inherits that ordering requirement.

**Instrumentation is distributed as rendered copies that get patched locally.** `concertino sync` copies `core/scripts/**` byte-for-byte into a consuming repository's `scripts/concertino/**`. The change that invalidated the escalation-cliff analysis (CON-128) was made in the consuming repository, to a rendered copy, and therefore appeared nowhere in the framework's own history. Three mechanisms already exist and none detects it: `sync-provenance` prints provenance at sync/diff time, `rendered-script-drift-gate` byte-compares the trees in *this* repo's test suite, and `concertino doctor` compares on demand. All are sync-time or this-repo-test-time. Nothing durable is recorded, and nothing runs in a consuming repo at run time.

## Goals / Non-Goals

**Goals:**
- Record ticket provenance at the moment of filing, with the originating repository, since that omission is what invalidated the original inference.
- Make a locally patched rendered script detectable from the consuming repository's own event log, with no reference to framework history.
- Close the role-typo split with a refusal, without refusing any role that legitimately emits today.
- Preserve the existing corpus byte-for-byte; CON-192 consumes it next.

**Non-Goals:**
- Backfilling or inferring provenance for existing tickets. The corpus does not reach back far enough and the inference method is known to fail.
- Surfacing either new kind in the dashboard UI. No acceptance criterion asks for it, and adding them to the telemetry tiers would actively mislead (see Decision 8).
- Detecting drift in rendered *role* files or `AGENTS.md`. Those are untracked render targets; the acceptance criterion concerns the scripts that emit events.
- Blocking or failing a run on detected drift. Drift is recorded, never enforced.

## Decisions

**1. Both tickets ship as one change.** They add two kinds to one file (`core/scripts/emit-event.sh`), share the same refusal-placement constraint, and the role-validation work (CON-191 item 3) touches the same validation block as the `ticket.filed` field checks. Splitting them would mean two sequential edits to the same 1,132-line script with a near-certain rebase conflict, and would land half the schema at a time in a corpus CON-192 is about to read. *Alternative rejected:* deliver CON-190 first and CON-191 on top — rejected because CON-191's own requirement is to record when event emission changes, and CON-190 *is* a change to event emission, so the two would have to reference each other across a merge boundary anyway.

**2. This delivery emits its own `schema.change` event — the self-reference is resolved deliberately as "yes".** CON-191 requires that any change to event emission emit a `schema.change`. This change is the largest such change in the corpus's history: it adds two kinds and begins refusing a previously accepted field value. Three reasons to emit rather than exempt. First, the requirement is unconditional, and an implementation that exempts itself is the precise failure mode the ticket was written about — an instrumentation change invisible in the instrumentation. Second, CON-192 will diff the corpus across exactly this boundary; a marker at the instant the schema changed is the difference between "role grouping got cleaner" being attributable and being another unexplained cliff. Third, it is the only self-demonstrating evidence the mechanism works end to end. *Mechanism:* a one-shot emission performed as an explicit task, carrying both ticket ids and the affected kinds, appended to this run's own log. It is deliberately distinct from the automated drift detection in Decision 3: that path fires on rendered-copy divergence, which is not what happened here — here the framework's own source changed, which no digest comparison would or should flag. Recording it by hand is therefore not a workaround; it is the correct channel for a source-side schema change, and the design states this so a reader does not mistake the manual step for an automation gap. *Alternative rejected:* exempting this change as "bootstrapping" — rejected because it silently reintroduces the gap at the one boundary that matters most to the downstream consumer.

**3. The digest is computed at run start, from the rendered copies, in the repository being operated on.** `setup-worktree.sh` already emits `run.start` and already runs from `scripts/concertino/` in the target repo, so it is the only place that observes exactly the scripts that will actually execute. It hashes those rendered `.sh` files and records the digest on `run.start`. *Why not sync time only:* CON-128 was a patch applied *after* a sync; a sync-time-only record cannot see it. *Why not `core/`:* the framework's templates are not what a consuming repo executes — that gap is the entire bug. *Why not per-script hashes on the event:* one aggregate digest answers AC2 ("were two runs measured by the same instrumentation") in a single comparison; the affected script names are carried on the `schema.change` event, where they are actually actionable.

**4. The render-time baseline is recorded by `sync`, and its absence is not drift.** `concertino sync` records the digest of what it wrote. At run start, a live digest differing from that baseline emits `schema.change` naming the affected scripts. When no baseline exists — the expected state for every repository that has not re-synced, including helio, which by owner ruling will not be synced until after this batch — the live digest is still recorded, no `schema.change` is emitted, and the run proceeds. Absence of a baseline is not evidence of a change, and treating it as drift would emit a false positive on every run in every unsynced repo. *Consequence worth stating plainly:* a legitimate `sync` updates the baseline, so live and baseline agree and no event fires. Only a post-sync local patch drifts. This is what keeps the signal specific rather than firing on every upgrade.

**5. Role validation refuses a closed seven-value set, placed below the auditor-lease release.** The legal set is the five agent roles plus `script` and `dashboard`. This is not a judgment call: `emit-event.sh` itself defaults `ROLE` to `script` (`CONCERTINO_ROLE:-script`), every procedure script emits under it — including the `run.end` that makes a run terminal. `dashboard` is included for a different and weaker reason, stated precisely because the design-gate skeptic corrected an earlier overstatement here: `dashboard`-role events exist in both corpora, but `lib/ui/session.js` writes them by direct `fs.appendFileSync`, bypassing `emit-event.sh` entirely, so the entry is currently INERT rather than exercised through the validated path. It is retained deliberately — omitting it would make routing `session.js` through the emitter later a silent breaking change — but no claim is made that it is presently exercised. A five-value set would refuse `cleanup.sh`'s `run.end` and leave runs non-terminal forever. The refusal is placed in the same post-lease-release block CON-189 established, for the same reason: a refused invocation must never strand a teardown lease. *Alternative rejected:* warn-and-record instead of refuse — rejected because the acceptance criterion says rejected, and a warning preserves exactly the silent split the ticket exists to close.

**6. `report-cost.sh` is the only dynamic role producer and is normalised at source.** Audited: every other call site in `core/`, `lib/`, and `bin/` passes a literal role, and the only dynamic value anywhere derives from the Claude Code hook payload's `agent_type`. That hook fires for *every* Task-tool subagent, not only `concertino-<role>` agents, so a general-purpose or exploratory subagent in the same session yields an out-of-set role. Under Decision 5 that event would be refused and its cost silently lost — during batch work, which is when such agents are most used. So `report-cost.sh` maps an unrecognised stripped `agent_type` onto a role inside the closed set and preserves the raw value verbatim in a separate field that role validation does not police. No information is lost, and the grouping key stays clean. This makes `run-cost-telemetry` a modified capability. *Alternative rejected:* exempting `run.cost` from role validation — rejected because a per-kind exemption is a hole that the next new kind inherits by default.

**7. `triage` is recorded as a JSON-encoded value, following the `models=` precedent.** The emitter is a flat `k=v` interface; `run.start` already carries its per-role `models` object this way. **Stated deviation:** CON-190's scope block shows `triage` as a nested JSON object, and this records it as a JSON-encoded string instead. The recorded content is identical and remains parseable by the downstream consumer; only the wire encoding differs, and it matches what the emitter already does for the one existing object-valued field rather than introducing a second, bespoke embedding path. Flagged explicitly because it is a departure from the ticket's literal shape. `triage-followup.sh` gains one machine-readable line so the values it already computes can be captured; its decision table and human-readable block are untouched, because that block is what the escalation passes through as `context=`.

**8. Neither new kind joins the dashboard's telemetry tiers, and `lib/ui/` is not modified at all.** The reducer's `applyEvent` ends in `default: break;`, `store.js` filters on shape only (`typeof ev.kind === 'string'`), `cache.js` and `discovery.js` never inspect `ev.kind`, and retention keys off `run.end` at whole-run granularity — so both kinds are carried, rendered-safe, and never specially pruned with no consumer change. They are deliberately kept out of `TIER2_KINDS`/`TIER3_KINDS`: those sets answer "is this run instrumented and progressing", and a run whose only event was a `schema.change` would otherwise report as partially instrumented while having made no progress at all. Confirmed no existing test asserts a closed set of kinds, so nothing breaks by addition.

**9. `read_raised_field()` is deliberately NOT tightened, and the handover condition was evaluated rather than ignored.** The CON-189 handover states that if either new event adds a field read back through that path, tightening it becomes this lane's responsibility. It does not: that helper reads only the last `escalation.raised` event for a ticket and serves `raised_at`/`sub_questions`/`escalation_id`. Neither `ticket.filed` nor `schema.change` is an `escalation.raised` event, and neither adds any field read through it. The condition is therefore untriggered, and touching that helper would be unrequested scope on the escalation path.

**10. Both copies of every changed script change in the same commit; `concertino sync` is not run.** `rendered-scripts-drift.test.sh` holds `core/scripts/**` and `scripts/concertino/**` to byte-identity, while CONTRIBUTING forbids hand-authoring a rendered file. The CON-189 commit is the precedent and resolves the apparent conflict: it changed `core/scripts/emit-event.sh` and `scripts/concertino/emit-event.sh` by the same 85 lines in one commit. The rendered copy is updated as a faithful copy of core, never independently edited. This does not conflict with the owner's no-sync ruling, which concerns rendering into helio, not this repository's self-hosted render.

**11. Validation applies only to new emissions; the corpus is untouched.** No existing log is rewritten, reordered, or backfilled. Every new refusal governs only what is emitted from now on, and every consumer keeps a defined behaviour for historical events lacking the new fields or carrying an out-of-set role. This is a hard constraint, not a nicety: committed tests assert the ~2,300-event corpus still folds, and CON-192 reads it next.

**12. Every new refusal must be proven failable by mutation.** A passing suite against unmutated input is not evidence that a check works. For each new refusal — missing `ticket.filed` field, illegal `origin_kind`, illegal `suggested_by`, out-of-set `role` — the verification must demonstrate a non-zero exit AND that no event was appended, and must show the pre-change behaviour accepted the same input. The two RED baselines were captured during Setup: today `schema.change` as an arbitrary kind is accepted silently, and `role=orchestorator` is accepted silently, both rc=0 with the event written.

## Risks / Trade-offs

- **Role refusal drops telemetry from a caller the audit missed** → The audit covered every `emit-event.sh` invocation in `core/`, `lib/`, `bin/`; the one dynamic producer is fixed at source (Decision 6); the legal set includes the emitter's own default. Residual risk: a consuming repo running a *stale rendered copy* that passes some other role. Accepted, and it is self-announcing — the refusal is loud on stderr and non-zero, never silent.
- **A digest computed over rendered scripts churns on every legitimate upgrade** → Drift is live-vs-baseline, and `sync` moves the baseline, so a legitimate upgrade emits nothing (Decision 4). Only a post-sync local patch drifts.
- **Emitting this change's own `schema.change` could read as ceremony** → Mitigated by stating exactly what it is: the correct channel for a source-side schema change, distinct from the automated rendered-copy drift path, and the marker CON-192 needs at this boundary (Decision 2).
- **`ticket.filed` provenance depends on the orchestrator following prose** → Partly unavoidable: the filing step is a role instruction, not a script. Mitigated by making the *event's* required fields mechanically enforced, so a malformed emission is refused loudly rather than recorded half-populated. Stated honestly: this change cannot mechanically guarantee the orchestrator emits at all, only that what it emits is well-formed.
- **The `triage` encoding deviates from the ticket's literal nested object** → Flagged in Decision 7 rather than quietly substituted; content is identical and parseable.

## Migration Plan

Additive. No data migration, no config schema change, no existing behaviour removed. New validation governs only new emissions. A repository that has not re-synced keeps working with no baseline and no drift events. Rollback is a plain revert of the commit; reverted, the new kinds simply stop being emitted and the historical events they wrote remain readable, since every consumer tolerates unknown kinds.

**Gate-chain implications:** N/A. This repository has no `.husky/` and no pre-commit hook framework (`npm test` is the whole verification gate, per CONTRIBUTING), and this change's diff touches no commit-gate chain, so `check-gate-chain-change.sh`'s Delivery-time checklist requirement does not apply.
