## Root cause (systematic-debugging.md)

- **Root cause:** `bin/concertino` resolved `CORE` once at module load as `path.join(path.resolve(__dirname, '..'), 'core')` — the core next to the *executing* copy of the script — and every core-reading function (`readRoleFile`, `emitClaude`, `emitCodex`, `copyAssets`, `checkArtifacts`) closed over that module constant instead of taking the target's own core as an input, so a globally npm-linked CLI invoked from inside one of its own delivery worktrees always rendered the main checkout's `core/`, even when the worktree's own `core/scripts/*` had diverged.
- **Probe:** stubbed `resolveCore` to unconditionally `return path.join(repo, 'core')` (the old behavior) and reran the new test file in isolation.
- **Probe output:** 10 of 35 assertions failed — exactly the worktree-divergence and `--core` scenarios (3.1's "renders the worktree's own edited core", 3.5's `--core` overrides, 3.6/3.6b's post-refactor worktree/`--core` renders, 3.7's eject role content) — confirming the stubbed (old) behavior reproduces the ticket's bug and that the new tests catch it. Restoring the real `resolveCore` implementation returns the suite to 35/35 passing.
