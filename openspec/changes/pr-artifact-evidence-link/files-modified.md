## Root cause / debugging notes

No bug was hit during implementation. One test-authoring pitfall worth recording per `systematic-debugging.md`'s spirit (even though it wasn't a product bug):

- **Symptom:** the first draft of the CON-55 `openInBrowser` "success" test failed with `Command failed: xdg-open ...` even though the fake script's own exit code was `0`.
- **Root cause (test harness layer, not product code):** the fake `xdg-open` script's shebang was `#!/usr/bin/env bash`; `env` itself still has to resolve `bash` via `process.env.PATH`, which the test had set to *only* the fake bin directory — so `bash` itself could not be found, and `execFileSync` reported a generic failure that looked like the fake script had failed.
- **Probe:** ran the fake script directly with `PATH=<fake-dir-only> /path/to/fake/xdg-open` — got `env: bash: No such file or directory`, confirming the interpreter lookup, not the exit code, was failing.
- **Fix:** changed the fake script's shebang to an absolute interpreter path (`/bin/sh` or `/usr/bin/bash`, whichever exists), which the kernel execs directly without any `PATH` lookup — only the `execFileSync('xdg-open', ...)` call itself needs `PATH` to find the fake binary. Verified this system also has a REAL `xdg-open` at `/usr/bin/xdg-open`, so the harness replaces (never merely prepends to) `PATH` for the duration of each test, so the "missing"/"failing" scenarios can never silently fall through to the real one.
