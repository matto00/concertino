## Context

See proposal.md - Why. The mechanism, as measured in this run rather than assumed:

`core/scripts/emit-event.sh escalation --await` polls `answer.json` on a **1s** period. The
CON-180 repro block backgrounds a pre-fix mutant of that script (with a 2s window injected
between its verdict read and its `cksum` re-read), writes `MALFORMED_A`, sleeps a fixed **1s**,
then writes `MALFORMED_B`, and asserts the logged verdict's `reason` describes A while its
`content_hash` describes B — the stale/fresh split CON-180 fixed.

An instrumented probe (marker written by the mutant immediately after its first read) measured
`t_firstread - t_Awrite`:

| condition | margins (s) |
| --- | --- |
| unloaded | 0.943, 0.945, 0.946, 0.947, 0.947 |
| 36 spin loops / 12 cores | 0.106, 0.162, 0.179, **1.048**, **1.050** |

Two facts follow. First, the wait has only ~55ms of headroom when idle. Second, the distribution
is bimodal, not merely shifted: the fixed wait is the *same length* as the poll period it races,
so the margin is set by where the A-write falls relative to a poll tick. Land just before a tick
and the margin is ~0.1s; slip past it and the next read is a full period later, which exceeds
1.000s and loses the race. No choice of constant equal to or below the poll period is safe, and
a larger constant only narrows the failing phase band rather than removing it — which is why
widening the sleep is a mitigation, not a fix.

Measured failure rates on a pristine checkout of the base SHA, with no other change present:

- 24 spin loops / 12 cores, unpinned: 0/4 trials failed (the rate quoted in the ticket did not
  reproduce this way).
- Pinned to one core (`taskset -c 0`) + 12 spin loops — a slow-runner emulation: **5/6 trials
  failed**.

## Goals / Non-Goals

**Goals:**
- Make the reproduction's interleaving deterministic by observation, independent of machine speed.
- Keep the assertion failable: it must still go red when the interleaving is not achieved.
- Fail loudly if the interleaving cannot be established, rather than asserting against a wrong one.
- Keep the diff confined to the one fragile wait.

**Non-Goals:**
- Changing `core/scripts/emit-event.sh`, the CON-180 fix, or any shipped behavior.
- Changing the meaning of any assertion, or the injected 2s race window.
- Fixing CON-196's process-teardown flakes, or setting `fail-fast: false` on the CI matrix. Both
  are CON-196's scope; this change is deliberately narrow because CON-188 is blocked on it.
- Rewriting the other fixed waits in this file (see Decision 3).

## Decisions

### Decision 1: the mutant records its first read; the test waits for that record

The mutant is generated by a python substitution that already rewrites the MALFORMED branch to
the pre-fix two-read shape. That injected bash gains one line, immediately after the verdict is
parsed from the read's result and **before** the injected race window:

```
reason="${result#MALFORMED:}"
[ -n "${CON180_FIRST_READ_MARKER:-}" ] && printf '%s' read > "$CON180_FIRST_READ_MARKER"
[ -n "${CON180_RACE_WINDOW_SEC:-}" ] && sleep "$CON180_RACE_WINDOW_SEC"
content_hash="$(cksum "$ANSWER_FILE" 2>/dev/null)"
```

The test exports `CON180_FIRST_READ_MARKER` into the mutant's environment, polls for the marker
to become non-empty, and writes B only then. The marker is positive evidence of the exact event
the race depends on — that the mutant has consumed A — so the interleaving no longer depends on
how fast the machine is.

*Why this placement.* It must be after the read (so it cannot fire before A has been consumed)
and before the injected window (so the test still has the full 2s to land B inside the window).
Writing it after the window would defeat the purpose: the window would already have closed.

*Why guarded on the variable.* An unguarded write would change the mutant's shape for any other
caller and would fail when the path is unset. Guarding keeps the generated mutant faithful to the
pre-fix script whenever the test does not ask for instrumentation — and gives the spec's
"instrumentation does not alter the mutant otherwise" scenario something real to check.

*Alternative considered: observe the injected sleep's start externally* (e.g. poll `ps` for a
`sleep 2` child of the mutant). Rejected: it infers the event from process state instead of
observing it, matches by pattern rather than by identity (which `wait-bounded.sh`'s own header
and `await-sentinel.test.sh` both call out as unsafe on a shared box), and is racy in its own
right — the sleep can start and finish between polls.

*Alternative considered: widen `sleep 1`.* Rejected on the measurement above and by the ticket's
own ruling: it keeps the defect class and lengthens an already-slow suite.

### Decision 2: the wait is bounded and fails through `check()`

The poll is bounded (10s at 0.05s resolution — two orders of magnitude above the ~0.95s the event
actually takes, so the bound is only ever reached on a genuine breakage, and it is far below the
20s bound the file's existing `wait_killed_bounded` calls use). On timeout the test records a
failed `check()` naming the missing first-read evidence.

This matters more than it looks. If the marker never appears — because a future refactor of
`emit-event.sh` moves or removes the MALFORMED branch, or the substitution's premise silently
drifts — a silent fallthrough would write B anyway and then assert the stale/fresh split against
an interleaving nobody established. That either produces a confusing failure in a *different*
assertion or, worse, an accidental pass. The file has a documented history of exactly this class
of mistake: its own header records a revision where a mutant was silently non-representative and
"the suite kept going with a WRONG, non-representative mutant" because a failure did not abort.
Failing loudly here is consistent with the hard abort that block already performs when the
substitution's premise does not hold.

### Decision 3: sibling fixed waits are left alone, deliberately

Every other `sleep` in this file was assessed. None is a which-write-wins race, so none shares
this defect:

- **line 320, `sleep 1`** (the CON-180 *fix*-side block, structurally the closest sibling): its
  assertion accepts *either* A or B, requiring only that `reason` and `content_hash` agree. It is
  race-tolerant by construction, so the wait's length cannot make it fail. Deliberately not
  converted — a condition wait there would add machinery that guards nothing.
- **line 149, `sleep 2`**: backs the *negative* assertion that `--await` is still running on an
  incomplete answer file. A longer-than-needed wait only strengthens it; a shorter one is the
  only risk, and 2s is already two poll periods.
- **line 767, `sleep 2.5`**: deliberately fixed, and its comment explains why at length — it must
  observe a full window of at least two poll intervals, and an earlier "adaptive" version of this
  exact wait was itself the bug (it short-circuited after one 0.2s sample and could pass on a
  transient reading). Converting it to a condition wait would regress CON-156's guard.
- **the `sleep 3`s (281, 323, 404, 522, 587, 624)**: wait for an event to land inside an already
  generous margin; not interleaving-sensitive.
- **the `sleep 0.1`s**: already inside bounded condition-poll loops.

### Decision 4: gate-chain implications

Not applicable. This change touches one test file; it adds no commit-gate script and modifies
nothing `.husky/**` invokes, so `check-gate-chain-change.sh`'s Delivery gate has no subject here.

## Risks / Trade-offs

- **[The marker could be written before A is actually consumed, making the wait meaningless]** →
  Mitigated by placement: the line sits after `reason` has been parsed out of the node read's
  result, so the read has provably already happened. The mutation test in tasks.md (defeat the
  wait, assert the assertion goes red) is what proves the wait is load-bearing rather than
  decorative.
- **[A condition wait could make the assertion unfailable — the worst outcome, silently ending
  CON-180's guard]** → Mitigated by an explicit mutation task: with the wait removed so B wins the
  first read, the assertion must go red under the same contended conditions. A second mutation
  (marker never written) must turn the new bounded-wait check red.
- **[The substitution's premise drifts and the instrumented line stops applying]** → The block
  already hard-aborts when its `assert src.count(...) == 1` premises fail; the new line is added
  inside the same asserted replacement, so drift aborts rather than silently no-ops.
- **[Trade-off: the test now depends on an env var the mutant honours]** → Accepted. It is
  confined to the generated mutant, guarded on the variable, and exercised by the suite itself.

### Decision 5: `--skip-specs`, not a new capability

**Adopted: no spec delta.** The change's `.openspec.yaml` sets `skip_specs: true` and Delivery
archives with `openspec archive <name> --yes --skip-specs`.

An earlier revision of this design invented a new capability
(`test-interleaving-condition-wait`) on the stated premise that no change in this repo opts out
of specs. **That premise was false, and the error was mine**: it came from grepping for
`skip_specs` when the flag in use is `--skip-specs`, so an empty result was read as evidence of
absence. `grep -rl -- "--skip-specs" openspec/changes/archive/` returns **16** matches — an
established, repeatedly-used pattern.

The directly analogous precedent is `2026-08-01-fix-cleanup-sh-comment-drift`: a narrow,
single-file, no-shipped-behavior fix whose proposal records `New Capabilities: (none)` and which
has no `specs/` directory at all, archived with `--skip-specs` per the orchestrator role's own
documented path for infra/doc-only changes (itself citing
`2026-07-30-codex-worker-dispatch-caution`).

CON-200 belongs in the same bucket, on the alternative's own merits rather than by analogy alone:

- It touches exactly one test file and changes no runtime, `core/`, `lib/`, or adapter behavior.
- The requirement the capability would have enshrined has exactly **one consumer** — this same
  test, in this same change. A capability whose only scenario is the change that created it does
  not bind anyone; it would sit in `openspec/specs/` as a permanent tracked requirement that no
  future ticket is meaningfully checked against.
- openspec's own artifact instruction is explicit: specs describe behavior, so if behavior does
  not change, no spec should change either, and one must not "invent a requirement just to
  satisfy validation." Writing a capability to avoid an opt-out is precisely that.

*Alternative considered: keep the capability so it binds future interleaving-sensitive tests.*
Rejected because nothing would ever exercise that binding — there is no gate that checks a new
test against `openspec/specs/`, so the requirement's only real effect would be to make a future
author's unrelated change appear to touch a spec. The durable lesson is instead recorded where a
future author actually encounters it: the replacement comment at the wait site, which states the
measured margins and why any constant at or below the poll period is unsafe. That is the same
place this file already records its other hard-won wait lessons (the CON-156 comment at line 767
and the mutant-generation header).

*Trade-off accepted:* the "guarded assertion remains failable" property is no longer
spec-tracked. It is enforced instead by the mutation tasks (4.1-4.3) and by the assertions
themselves, which is where it is actually checkable.
