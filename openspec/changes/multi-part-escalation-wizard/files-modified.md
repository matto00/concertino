# Files modified — multi-part-escalation-wizard (CON-46)

- `core/scripts/emit-event.sh` — accepts an optional `sub_questions=` field (task 1.1); adds an oversized-`sub_questions` guard in `write_escalation_raised()` that runs before either lossy fallback, independent of whether `context` is present (task 1.2, design.md Decision 4); `--await` captures the raw `sub_questions` value and parses `total` up front (task 1.3); the poll loop gains a multi-part branch that resolves only on `complete === true`, emits `escalation.answered` with `sub_answers`, and prints one sub-answer per line (tasks 2.1/2.2); the single-question poll path and the existing `on_kill`/deadline handling are untouched (tasks 2.3/2.4).
- `lib/ui/store.js` — adds `writeSubAnswer(root, ticket, index, value, total)` (temp-file-then-`renameSync`, refuses to overwrite an already-answered slot) and `readSubAnswers(root, ticket)` (safe parse, `null` on any missing/malformed file); `writeAnswer` is untouched (tasks 3.1–3.3).
- `lib/ui/reducer.js` — `escalation.raised` now `JSON.parse`s `ev.sub_questions` (when present) into `run.escalation.subQuestions`, degrading to `undefined` on a parse failure; `escalation.answered`/`escalation.timeout` continue to unconditionally null out `run.escalation` (tasks 4.1/4.2).
- `lib/ui/screens/escalation.js` — adds the wizard step-through render/handleKey path (`isWizard`/`clampSubIndex`/`resumeSubIndex` helpers; both an option-key answer and a confirmed free-text reply resolve to the single `answer-sub` action so "no jump ahead" is structural, per Decision 6); the single-question path computes the same `currentQuestion`/`currentOptions` it always did, so it is unchanged (tasks 5.1–5.4). `resumeSubIndex` is exported so `watch.js` and this module's own tests share one definition of "resume point" (task 5.5, Decision 7).
- `lib/ui/watch.js` — adds `escalationSubIndex` state (reset alongside `escalationTicket`/`backToFleet`); `open-escalation` now calls `store.readSubAnswers` + `escalationScreen.resumeSubIndex` to resume a multi-part escalation at the first unanswered step instead of unconditionally defaulting to `0`; adds `answerEscalationSub()` (wired to the new `answer-sub` action) that advances `escalationSubIndex` by one on an incomplete write, navigates back to the fleet on a complete write, and surfaces an "already answered" race as a notice, mirroring `answerEscalation()` (task 5.2/5.3/5.5).
- `core/roles/orchestrator.md` — documents the multi-part `sub_questions=` invocation form in "How to raise one", alongside the existing single-question example; informational only (task 6.1).
- `test/escalation.test.js` — new coverage for the wizard render/handleKey path (single-step rendering, no-jump-ahead, free-text per step, the final step's `answer-sub` action), `writeSubAnswer`/`readSubAnswers`'s incremental/complete semantics, and `resumeSubIndex`'s resume-at-first-unanswered-step behavior; all pre-existing single-question tests are untouched (task 7.1).
- `test/reducer.test.js` — new coverage for `escalation.raised`'s `sub_questions` parsing (valid, malformed, absent) and `escalation.answered` clearing a multi-part escalation exactly like the single-question path (supports task 4.1/4.2; not explicitly required by tasks.md's Tests section but added for direct coverage of the reducer change).
- `test/scripts/escalation-loop.test.sh` — new coverage for `--await`'s multi-part resolution (an incomplete `answer.json` does not resolve the wait; a complete one does, printing sub-answers in order and logging `sub_answers`) and Decision 4's two oversized-`sub_questions` cases (no `context` at all; a small, otherwise-truncatable `context` also present) — both fail the raise outright with no `escalation.raised` line written; all pre-existing single-question coverage is untouched (task 7.2).
