### New findings (round 2, not raised in round 1)

**Finding 1 — the two tiers are not mutually exclusive, and this run's own filing now proves it live.** The `standaloneTicket` template (`lib/cli/render.js`) unconditionally writes `origin_kind: followup` / `origin_ticket: $TICKET_ID` into every filed ticket's **description text**, regardless of whether the separate, optional `provenanceEmit` bash block (which actually calls `emit-event.sh ticket.filed`) is also run. CON-213 — this run's own showcase row, filed specifically to give the provenance tier "its first genuine row" (Decision 11) — is a live, concrete example: it has a real `ticket.filed` event (provenance tier) **and** its description literally matches the convention-recovery needle (confirmed above: it is one of the 2 CON hits my formatting-tolerant scan found). Nothing in task 4.2 (provenance tier, reads `ticket.filed` events) or task 4.3 (recovered-convention tier, text-scans descriptions) excludes a ticket already counted via provenance from also being counted via text recovery. Per spec.md's own template convention, **every** ticket ever filed through this workflow will always carry the convention text, whether or not its provenance event was also emitted — so the recovered-convention tier is not "what provenance missed," it is "everything the provenance tier reads plus everything it doesn't," an overlapping, not complementary, set. The two-tier design's entire stated rationale (Decision 3: "never summed," never presenting "a confidently-wrong authoritative-looking number") is undermined at the counting level, not just the presentation level: a reader who inspects both tiers' totals side by side will find the same ticket id counted in both, with no disclosure that the sets overlap. This is not hypothetical — it is reproducible today with live data, and it is the ticket's own remediation action (filing CON-213) that exposed it. **Required revision.**

**Finding 2 — design.md overclaims what the emitter validates for `origin_role`.** As detailed above, `emit-event.sh` performs zero closed-set validation on `origin_role`'s value; it only checks non-emptiness. Design.md's claim ("validates `origin_role` against the closed role set and accepts any member") describes a safety net that does not exist — the closed-set check it is referring to belongs to a different field (`role=`). This matters because item 3 of my brief specifically asked me to check this distinction, and it is wrong as stated: the correct fact is "the emitter performs no origin_role validation at all," not "the emitter validates against a closed set." The substantive point Decision 11 relies on (this run's log can and does carry a truthful non-`orchestrator` role) is still true in outcome, but the design's own reasoning for *why* that's safe (implying a validated closed set) is inaccurate and should not ship uncorrected — a future caller could set `origin_role=banana` and nothing would refuse it. **Required revision** (fix the claim, and consider whether `origin_role` should in fact gain closed-set validation, matching the rigor design.md believes already exists).

**Finding 3 — CON-213's own mirrored provenance text contradicts its own emitted event.** CON-213's Linear description, under its own "## Provenance" heading, states `origin_role: orchestrator` — but the `ticket.filed` event emitted for CON-213 (verified in `events.jsonl` line 13) carries `origin_role: skeptic`. These are two different provenance records for the same filing, in direct disagreement, and the wrong one (the stale `orchestrator` default) is the one that is human-readable on the ticket itself and the one the convention-recovery text scan will read. Design.md's Decision 11 touts this filing as proof the log "carries a non-`orchestrator` row" and that this exercises the provenance tier "end-to-end" — but the same filing's own on-ticket text record says the opposite. Since design.md's entire premise is that recorded provenance should be trustworthy and traceable, shipping this contradiction in the change's own generated example undermines the credibility of the demonstration it is meant to provide. **Required revision** — either correct CON-213's description to match the true origin role, or explicitly disclose the mismatch in design.md as a known artifact of the manual filing step (which itself is evidence for CON-213's own thesis: manually-produced provenance text is unreliable and the template should thread the real role through everywhere, not just the emitted event).

**Finding 4 (minor) — ticket count is off by one.** My live re-scan finds 212 CON tickets (not 211, as design.md's Context section states in two places: "211 CON" and the acceptance-criterion-defects section referencing "211/211 descriptions non-empty" from round 1's report, itself quoting design.md). This is very likely explained by CON-213 having been filed after the original count was taken (212 = 211 + CON-213), which is internally consistent with the timeline, but design.md does not update this figure or flag it as pre/post-filing. Non-blocking on its own, but worth tightening given how much weight this document places on exact reproducible counts (Decision 9 / C1's whole point is that stale or unverified counts are the actual failure mode this ticket exists to prevent).
