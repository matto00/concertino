### Verdict: REFUTE

### Change Requests

**1. Decision 1's foundational premise — "`a`/`d` are already claimed at the fleet screen's top level" — is factually false, and this was self-approved by the orchestrator from code evidence that does not hold up.**

`proposal.md` #1 and `design.md`'s Context #1 both assert: *"`lib/ui/screens/fleet/keys.js`'s own CON-78 comment already lists `a` and `d` among the letters claimed at the fleet screen's top level ... so neither key has a free top-level slot."* Direct verification:

- `d` does not appear **anywhere** in `lib/ui/screens/fleet/keys.js` — not top-level, not inside any existing focus block. (`grep -n "'d'" lib/ui/screens/fleet/keys.js` returns nothing.) It is bound only in `lib/ui/screens/ticketdraft.js:143` (`open-draft-field field: 'description'`), a wholly separate screen/mode reached via the `n`-prompt's free-text draft flow — not "the fleet screen's top level" by any reading. `docs/dashboard.md`'s own Keys table (lines 127-138) documents every currently-bound fleet key and has **no row for `d` at all**, independently confirming it is genuinely free today.
- `a` **is** bound in `keys.js`, but only inside `if (focus === 'quickstart')` (line 218: `quickstart-add`) — itself a focus-scoped binding, not a top-level/unconditional one. `docs/dashboard.md:136` documents it the same way: *"While QUICK START is locally focused: quick-start the highlighted eligible ticket."* So `a` is in exactly the situation the design proposes creating for FAILED — scoped to one focus mode, free everywhere else a FAILED row would be reached from (`focus === 'runs'`).
- The CON-78 comment being cited (`keys.js:257-258`, *"a c d f h H j k l L m n N p P q r s S t y"*) is itself an inaccurate/stale artifact — it lists every letter used anywhere in the file (including focus-scoped ones) without distinguishing scope, and for `d` describes a binding that does not exist in this file at all.

This matters because `design.md`'s own "Alternative considered" — bind `a`/`d` directly at the top level, gated on `runs[selected].status === 'failed'` (no new focus mode) — is rejected **solely** on this disproven premise. `design.md`'s own Decision 1 text separately *admits* FAILED rows are structurally unlike QUEUED/QUICK START: *"Unlike QUEUED/QUICK START, FAILED rows also live in the ordinary flat `runs` index space"* — which is exactly why QUEUED/QUICK START needed their own focus modes (their items aren't in the `runs`/`selected` array at all) and exactly why FAILED does not have the same structural need. `t` (view-ticket) and `l` (drilldown) already work today as ordinary top-level bindings conditioned on `runs[selected]`, with no focus mode; `k`/`r` (kill/restart) work the same way one screen over, gated on `isLive(run)` in the drilldown. The simpler alternative the design rejected is directly analogous to these existing, working patterns.

Required: either (a) re-justify Decision 1 on accurate grounds (if there's a genuine UX reason to give FAILED its own scoped cursor — e.g. keeping `j`/`k` confined to just FAILED rows — state that explicitly and drop the false "already claimed" justification), or (b) replace it with the simpler top-level-conditional-binding approach the design incorrectly ruled out. Either way, `proposal.md` #1 and `design.md`'s Context #1 / Decision 1 must stop asserting the disproven premise as settled fact — this was self-approved by the orchestrator from "direct code evidence" that, on inspection, does not support the claim.

**2. Missing wiring: no task threads the new `failedFocus` cursor into row rendering, so the FAILED-local cursor would be invisible.**

`lib/ui/screens/fleet/grid.js` is the only place QUEUED/QUICK START's own local cursor gets a visual highlight: lines 250/257 compute `focused = ctx.focus === 'queue' && ctx.queueFocus === k` / `ctx.focus === 'quickstart' && ctx.quickStartFocus === k`, consumed by `renderQueuedRow`/`renderQuickStartRow`'s `»` marker (`rows.js:195/221`). Ordinary FAILED rows render via `renderRun`/`renderFinishedRow` (`rows.js:98/146`), whose `▸` marker is driven by `rowIndex === ctx.selected` (`grid.js:260/262`) — i.e. `state.selected`, which Decision 1 explicitly leaves untouched when entering FAILED focus ("`j`/`k` moving `selected` onto a FAILED row does NOT itself enter `focus: 'failed'`"). Neither `design.md` nor `tasks.md` mentions `grid.js` or `rows.js` anywhere (`grep -n "grid.js\|highlight\|rows.js" design.md tasks.md proposal.md` → no matches). As specified, an operator who digit-jumps into FAILED focus and presses `j`/`k` would see **no visual indication of which row `failedFocus` points to**, while the stale `▸` marker (still following pre-focus-entry `state.selected`) keeps pointing somewhere else — actively misleading about which row `a`/`d` are about to act on.

Required: add a task wiring `focus === 'failed' && failedFocus === k` into `grid.js`'s per-row `focused` computation (mirroring the queue/quickstart lines above), and the corresponding row-rendering change in `rows.js`/wherever FAILED rows get their own visual highlight.

**3. Missing wiring: no task renders the `markDoneConfirm` "are you sure?" banner.**

`lib/ui/screens/fleet/sections.js`'s `buildHeadTail` (lines 299-330) is where `clearQueueConfirm`/`forceStartConfirm`/`quitConfirm` actually print their confirm banner + hint text via `confirmLines(...)`; those three fields are threaded there via `render.js`'s `render()` (lines 280/286/296, mirroring `state.forceStartConfirm`/`state.clearQueueConfirm`) and via `watch.js`'s `draw()` opts (line 634). `tasks.md` 4.3 only says: *"Wire the confirm gate into `fleet.js`'s `handleKey` ... and into `scrollToShow`'s `winOpts` (so `buildHeadTail` height estimation stays accurate ...)"* — this covers keypress interception and the height-estimate object `scrollToShow` builds for scroll math, but never mentions adding a `markDoneConfirm` branch to `buildHeadTail`'s actual banner-printing logic, nor threading `state.markDoneConfirm` through `render.js`/`watch.js`'s real render opts (as opposed to the height-estimate-only `winOpts` in `controllers/fleet.js`). As specified, pressing `d` would open an invisible confirm gate — subsequent keys are intercepted per 4.3, but the operator sees no on-screen text explaining what's being confirmed, until they guess `y`.

Required: add a task explicitly threading `markDoneConfirm` through `render.js`'s `render()` and `watch.js`'s `draw()` opts, and adding an `else if (markDoneConfirm)` branch to `sections.js`'s `buildHeadTail` that prints the actual warning/confirm-hint text, distinct from the height-estimation-only wiring 4.3 currently describes.

### Non-blocking notes

- Decisions 2 and 3 (the `run.override` event + `deriveStatus` precedence branch, and the retry-visibility refinement reusing `spawnedAt`/`endedAt`) check out against `reducer.js`'s actual chronological-fold/`applyEvent`/`deriveStatus` structure — technically sound, consistent with the CON-48 precedent, and require no new event kind beyond `run.override` (the retry-visibility fix is reducer-only). `session.js`'s `writeSpawnEvent` is a genuine, faithful precedent for the proposed `writeOverrideEvent`.
- Decision 4 (`/concertino-address-failure` as a thin command handing off to the orchestrator's `ADDRESS_FAILURE=true` entry point) is architecturally sound and does not naively lean on the ordinary Setup flow's resume behavior: `setup-worktree.sh`'s idempotency is keyed on the exact branch string passed in, and Setup's own branch-name derivation (`core/roles/orchestrator.md` Setup step 2) is an LLM-derived "3-5-word-description" with no guaranteed reproducibility across invocations — so the design correctly bypasses ordinary Setup and reads the branch name from the audited `run.start` event instead, rather than assuming re-derivation would land on the same worktree. This is good, verified reasoning, not hand-waving.
- Decisions 5, 6, 7 (dashboard-only bookkeeping, FAILED-only scope with the other three panes explicitly audited/documented, design-ticket-type idea filed as CON-100) are consistent with the ticket's escalated answers and are not hand-wavy — the DONE-pane "considered and explicitly deferred" reasoning in particular is a real judgment call, stated plainly rather than silently skipped.
- `lib/cli/emit.js`'s `emitClaude` write-call pattern (line 79, `concertino-deliver.md`) is a clean, direct precedent for the new `concertino-address-failure.md` write task 7.2 describes.
- Minor: tasks.md 3.5/4.4/5.5 reference unit tests in "keys.js/fleet.js controller" tests without naming an exact file; `fleet.test.js` exists and is the likely home, but there's no `controllers-fleet.test.js` the way `controllers-sessions.test.js` exists for sessions — worth a one-line clarification, not blocking.
