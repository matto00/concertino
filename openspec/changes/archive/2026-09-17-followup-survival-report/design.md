## Context

See `proposal.md` — Why. This section records only the measured constraints that shape the approach. Every number below was probed against the live repos and Linear API during Planning, not inferred; the probes and their controls are in `premise-validation.md` and restated here where they drive a decision.

- **The provenance tier is empty; the convention-recovered tier is NOT (corrected after a self-caught false negative).** `ticket.filed` count across both corpora is **0**. A first scan for CON-190's `origin_kind: followup` description convention reported **0 hits** — that result was **wrong**. The real text renders as ``* `origin_kind`: followup`` (a backtick sits between the key and the colon), so the strict needle `/origin_kind:\s*followup/i` could never match it. A formatting-tolerant needle finds **1** CON ticket (**CON-209**, state `backlog`) and **0** HEL, *as measured before this run filed CON-213*. After that filing the same scan returns **2** CON rows (CON-209, CON-213), both `backlog` — independently reproduced by the round-2 design gate. Every ticket-count figure in this document is therefore stated as of a point in time: the CON team held **211** tickets pre-filing and **212** post-filing, and the 159-completed figure is pre-filing. The first probe's controls (impossible needle -> 0; 211/211 descriptions non-empty) proved the scan *read* descriptions and *discriminated*, but never proved the needle could match real-world markdown — the exact zero-hit-grep trap. See Decision 9 and constraint C1.
- **The one recoverable row is partial.** CON-209 yields `origin_kind=followup`, `origin_repo=concertino`, `origin_role=orchestrator`, `origin_phase=setup`, `suggested_by=agent`. `origin_ticket` is **not** recoverable by adjacent-text matching (the value renders as a Linear issue-link macro, not plain text), and there is **no** `triage`/`overlap` data in the description at all. So every convention-recovered row is `overlap=unknown` by construction.
- **n=1 with zero completions is a live misleading-number hazard.** CON-209 is `backlog`, so a naive convention-recovered survival figure is `0/1 = 0%` — an authoritative-looking number off a single row. This is why small-n suppression (Decision 10) is a requirement, not a nicety: zero-n handling alone does not cover it.
- **`fetchOneTicket` cannot see descriptions or state.** `ISSUE_QUERY` selects only `id`, `identifier` and `labels`. A probe using it returned an empty description and falsely failed its own positive control. All description/state-bearing reads MUST go through `fetchTickets`. See constraint C2.
- **CON-190's own run filed CON-209 but never emitted `ticket.filed`.** Its event log carries `evidence` events and no `ticket.filed` at all. The provenance emitter shipped and its very first opportunity was missed — which is itself evidence for this ticket's thesis, and is why Decision 11 requires this run to emit provenance for the follow-up it files.
- **A prose heuristic does recover real rows.** `follow-up from|of|to` matches 14 CON tickets (8 completed) and 41 HEL (15 completed) — independently reproduced exactly by the round-2 design gate against live Linear. The looser bare `follow-up` needle matches 49/105 — too loose to use, because it also matches prose like "no follow-ups needed". This is recoverable signal, but it is text matching, not provenance — and it is a DIFFERENT, weaker marker than the CON-190 convention above, so the two are reported as distinct sources with distinct confidence, never pooled.
- **`origin_role` is degenerate along the TEMPLATE path, not in the event schema.** The `standaloneTicket` render template in `lib/cli/render.js` — the path an orchestrator follows when it triages a `standalone` follow-up — hardcodes `origin_role=orchestrator`, so every template-driven filing reports that role regardless of where the suggestion actually came from. The emitter imposes no limit either — but NOT for the reason an earlier draft of this document claimed. That draft said `emit-event.sh` "validates `origin_role` against the closed role set and accepts any member"; that was **wrong**, and conflated two different fields. The closed-set `case "$ROLE" in orchestrator|executor|evaluator|skeptic|auditor|script|dashboard)` validates the event's own `role=` field. `ORIGIN_ROLE` appears three times in the script — declaration, assignment, and a **presence-only** `[ -z "$ORIGIN_ROLE" ]` check inside the `ticket.filed` required-field block — and has **no value validation whatsoever**, unlike its siblings `origin_kind` and `suggested_by`, which both have real enum checks. So `origin_role=banana` would be accepted and recorded today. That gap is folded into CON-213's scope (see defect 1). A direct emitter call can therefore record a truthful role, and **this run does exactly that**: the CON-213 filing below was emitted with `origin_role=skeptic`, because the suggestion genuinely originated in the design-gate skeptic's change request 1. So this run's own log carries a non-`orchestrator` row, and the report's role axis is NOT single-valued for this run — the `singleValued` annotation is computed from the observed rows (Decision 6 / task 1.6), never assumed. The defect is that the template discards a role it already knows; see "Acceptance-criterion defects" below and CON-213.
- **The Linear client cannot currently see completions.** `OPEN_STATE_TYPES` is `[backlog, unstarted, started]`. `fetchTickets` does accept `opts.stateTypes`, and passing completed states works (159 of 211 CON tickets are `completed`). But neither `QUERY` nor `normaliseTicket` carries `createdAt`/`completedAt`; a raw GraphQL probe confirms both fields are available from the API and return real values.
- **Completion must key on `state.type`, not name.** The Concertino team's completed state happens to be named `Done`, but `In Review` is type `started` and `Canceled`/`Duplicate` are their own types. Keying on the display name would break on a rename and would silently miscount.
- **Essentially the whole escalation corpus predates reliable escalation identity.** Exactly **1** of 378 `escalation.raised` events carries `escalation_id`; the boundary is CON-188's merge at `t=1789595291000`.
- `CONTRIBUTING.md`: zero runtime dependencies, pure-function/driver separation, `npm test` is the whole gate, and **never hand-edit a rendered file** under `scripts/concertino/` — fix `core/` instead.

## Goals / Non-Goals

**Goals:**

- A read-only report that is honest when it has nothing to say, and whose every figure is traceable to a named source tier.
- Computation isolated in a pure, dependency-free module that can be unit-tested over synthetic rows, so the arithmetic is provable without network or event-store I/O.
- The three competing explanations for the follow-up decline made *distinguishable* by the output (volume and survival per period, side by side) rather than adjudicated by the report.

**Non-Goals:**

- **Adjudicating which explanation is true.** With zero provenance rows the report cannot, and must not, pick one. It supplies the shape of evidence that will answer the question once rows exist.
- **Backfilling by inference.** No row's role, suggester, kind, or overlap is ever guessed. Unrecoverable is reported as `unknown`.
- **Emitting any new instrumentation.** This change consumes CON-190's and adds none, so no `schema.change` event is warranted and no procedure script changes.
- **A dashboard surface.** CLI only; a TUI panel is a separate concern.
- Changing the launch pad's default fetch behaviour.

## Decisions

**1. A new `concertino report <name>` subcommand, not a new top-level verb per report.** Follows the established `bin/concertino` dispatch + `lib/cli/<cmd>.js` + `lib/cli/help.js` `USAGE`/`USAGE_ORDER` pattern (`lib/cli/gates.js` is the closest read-only precedent). A `report` namespace leaves room for later reports without another top-level verb each time. *Alternative rejected:* `concertino followup-survival` as its own verb — pollutes the top-level namespace for what is one instance of a general class.

**2. Split pure computation from all I/O.** `lib/followup-survival.js` exports pure functions over plain arrays of rows (`computeSurvival`, bucketing, median); `lib/cli/report.js` does the reading (event store via `lib/ui/store.js`, tickets via `lib/ui/linear.js`) and the printing. This is the repo's existing `render(state) -> string` / stateful-driver convention, and it is what makes Decision 6's control possible. *Alternative rejected:* one command module doing fetch-and-compute — the arithmetic would only be testable through the network.

**3. Two tiers, never summed.** The `provenance` tier (from `ticket.filed`) is authoritative; the `recovered-heuristic` tier (from the `follow-up from|of|to` marker) is indicative. They are printed under separate headings, each figure labelled, the marker disclosed, and **no combined total is ever printed**. This is the single most important decision in the change: summing them would produce exactly the confidently-wrong authoritative-looking number this class of artifact is prone to. *Alternative rejected:* one blended number with a footnote — a footnote does not survive being quoted.

**4. Additive-only extension of the Linear client.** Add `createdAt`/`completedAt` to `QUERY` and `normaliseTicket`; pass `stateTypes` explicitly from the report. `OPEN_STATE_TYPES` and the launch pad's defaults are untouched, so no existing capability's requirements change. Survival keys on `state.type === 'completed'`. *Alternative rejected:* a second, separate GraphQL query module — duplicates auth/paging plumbing the client already owns correctly.

**5. Missing credentials fail loudly; an empty corpus succeeds quietly.** These are different conditions and must not share an outcome. No `LINEAR_API_KEY` means completion state is unknowable — exit non-zero with a clear message, because reporting 0% survival there would be a fabricated number. Zero `ticket.filed` rows is a true, informative answer — print the explicitly-empty provenance result and exit 0.

**6. The computation carries its own falsifiability control, as a test.** `test/followup-survival.test.js` includes a mutation-style control: the same `computeSurvival` over a fixture where survivors are flipped to non-survivors MUST produce a different percentage, and a fixture with a differing `suggested_by` distribution MUST produce differing per-segment figures. A report whose number cannot be made to change by changing its input is measuring nothing — the live-data analogue is already established (the heuristic tier's completed fraction is 57% CON / 37% HEL against a 75% base rate, so the metric demonstrably discriminates rather than echoing the base rate).

**7. Period bucketing by ISO week, chronologically, with empty periods explicit.** Matches the unit the decline was originally observed in (W33–W38). An empty week prints "no data", never "0%" — a zero-denominator rendered as zero survival is the same fabrication as Decision 5's.

**8. Report escalation-derived context only if segmented at the CON-188 boundary.** Given 1 post-boundary event of 378, the report states the boundary and the two populations rather than any pre/post rate comparison, which would be a rate over n=1.

## Acceptance-criterion defects (stated loudly, not worked around)

1. **"Segment by originating role (executor / evaluator / skeptic / auditor / orchestrator)" cannot resolve five roles from template-driven filings.** The `standaloneTicket` template hardcodes `origin_role=orchestrator`, so in normal operation the axis collapses to one bucket even though the emitter would accept any role. The axis is implemented as written and the report labels it single-valued **only when the observed rows actually are**. Fixing the template to thread the originating role through is **filed as CON-213** (not merely promised — see Decision 11 and task 6.4a). CON-213's scope also now covers adding the missing closed-set validation for `origin_role` itself (see the corrected Context bullet above): the field is recorded with no value validation at all today, so a wrong role is accepted silently. Recorded here rather than filed separately because it is the same emitter/provenance defect in the same code path.
2. **"Backfill what is recoverable" recovers very little — one row, not zero.** Exactly one ticket (CON-209) carries the CON-190 convention, and it carries no `triage`/`overlap` and no plain-text `origin_ticket`. An earlier draft of this document claimed zero, from a false-negative needle; that is corrected above. The prose heuristic recovers more rows but is a weaker marker. Both are reported under Decision 9 as recovered, marker-labelled, and small-n-suppressed, never as provenance.
3. **The ticket's own decline figures are imprecise.** It states "fell 7x" and "16, 14, 3, 7, 2, 1"; the canonical probe measures W36 as **9**, not 7, and an endpoint ratio of **16x**, not 7x. Corrected in `ticket.md`; the qualitative decline is real and confirmed.

**8a. The recovered tier EXCLUDES anything the provenance tier already counted (dedupe by ticket id), and discloses the overlap it removed.** Round 2 of the design gate found that the two tiers are overlapping, not complementary, and proved it with this run's own data: the `standaloneTicket` template writes `origin_kind: followup` / `origin_ticket:` into **every** filed ticket's description text unconditionally, whether or not the separate, optional `provenanceEmit` block also runs. So CON-213 — filed by this very run to give the provenance tier its first row — has both a `ticket.filed` event AND convention-matching description text, and a naive reading of the two tiers would count the same ticket twice. Left unaddressed, Decision 3's "never summed" guarantee would hold only at the presentation layer while the underlying sets silently intersected.

Therefore: the recovered tier is computed as `recovered \ provenance`, keyed on ticket id, so it means strictly "what provenance missed" — and the report prints an explicit disclosure of the form "N recovered rows excluded because they already have provenance", so the exclusion is visible rather than inferred. *Alternative rejected:* permitting the overlap with only a footnote — the tiers' independence is the entire basis on which a reader is invited to compare them, so an undisclosed intersection is exactly the "authoritative-looking number over untrustworthy input" failure this design exists to prevent.

**9. The recovered tier is split by marker, and every text needle carries a positive control.** Recovery distinguishes `convention` rows (CON-190's `origin_kind:`/`origin_ticket:` markers, matched formatting-tolerantly so backticked/bolded renderings match) from `prose` rows (the weaker `follow-up from|of|to` heuristic). Each recovered row records which marker matched. Every needle MUST be accompanied by a positive control asserting it matches a known-present, real-world-formatted example; a zero-hit result from a needle with no positive control is not evidence. *Rationale:* this change's own Planning shipped a false-negative zero on exactly that omission.

**10. Small-n suppression, not just zero-n.** A survival percentage is suppressed and reported as `small-n (n=<k>)` whenever the denominator is below a stated minimum (default 5), for the overall figure and every segment and period bucket. The counts are still shown; only the percentage is withheld. *Alternative rejected:* printing `0%` with a footnote — with n=1 that is the confidently-wrong number this design exists to prevent, and a footnote does not survive being quoted.

**11. This run emits provenance for the follow-up it files.** The `origin_role`-emitter follow-up that Decision/defect 1 names is actually filed, and a `ticket.filed` event is emitted for it through the real emitter. *Rationale:* CON-190 filed CON-209 and skipped the emit, leaving the provenance tier empty; a ticket about whether promised follow-ups get delivered must not repeat that. This also gives the provenance tier its first genuine row, so the tier is exercised end-to-end rather than only in fixtures. **Known artifact, now corrected:** CON-213's description was first written with the template's default `origin_role: orchestrator` while its emitted event correctly carried `origin_role: skeptic` — two provenance records for one filing, disagreeing, with the wrong one being the human-readable and text-scannable copy. The description has been corrected to `skeptic`. This is itself direct evidence for CON-213's own thesis: provenance written by hand into ticket prose drifts from provenance emitted as an event, which is why the template must thread the real role through **both**, not just one. **Done:** CON-213 is filed, and `ticket.filed` was emitted for it and verified present in `.concertino/runs/CON-192/events.jsonl` with `origin_role=skeptic`, `origin_kind=followup`, `suggested_by=agent`, and a real `triage` payload (`overlap=none`, `recommendation=standalone`) produced by `triage-followup.sh` rather than hand-written.

## Risks / Trade-offs

- **The report ships with an empty authoritative tier and could read as useless.** → This is the honest state of the data and is the spec'd behaviour, not a defect. The heuristic tier and the synthetic-fixture tests demonstrate the machinery works, so the first real rows are scored correctly with no further change.
- **The heuristic marker is quoted as though it were provenance.** → Mitigated by Decision 3: tier labels on every figure, the marker itself printed, and no combined total to quote.
- **Live Linear data makes the report's output non-deterministic across runs.** → Mitigated by keeping all arithmetic in pure functions tested over fixtures; the command module's own tests inject a fake transport rather than hitting the network, following `test/linear.test.js`'s existing pattern.
- **A text needle silently under-matches and a zero is read as a fact.** -> Decision 9's positive-control requirement, promoted to standing constraint C1. This risk already materialised once in this change's own Planning.
- **Two tiers silently share rows and are read as independent.** -> Decision 8a's dedupe plus a rendered exclusion disclosure, promoted to standing constraint C4. Found by the round-2 design gate using this run's own filing as the counter-example.
- **A small denominator is quoted as a rate.** -> Decision 10's suppression, promoted to C3.
- **`--help` regression.** → `test/cli-help-flags.test.js` already enumerates every subcommand; adding to `USAGE_ORDER` without a usage block would fail it. Verified by running that suite.
- **Median of an even-sized set / of an empty set.** → Defined explicitly: mean of the two middle values; an empty set yields `null` and prints "no data", never `0`.

## Migration Plan

None required. Additive CLI surface plus two additive GraphQL fields; nothing is removed, renamed, or re-defaulted. Rollback is deleting the new modules and reverting the two additive field lists.
