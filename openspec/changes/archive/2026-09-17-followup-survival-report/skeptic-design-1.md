### Analysis against the five attack vectors

**1. Two-tier decision, given both tiers' authoritative source is allegedly empty today.** This premise is only half true. The `provenance` tier (`ticket.filed`) is genuinely empty (0/0, confirmed above). But the `recovered-heuristic` tier is **not** built from the CON-190 `origin_kind: followup` description-convention scan that returned 0 — it is built (per Decision 3 and task 4.3) from the separate prose regex `/follow[- ]?up\s+(from|of|to)\b/i`, which design.md states matches 14 CON / 41 HEL tickets with real completions. So the report, as specced, will not ship two blank tiers — it ships one empty (honestly-labelled) tier and one populated (honestly-labelled, marker-disclosed) tier. Given the never-summed constraint, disclosed marker, and separate headings, I judge this sufficient to avoid the confidently-wrong-number failure mode. This is not a defect.

**2. Testability / vacuous scenarios.** I did not find a scenario that would pass vacuously against an empty corpus — the empty-corpus scenarios all carry a specific, checkable negative assertion (no `%` sign, no combined total, exits 0) rather than "did not crash." However, see Revision 3 below: the specific real-world state the report ships in today (empty provenance + populated heuristic, simultaneously) has no automated regression test, only a one-off manual run (task 6.5). That is a coverage gap, not an unfalsifiable scenario, but it means the two-tier interaction that is the entire point of this ticket right now is not locked in by the test suite.

**3. "Acceptance-criterion defects" documented-and-proceed vs. escalating.** I judge this an acceptable, non-blocking design choice, not a case that needed escalation: the report fulfills the letter of the AC (implements the five-role segmentation as specified) while refusing to misrepresent its degenerate result, which is strictly more honest than either silently working around it or blocking the whole change on fixing an upstream emitter that is explicitly out of scope. However — design.md promises "fixing the emitter... is a genuine follow-up, out of scope here" and no task anywhere in tasks.md operationalizes that promise (see Revision 1). For a ticket whose entire subject is "measure whether filed follow-ups get delivered," failing to actually file the follow-up it names is a real, on-theme gap.

**4. Falsifiability control (Decision 6 / tasks group 2).** This is a real control, not theatre. Tasks 2.1-2.3 are true mutation-style assertions against the pure `computeSurvival` function (flip survivors, assert `pct` changes; vary `suggested_by` distribution, assert segment maps differ; pin both ends of the scale at 100/0). Because Decision 2 isolates all arithmetic into dependency-free functions over plain arrays, these controls are actually exercised against the real computation path, not a mock. The live-data corroboration cited (57% CON / 37% HEL against a 75% base rate) is a reasonable existence proof that the heuristic tier discriminates rather than echoing a base rate, though I did not re-run that specific query myself.

**5. Tasks whose stated verification would pass while measuring nothing.**
- Task 4.4's verification ("verify with a fake transport... that no network call occurs in tests") only proves the test harness intercepts the transport — it does not assert that the `stateTypes` actually passed to the fetch includes a completed state. A caller that dropped or mistyped `opts.stateTypes` (the entire point of task 3 wiring) would pass this verification unchanged, because "no network call occurs" is true regardless of what arguments were passed to the fake transport. This is exactly the "verification that would pass while measuring nothing" failure mode named in the request.
- Task 4.9's verification ("does not print a pre/post rate") is a valid negative check but should be paired with a positive assertion that the boundary populations actually are printed with the stated counts (86+292 style, or whatever the live numbers are) — as written it would pass even if the feature under-delivers (e.g., prints the boundary timestamp but omits the population counts), since "does not print a rate" is true of that degenerate output too. This is minor compared to 4.4 but the same shape of gap.

### Verdict: REFUTE

### Change Requests

1. **Add a tasks.md line item to actually file the follow-up ticket** design.md names ("fixing the emitter to record the role that actually originated a suggestion... is a genuine follow-up, out of scope here"). As written this is a promise in prose with no corresponding action anywhere in tasks.md — for a ticket about whether promised follow-ups get delivered, that gap should not ship undetected. Either add a task ("6.6 File a CON follow-up ticket for the origin_role emitter fix; verify by the new ticket id appearing in the change's PR description or a comment on CON-192") or explicitly state in design.md that filing it is deferred to the human/orchestrator and record who owns that decision.

2. **Strengthen task 4.4's verification** to assert the fake transport was actually invoked with `stateTypes`/`states` covering a completed state (e.g., assert the captured call args include `'completed'`), not merely that no real network call occurred. As written, the test can pass even if the report never actually requests completed-state tickets — silently reproducing exactly the "silently sees zero Done tickets" failure mode design.md itself calls out as the reason this task exists.

3. **Add an automated (not manual-only) test exercising the simultaneous empty-provenance + populated-heuristic state** — the literal state the report ships in today. Task 6.5 checks this once, by hand, against live data; nothing in `test/cli-report.test.js` locks it in as a regression test with a fake transport returning heuristic-matching fixture tickets and an empty event store. Without this, a future change could silently break the one behavior this ticket exists to demonstrate, and the test suite would stay green.

4. **Strengthen task 4.9's verification** to include a positive assertion that the boundary timestamp and both population counts are actually printed, not only the negative assertion that no pre/post rate is computed. As written it would pass against an under-delivering implementation that prints the boundary but drops the population counts.

### Non-blocking notes

- The heuristic-tier disclosure (Decision 3: separate heading, marker printed, no combined total) is a sound mitigation for the "confidently wrong number" risk named in attack vector 1; I have no further objection there once Revision 3 closes the coverage gap on the interaction itself.
- I did not independently re-run the live Linear scans (211 CON / 1054 HEL description-convention scan, the 14/41 prose-heuristic match counts) given effort budget; every independently-recomputable claim I did check (event counts, hardcoded `origin_role`, missing GraphQL fields) matched exactly, which is reasonable but not conclusive corroboration for the claims I didn't re-run.
