**D2's trap semantics — measured, not assumed.** I wrote a `#!/usr/bin/env bash` + `set -uo pipefail` script (matching this script's own header, verified) with an `EXIT` trap, backgrounded it, and sent `SIGTERM`: the trap fired and the shell exited 143. So the design's claim that an `EXIT` trap covers a harness `SIGTERM` is true under this script's actual shell, not merely hoped. Explicit-restore-then-trap double firing is harmless (`reset --soft` to the commit HEAD already holds is a successful no-op), which is also D3's argument and it is sound for the same reason: a failed forward reset did not move the ref, so the trap's restore targets the current value.

**D4 vs CON-164 D6 — read the archived source.** `openspec/changes/archive/2026-09-09-squash-branch-dry-run-mode/design.md` D6 bundles two things: the dry/wet exit-code divergence (upheld as correct) and the resulting stranded branch (punted to CON-170 by name). "No owner named" is justified here.

**Spec delta hygiene.** The `MODIFIED` header matches the live requirement at `spec.md:114` exactly, and both pre-existing scenarios are reproduced verbatim — no scenario is silently dropped by the whole-requirement replacement. Most new scenarios are genuinely failable: "Commit hooks still run" fails the instant anyone switches to `commit-tree` (D5's deliberate double-duty fixture), and "A successful squash is unaffected" would catch a trap that misfires.

### Verdict: REFUTE

One gap, and it is squarely in the mechanism the design itself flags as riskiest.

### Change Requests

1. **`tasks.md` §3 has no coverage for D2's trap — the one mechanism with no other test, and a new spec scenario asserts its behaviour.** Tasks 3.1–3.7 cover hook-rejection restore, the mutation red, the empty staged set, the success path, `DRY_RUN=1`, and the pre-existing scenarios. Every one of those exercises the **explicit** restore on the commit-failure branch (3.5 only proves the trap does *not* fire). Nothing anywhere exercises the trap actually firing. Yet the spec delta adds a requirement sentence ("SHALL be armed ... against abnormal termination") and a scenario ("The step is terminated between the reset and the commit → HEAD is restored ... as the step terminates") that assert exactly that behaviour. As planned, that scenario is **unverified**, and by AC6 the new failure path needs coverage that is proven failable, not asserted. This also matters because the trap is the added mutation on a failure path that design.md's own Risks section names as the thing that could damage a branch that today merely looks damaged — installing it wrong (mis-scoped arming window, disarm in the wrong place, restore helper unreachable under `trap`'s evaluation) would ship silently.
   It is testable with the machinery already chosen: give the fixture a `pre-commit` hook that `sleep`s instead of exiting 1, run the script in the background, `kill -TERM` it while it is parked inside the hook (i.e. after the forward reset, before the commit returns), then assert `git rev-parse HEAD` equals the pre-run commit rather than the merge-base. Add that as a task in §3, and add its failability arm the same way 3.3 does (delete the `trap` line via the `PRISTINE_SCRIPT` snapshot machinery, assert HEAD **is** at merge-base, restore) — otherwise the trap's assertion is green-by-construction.

### Non-blocking notes

- The widened requirement's first sentence ("SHALL NOT move HEAD ... on any path that ends in anything other than a completed squash commit") is, read literally, falsified by the very mechanism the next paragraph mandates: record-and-restore *does* move HEAD, transiently. The intent is unambiguous from context and from tasks.md, so no implementer would build the wrong thing, but "SHALL NOT **leave** HEAD, the index, or the working tree changed" would say what is meant without contradicting the paragraph below it.
- The abnormal-termination scenario says "killed or otherwise terminated abnormally". `SIGKILL` is uncatchable, so as written the scenario is false for the most literal reading of "killed". Qualifying it to catchable termination (`SIGTERM`/`SIGINT`/`SIGHUP`) would make it exactly as strong as it can actually be, and no weaker.
- The spec's "The restore itself fails" scenario has no corresponding task. Inducing a `git reset --soft` failure is genuinely awkward, so verification by direct inspection of the diagnostic is a reasonable answer — but say so in tasks.md rather than leaving the scenario with no verification route at all.
- Real-world nuance D2 does not mention: a consumer's `pre-commit` hook can itself mutate the index (a `lint --fix` + `git add` chain) before failing. In that case the restore returns the *ref* faithfully but the index is not bit-identical to invocation time, through no fault of this script. Worth one sentence in D2 so a future reader does not read AC1's "index ... restored to exactly the state" as a guarantee the script can unilaterally make.
- If the explicit restore fails and prints its loud two-SHA diagnostic, the `EXIT` trap will then attempt the restore a second time and may print it again. Harmless (and the second attempt could even succeed), but the executor should be aware the diagnostic can appear twice.
