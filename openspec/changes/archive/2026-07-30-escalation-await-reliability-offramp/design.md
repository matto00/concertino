## Context

Round 1 of the design-soundness skeptic gate (`skeptic-design-1.md`) measured Part 1's originally-proposed root cause against real event-log traces and found the ticket's own premise false: CON-30 (twice) and CON-35 were all killed at **599.9s**, and CON-22 ran to completion at **+3600.5s from raise** — `timeout: 600000` *was* being honored every time; the harness's call cap was never the actual problem. The measured defect is that `core/scripts/emit-event.sh` never sources `.concertino.env` at all (every sibling procedure script does — `assert-phase.sh`, `start-servers.sh`, `cleanup.sh`, `resolve-speed.sh`, `setup-worktree.sh`), so `CONCERTINO_ESCALATION_TIMEOUT_MIN` (rendered into this project's `.concertino.env` as 8 minutes — `bin/concertino`'s own `DEFAULT_ESCALATION_TIMEOUT_MIN`, since this project's config sets no explicit override) never applies; `--await` always falls back to its 60-minute default — six times the harness's 10-minute call cap, which guarantees the harness will always kill the call first. CON-22's own `escalation.timeout` firing at exactly +3600.5s is direct confirmation the 60-minute fallback is what actually ran there.

Round 1 also established that copying the sibling scripts' exact sourcing pattern (`[ -f "${SCRIPT_DIR}/.concertino.env" ] && source ...`, where `SCRIPT_DIR` is wherever the *currently executing* script file physically lives) would not actually fix the real failure: `.concertino.env` is gitignored and is only copied into a worktree when listed in the project's `envFiles` config (empty by default in this project); a fresh worktree's own `scripts/concertino/.concertino.env` genuinely does not exist. Since escalations are raised well after the orchestrator has `cd`'d into `WORKTREE_PATH`, `emit-event.sh` is, in the real failure case, invoked with the *worktree's* copy as `SCRIPT_DIR` — which never has `.concertino.env` even after the sibling-script fix.

Round 2 (`skeptic-design-2.md`) probe-verified the corrected fix directly (Probe A: reproduced the failure from a real worktree against the unpatched script; Probe B: the same setup with the proposed two-branch sourcing snippet applied, confirmed the main-checkout's configured value is picked up from inside the worktree) and confirmed Part 2 sound with no change requests in either round. It REFUTE'd on a second mechanism this design had proposed in round 1's response — a read-only "was it already answered?" safety-net check — for a structural reason: after *any* `--await` exit (killed or naturally timed out), the event log's most recent entry for that ticket is *always* `escalation.timeout` (both `on_kill`'s trap and the natural-deadline path write it unconditionally), so a check keyed on finding a recorded `escalation.answered` there can never succeed at the point it was specified to run. Worse, the round found that the answer an orchestrator actually stands to lose in this scenario lives in `answer.json` (written directly by the dashboard) — never in the event log as `escalation.answered`, since only `--await` itself ever promotes `answer.json` into that event, and by construction it didn't get the chance to. Round 2 explicitly named dropping this second mechanism a legitimate resolution, since the root-cause fix and Part 2 are independently sound without it.

This design reflects that outcome: the root-cause fix, the trust off-ramp, and nothing else.

## Goals / Non-Goals

**Goals:**
- Make `CONCERTINO_ESCALATION_TIMEOUT_MIN` (and any other `.concertino.env` setting) actually apply to `emit-event.sh`, in the real invocation context (from inside a worktree) as well as the main checkout, so the script's own deadline lands inside the harness's call-timeout cap and the script's own natural timeout — not a harness kill — is what ends an unanswered wait in the ordinary case.
- Give the orchestrator role a concrete, load-bearing stopping point for skepticism about a chat-relayed answer's authenticity, so a properly recorded answer is never re-litigated.

**Non-Goals:**
- A `--resume`/re-issue-loop mechanism for continuing an already-timed-out wait without re-raising. Proposed in round 1's response to the first REFUTE, rejected in round 1 itself — see "Rejected approaches" below.
- A read-only "was it already answered?" safety-net check before falling back to chat. Proposed in round 1's response, rejected in round 2 — see "Rejected approaches" below. A correct version of this idea (reading `answer.json` directly with a staleness rule) is left as a follow-up (Open Questions), not attempted a third time in this change.
- Auditing or fixing the same latent `.concertino.env`-sourcing gap in the sibling scripts (`assert-phase.sh`, `start-servers.sh`, `cleanup.sh`, `resolve-speed.sh`, `setup-worktree.sh`). Flagged in Open Questions as likely follow-up work; out of scope for this ticket, which is specifically about escalation reliability.
- Changing `CONCERTINO_ESCALATION_TIMEOUT_MIN`'s default value or `dashboard.escalationTimeoutMinutes` — the configured 8-minute value is a project choice this change makes *actually take effect*, not something it re-tunes.
- Changing how the dashboard writes `answer.json` (`lib/ui/store.js`'s `writeAnswer`) — untouched.
- Weakening skepticism about *new* claims — the off-ramp clause only closes the loop on a question that has already gone through one of this project's own defined resolution mechanisms.

## Rejected approaches

### `--resume` / re-issue loop (rejected round 1)

- After *any* kill (harness-imposed or otherwise), `on_kill`'s existing trap already writes `escalation.timeout` as the ticket's most recent event — the exact condition the proposed "still open, safe to resume" trigger required to be *absent*. The trigger could not fire in the scenario it existed to handle.
- `lib/ui/reducer.js` nulls `run.escalation` on `escalation.timeout`, and `watch.js` bounces the human off the escalation screen and drops it from the cross-screen banner. By the time any resume logic would run, the question is not displayed anywhere in the dashboard and no `answer.json` will ever be written for it.
- CON-22 independently confirms a killed `--await` process can outlive its own Bash tool call by roughly 50 minutes, still polling and eventually writing its *own* `escalation.timeout` well after the orchestrator recorded the real answer through the chat fallback — a resume mechanism adding a second concurrent poller for the same `answer.json` would make races like this worse, not better, without first solving orphan detection.

### Read-only "already answered?" safety-net check (rejected round 2)

Proposed as `check-escalation-answer.sh <WORKTREE_PATH> <TICKET_ID>`: scan the ticket's event log for the most recent event among `escalation.raised`/`escalation.answered`/`escalation.timeout`; if it's `escalation.answered`, report the recorded answer instead of falling back to chat. Round 2 found this reproduces the same structural defect as `--resume`, one level up:

- **The success branch is unreachable at its specified call site.** The call site was "on a non-zero `--await` exit, before falling back to chat" — but every reachable state at that instant already has `escalation.timeout` as the most recent event (both the natural-deadline path and `on_kill` write it unconditionally on every exit that isn't a clean answered-exit-0). `core/roles/orchestrator.md`'s own existing text states this invariant outright: *"Non-zero exit: it timed out, or the wait was killed. Either way `--await` has already recorded `escalation.timeout`."* A check for `escalation.answered` at that exact point checks a condition its own trigger has already ruled out.
- **The answer that a kill actually loses was never in the event log to begin with.** `lib/ui/store.js`'s `writeAnswer` writes only `answer.json`; `emit-event.sh` is the *only* thing that ever promotes it into an `escalation.answered` event, and by construction the killed process never got to do that. Round 2's Probe C demonstrated this directly: an answer written to `answer.json` moments before a kill survives on disk, untouched, while the event log's most recent entry says only `escalation.timeout` — the exact case this check was meant to catch, and the exact case it cannot see.
- A correct version would need to read `answer.json` directly (not the event log), with an explicit staleness rule (e.g. accept it only if its mtime postdates this escalation's own `escalation.raised` timestamp — mirroring the staleness reasoning `emit-event.sh`'s own pre-poll discard logic already applies) to avoid trusting a leftover answer that belongs to an unrelated, earlier question. That is real, independent design work — matching-rule precision, and reconciling it with the residual cases (session restart, compaction) that have no `--await` exit code to hook in the first place, since the orchestrator restarting is a fresh context with nothing to catch a non-zero exit from. Deferred to a follow-up ticket rather than attempted a third time here (see Open Questions).

## Decisions

### Decision 1 — `emit-event.sh` sources `.concertino.env`, with a main-checkout fallback for the worktree case

Immediately after `ROOT="$(main_checkout)" || exit 0` (the line that already resolves the main checkout for the log path — this reuses that same resolution rather than adding a second one), add:

```bash
# shellcheck disable=SC1091
if [ -f "${SCRIPT_DIR}/.concertino.env" ]; then
  source "${SCRIPT_DIR}/.concertino.env"
elif [ -f "${ROOT}/scripts/concertino/.concertino.env" ]; then
  source "${ROOT}/scripts/concertino/.concertino.env"
fi
```

The first branch matches the sibling scripts' existing convention exactly (covers being invoked directly from the main checkout, and is sync-relocatable if the rendered output directory ever moves). The second branch is the one that actually fixes the observed failure: `emit-event.sh` is, in real runs, invoked via a relative path from inside `WORKTREE_PATH` once Planning is underway, where `SCRIPT_DIR` is the worktree's own (never-populated) copy of `scripts/concertino/`; `ROOT` — already correctly resolved via `git rev-parse --git-common-dir`, which works from any worktree — points back to the main checkout, whose `scripts/concertino/.concertino.env` is the one `concertino sync` actually generates. Neither branch fires in a throwaway test repo with no `.concertino.env` anywhere (every existing test in `test/scripts/emit-event.test.sh`), so `TIMEOUT_MIN`'s `${VAR:-60}` fallback is completely unaffected there — zero behavior change for the entire existing suite. Probe-verified in round 2 (Probe B): the exact snippet above, applied to the real script and run from a real worktree against a `.concertino.env` present only in the main checkout, correctly picked up the configured value.

`source` unconditionally reassigns whatever `.concertino.env` sets, which means a sourced `CONCERTINO_ESCALATION_TIMEOUT_MIN` **overrides** an already-exported value of the same name from the calling process's environment — this matches the sibling scripts' existing convention exactly (they source unconditionally too) and is a deliberate, pre-existing project convention (config file wins over ambient env), not something this change introduces. New tests added under Decision 1 must therefore never place a `.concertino.env` anywhere a pre-existing test in the same suite could pick it up — see Decision 1's test task for how this is kept isolated.

Alternatives considered: matching only the sibling scripts' `SCRIPT_DIR`-only pattern was rejected — verified against this ticket's own worktree that it would not actually have fixed the observed failure, since `.concertino.env` is never copied into a worktree by default. Hardcoding `${ROOT}/scripts/concertino/.concertino.env` as the *only* path (dropping the `SCRIPT_DIR` branch) was rejected because it would silently ignore a project that renders to a non-default `--out` directory when the script happens to be run from there directly; checking the local copy first preserves that case exactly as the sibling scripts already do.

### Decision 2 — The trust off-ramp is a new clause in "How to raise one", not a new mechanism

Unchanged from the original design and confirmed sound by the skeptic in both rounds, with no change requests against it in either. No new event kind, no new script, no new field. The clause instructs the orchestrator, in the document's own imperative voice, to:
1. Corroborate a claim of human intent against independently verifiable ground truth (ticket state, PR state, config/git state) *before* recording an answer — exactly what CON-30 already did correctly.
2. Treat the moment an answer is recorded through `--await`'s `answer.json` path or the documented manual `escalation.answered` fallback as **terminal** for this run — proceed on it, not "a chat message that happened to convince you."
3. Never reopen a question already resolved that way; new suspicion attaches only to *new* claims going forward.
4. Distinguish this from an unsolicited claim with no standing escalation behind it (no `escalation.raised` in the log) — that case still needs independent verification or a proper escalation before acting on anything irreversible.

Placed immediately after the existing "Exit 0 / Non-zero exit" bullets in "How to raise one" — the same section a reader is already in when handling an answer — rather than in Guardrails or a new top-level section. Round 1 flagged a potential prose tension with the (then-proposed) re-issue loop; round 2 confirmed that tension is resolved (task 5.5) by scoping the off-ramp explicitly to *answers*, never *timeouts* — `core/roles/orchestrator.md`'s existing text already states "a timeout is never an approval"; the new clause sits consistently alongside that rather than contradicting it. With the re-issue loop and the safety-net check both dropped, this tension no longer has a second mechanism to conflict with at all.

## Risks / Trade-offs

- [The main-checkout fallback in Decision 1 assumes the rendered scripts live at `<repo-root>/scripts/concertino/` relative to `ROOT`] → Mitigated: this matches the project's actual, default `concertino sync` output layout (verified directly against this repo, and probe-verified in round 2), and the `SCRIPT_DIR`-first branch still covers any project that renders to a custom `--out` and happens to invoke the script from there.
- [The sibling scripts likely share the same `SCRIPT_DIR`-only gap, unfixed by this change] → Explicitly out of scope (Non-Goals); flagged in Open Questions as follow-up. Their env vars default harmlessly today, unlike `CONCERTINO_ESCALATION_TIMEOUT_MIN`, so the urgency is lower — though round 2's non-blocking notes flag `resolve-speed.sh`'s `CONCERTINO_HARNESS` fallback as a concrete instance worth naming in that follow-up.
- [Dropping the safety-net check means an answer genuinely lost to a kill (written to `answer.json` moments too late) is not recovered by this change — the orchestrator still falls back to chat and re-asks] → Accepted trade-off: Decision 1 substantially shrinks how often a kill happens at all (the script's own deadline now lands inside the harness cap in the ordinary case), and the existing chat fallback + this change's own trust off-ramp (Decision 2) together mean a human re-answering in chat is handled cleanly and is never re-litigated once recorded. A real recovery mechanism is left to a follow-up (see Open Questions) rather than shipped half-verified a third time.
- [`source`-based unconditional override of an already-exported `CONCERTINO_ESCALATION_TIMEOUT_MIN`] → Documented explicitly in Decision 1 as matching existing sibling-script convention; new tests are written to avoid placing a `.concertino.env` anywhere an existing test case could pick it up unintentionally.

## Migration Plan

No data migration. `emit-event.sh`'s change is additive: it gains a sourcing step that only changes behavior when a `.concertino.env` is actually found at one of the two checked locations (never true in the existing test suite's throwaway repos). Land the script change and the role-prose off-ramp together; refresh the tracked rendered copies by hand (see tasks.md section 4 — **not** a full `concertino sync`, which would sweep in pre-existing, unrelated vendored drift already present in this repo's main checkout), and land all of it in one PR (per the ticket's own instruction that both parts ship together). No feature flag needed.

## Open Questions

- Whether the same `.concertino.env`-sourcing gap exists in the five sibling scripts, and whether it's worth a follow-up ticket to fix uniformly (e.g. by extracting a shared sourcing helper) rather than leaving each script to carry its own copy of Decision 1's two-branch logic. `resolve-speed.sh`'s harness-detection fallback is a concrete instance likely worth naming explicitly in that follow-up (round 2 non-blocking note). Not attempted here — scoped to `emit-event.sh` only, per this ticket's title.
- Whether a correct version of the dropped safety-net check (reading `answer.json` directly, with a staleness rule anchored to the escalation's own `raised` timestamp, and a trigger that also covers session-restart/compaction resume — not just a non-zero `--await` exit code) is worth building as its own follow-up ticket. Left unbuilt here after two rounds of finding the event-log-based version structurally unreachable.
- Whether the CON-22-style orphan-poller hazard (a killed process still running and eventually writing a stray `escalation.timeout` well after the run has moved on) needs its own fix now that Decision 1 shrinks its window — left as a candidate follow-up ticket, not solved here.
- Whether `TIMEOUT_MIN`'s hardcoded `${CONCERTINO_ESCALATION_TIMEOUT_MIN:-60}` fallback (round 3 non-blocking note) should itself be lowered to match `bin/concertino`'s own `DEFAULT_ESCALATION_TIMEOUT_MIN` (8) — after this fix, 60 minutes only applies when *no* `.concertino.env` is found at either location, which is exactly the state of a fresh clone before anyone has run `concertino sync` (the vendored scripts are committed; `.concertino.env` is gitignored and doesn't exist until sync generates it), so the original failure mode remains reachable there. Non-Goal for this ticket (it re-tunes a default rather than making an existing one take effect); left as a named follow-up.
