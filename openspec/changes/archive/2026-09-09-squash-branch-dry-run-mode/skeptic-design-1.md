## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)

- **Base is what the brief claims.** `git log --oneline -3` in the worktree: `2101a78 CON-162 ...`, `fc88cd0 CON-163 ...`. Working tree clean apart from the untracked change dir.
- **Read `core/scripts/squash-branch.sh` in full (296 lines), not a summary.** The structure the design describes in §Context steps 1–8 is accurate: argument binding (71–79), worktree check (81–84), D1 merge-base + criss-cross refusal (95–106), D3 base-advancement logging (109–116), prospective staged set computed without moving HEAD (120–124), CON-162 on-disk/staged-blob/divergence refusals (139–180), declaration parse (182–208), unconditional staged count+list print (240–246), the two guard refusals (249–280). The single `git reset --soft` is at 284.
- **The load-bearing claim is only PARTLY true.** The design asserts (§Context) that step 9 "is the **only** mutation in the script, and every validation and every refusal lives strictly above it", and (D2) "Only the success path differs, and only by substituting an early `exit 0` for reset-then-commit. **Both exit 0.**" The file contradicts the second half: there are **two non-zero exits below the mutation point** —
  - `284–287`: `if ! git_wt reset --soft "$MERGE_BASE" ...; then echo "FAIL git reset --soft ... failed"; exit 1; fi`
  - `289–292`: `if ! git_wt commit -q -m "$SUBJECT" ...; then echo "FAIL git commit failed after guard passed"; exit 1; fi`
  These are not *guard* refusals, so the exit-code-identity argument holds for every **validation** outcome. It does not hold for every **path**, which is what the artifacts claim. See CR1.
- **The divergent path is reachable, not theoretical.** A branch with an empty prospective staged set passes the guard: at 249 `UNEXPECTED` is empty so the branch is skipped, and at 269 `UNEXPECTED` is empty so no refusal fires — control reaches 284. The wet run then resets and runs `git commit` with nothing staged. Reproduced that this exits 1: fresh `git init` + empty base commit, then `git commit -q -m "empty squash"` → `nothing to commit, working tree clean`, `exit=1`. The script passes no `--allow-empty` (line 289). So on that input a dry run exits **0** ("guard passed") and the identical wet invocation exits **1** — a direct violation of ticket AC3 and of the spec delta's unqualified SHALL.
- **Mutation-proof targeting is correct.** Tasks 2.1–2.3 build a *passing* fixture (mirroring the existing 4.5 fixture at test file line 774) and assert HEAD / `write-tree` / `status --porcelain` / commit count unchanged; task 3.1 mutates the script to delete the dry-run early return and asserts HEAD **moved**. That is the defect the ticket names (accepts the flag, commits anyway), not a refusal-path stand-in. AC6/AC7 are genuinely satisfied by the plan.
- **Snapshot/trap machinery exists as claimed.** `test/scripts/squash-branch.test.sh:17` `SCRIPT="$ROOT/core/scripts/squash-branch.sh"`, `28–29` `PRISTINE_SCRIPT` snapshot from the working file (not git HEAD), `37` `trap restore_script EXIT`, precedent at Scenario 2d (line 326). Task 3.2 correctly reuses it rather than adding a second mechanism.
- **`DRY_RUN=1` exact-match (D1) is the right call.** It matches the cited sibling convention and, more importantly, exact-match is the fail-safe direction here: an unrecognized spelling falls back to the *wet* path, which is the pre-existing behaviour, never to a silent no-op that a caller could mistake for a completed squash. Task 2.5 pins this with a positive assertion (`DRY_RUN=true` must commit).
- **Render-target discipline respected.** Task 1.5 leaves `scripts/concertino/squash-branch.sh` untouched; task 4.3 asserts it is absent from the diff; design §Risks records that this run's own delivery is guarded by the stale rendered copy and must not be read as evidence about `core/`. Consistent with CON-172 and AC9.
- **Guard judgment unweakened.** Task 1.3 forbids any second `DRY_RUN` conditional and any touch of a refusal path; no task alters allowlist, declaration grammar, or refusal conditions. AC8 is structurally protected.

### Verdict: REFUTE

One blocking defect: the design's central argument, and the spec text that encodes it, state as unconditional something the file falsifies. This is not a nit — the spec delta would ship a SHALL that is demonstrably violable, and AC3 as written cannot be satisfied by the designed implementation.

### Change Requests

1. **Correct the "every path" claim in `design.md`.** §Context and D2 must stop asserting that every non-zero exit lies above the mutation point and that "Both exit 0." State the true, narrower fact: every *guard/validation* outcome lies above the single mutation point, so dry/wet exit-code and diagnostic identity is structural **for all validation outcomes**; the only exits below the boundary are the reset-failure (`core/scripts/squash-branch.sh:284–287`) and commit-failure (`289–292`) handlers, which report failures of the git operations themselves and which a dry run by construction cannot predict. The revised text must name those two line ranges explicitly so a later reviewer does not re-derive the false claim.

2. **Qualify the exit-code SHALL in the spec delta** (`openspec/changes/squash-branch-dry-run-mode/specs/delivery-squash-guard/spec.md`, "The guard is consultable without submitting to it"). "SHALL exit with the same status code the identical invocation would have produced with `DRY_RUN` unset" is falsifiable as written. Scope it to the guard's own verdict — same status for every validation outcome — and add an explicit carve-out that a dry run does not predict failure of the reset or commit operations themselves (CON-170's territory). A spec requirement that a reachable input violates is worse than no requirement.

3. **Name the concrete divergent input and decide it deliberately.** The empty-prospective-staged-set case (guard passes, dry exits 0, wet exits 1 because `git commit` has nothing to commit — reproduced above) must appear in `design.md` as an explicit, argued Non-Goal or be handled, not be left implicit. If it stays a Non-Goal, say why (it is a pre-existing wet-path defect owned by CON-170, and a dry run reporting "guard passed" on it is truthful about the guard). Add a matching one-line note to `tasks.md` §4.3's diff review so the implementer does not "fix" it by, e.g., adding `--allow-empty`, which would be an unrequested behaviour change to the wet path.

4. **Reconcile ticket AC3** in the change artifacts. AC3 demands identical exit codes "on both the passing and every refusing path"; per CR1–CR3 that is unachievable in the literal sense. `proposal.md` (which currently repeats the unqualified "identical code ... on every path") must carry the same qualification, so the final gate is not asked to certify against a criterion the design knowingly cannot meet.

### Non-blocking notes

- Task 2.4 (refusal identity: run one refusing fixture with and without the flag, compare) passes vacuously against a script that ignores `DRY_RUN` entirely — an unknown env var changes nothing. That is acceptable because 2.3 is the load-bearing assertion and 3.1 proves *it* failable; just do not cite 2.4 as evidence that dry-run mode exists.
- Task 2.5 (`DRY_RUN=true` must commit) mutates its fixture by committing. Ensure it builds its own fixture rather than reusing the one from 2.1–2.3, or ordering will make the earlier assertions fragile.
- Task 3.1's in-place mutation needs a stable anchor for the deletion; prefer deleting by matching the marker string `READY dry run:` plus its `exit 0`, so the mutation cannot silently no-op (a sed that matches nothing would make the "HEAD moved" assertion pass for the wrong reason — the unmutated script would still be wet-path-only if the flag were absent). Consider asserting the mutation actually changed the file before running it.
- The design's gate-chain analysis (not pre-commit-referenced, so no Gate-Chain Implications Checklist) matches how `check-gate-chain-change.sh` is described, and the instruction to investigate rather than work around a firing check is the right posture.
