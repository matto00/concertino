The new behavior (`setup-worktree.sh` now fails *before* creating a worktree or emitting `run.start` when harness resolves to `unknown`) is a deliberate, designed tightening this ticket's own resolve-speed.sh gate requires, matching the existing "Server start" `BLOCKER` circuit-breaker shape documented in `orchestrator.md`'s circuit-breaker table (`Speed resolution (resolve-speed.sh, via setup-worktree.sh) | 1 attempt | BLOCKER → human`). - Error handling: `resolve-speed.sh` fails loudly (non-zero + message) on unknown speed / harness-with-no-tiers / missing `speeds.json`; `setup-worktree.sh` propagates that as `FAIL` before any worktree is created (verified the `set -e`-safe `|| { ... }` capture pattern is correct — `VAR=$(cmd)` does abort under `-e`, so catching in the same statement is required, and it is). `watch.js`'s `resolveModelsForPlan()` degrades to `null` (never throws) for the same failure classes, appropriately non-fatal for a pre-flight preview.
