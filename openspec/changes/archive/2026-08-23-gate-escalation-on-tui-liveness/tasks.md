      deliberately mutated single line of `tui-attached.sh` (e.g. flip the `kill -0` exit-code

      throwaway dir under the scratchpad temp dir; if a worktree is needed for the probe, create it
      inside `.concertino/worktrees/`, never a scratchpad path (per the CON-127 cleanup lesson).
- [x] 4.2 Red-before-green for "no blocking wait" (the core claim of this ticket): with
      `tui-attached.sh` forced to exit 1 (no lockfile present in the probe's throwaway main
      checkout), demonstrate — by measuring elapsed wall-clock time around the raise procedure's
      no-TUI branch in isolation — that no `--await`/`--wait-only` call is made and no multi-second
      wait occurs, as distinct from merely asserting "the no-TUI code path was chosen." A test that
      only checks which branch executed, without timing evidence that the blocking primitive was
      never invoked, does not satisfy this task.
- [x] 4.3 Prove the TUI-attached branch is unchanged: with a live, real (not simulated) `pid` held
      by a throwaway background process backing `watch.lock`, exercise `--await`'s exit-0 path (a
      probe writes a matching `answer.json`) and its non-zero/timeout path (probe times out,
      confirm `escalation.timeout` recorded), matching pre-change behavior byte-for-byte on the
      event shapes involved.
- [x] 4.4 Demonstrate "a timeout is never an approval" on both branches with real evidence: on the
      TUI-attached branch, a timed-out `--await` call followed by no orchestrator action until a
      real chat-recorded answer exists; on the no-TUI branch, confirm by inspection/probe that no
      code path in the new branch can reach a resolved state without an explicit `concertino answer`
      call having succeeded.
- [x] 4.5 Confirm `concertino answer`'s refusal-on-already-answered behavior is exercised unchanged
      by a probe that answers twice in the no-TUI branch and observes the second call's refusal —
      proving first-write-wins is preserved by construction, not merely asserted.
- [x] 4.6 One item on this list is not mechanically testable and is stated here rather than given a
      vacuous check: whether the orchestrator LLM, mid-run, actually reads `TUI_ATTACHED` correctly
      and picks the right branch (as opposed to hallucinating a call it wasn't instructed to make)
      is runtime LLM behavior, verified only by this delivery's own live evaluator/skeptic gates and
      real-world observation over subsequent runs, not by a deterministic test.
- [x] 4.7 Evidence-shaped-non-evidence check: every assertion above must bind to the real artifact
