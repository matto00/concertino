## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)

- Read all planning artifacts: `ticket.md`, `proposal.md`, `design.md` (178 lines), `tasks.md` (86 lines), `specs/tui-liveness-detection/spec.md`, `specs/escalation-bubble-up/spec.md`.
- `lib/ui/watch-lock.js` — read in full. Confirms the design's premise: `.concertino/cache/watch.lock` = `{pid, startedAt, heartbeatAt}`, ownership by `pidAlive()` (`process.kill(pid,0)`, EPERM => alive), heartbeat diagnostic-only, torn/absent => no lock, dead holder's lock overwritten on `acquire`. Path confirmed via `lib/ui/cache.js:45` `cacheDir(root) = <root>/.concertino/cache`.
- `lib/ui/watch.js:197-208` — `acquire()` is called on every `concertino watch` start; `lib/cli/watch.js:43` passes `root: resolveOut(args)` (the `--out` dir / cwd), NOT a `git rev-parse --git-common-dir` resolution.
- `scripts/concertino/emit-event.sh` — read the escalation paths: `main_checkout()` (l.91-96), `ANSWER_FILE=${RUN_DIR}/answer.json` (l.298-304), `discard_stale_answer()` (l.484-491) and its call site immediately after `write_escalation_raised` (l.659-662), `--raise-only` exit (l.665), `--await` deadline/trap (l.700-739), `--wait-only` (l.600-647).

- `lib/cli/sync.js` / `diff.js:85-86` / `doctor.js:43-44` / `resolve-core.js:46-57` — `scripts/concertino/**` is rendered verbatim from `core/scripts/**` (recursive listing).
- Ran `bash -c 'kill -0 1; echo $?'` as uid 1000 → prints `kill: (1) - Operation not permitted`, **exit 1**.

### Verdict: REFUTE

The core idea (reuse `watch-lock.js`'s PID-liveness pidfile; gate at CON-127's single call site) is sound and well-argued. But the design rests on four ground-truth claims that are false, and one composition hole that can hang a run — the exact failure mode this ticket exists to remove.

### Change Requests

1. **Wrong authoring location — the script would never reach any consumer repo.** `proposal.md` "Impact", `design.md` Decision 1, and `tasks.md` 1.1/1.3 all name `scripts/concertino/tui-attached.sh` as the file to create. That directory is *generated*: `lib/cli/sync.js` (via `listFilesRecursive(core/scripts)`, see `lib/cli/diff.js:85-86` and `lib/cli/doctor.js:43-44`) renders `core/scripts/**` verbatim into `<out>/scripts/concertino/**`; `core/scripts/emit-event.sh` is the source of truth for the script the design compares against. A `tui-attached.sh` authored only under `scripts/concertino/` is an unrendered orphan: every downstream repo running `concertino sync` gets an `orchestrator.md` that invokes a script it does not have. (Failure is in the safe direction — non-zero exit reads as "no TUI" — so this would ship silently broken, with the feature permanently dead everywhere except this repo.) Fix: author at `core/scripts/tui-attached.sh`, add the `concertino sync` re-render of `scripts/concertino/tui-attached.sh` as an explicit task alongside 3.1, and correct the Impact list.

2. **Second no-TUI escalation in the same run is unresolvable — nothing performs `discard_stale_answer`.** `answer.json` is per-**ticket-run**, not per-escalation (`emit-event.sh:298-304`), and `store.writeAnswer` opens it `wx` (`lib/ui/store.js:216`). Today the raise path is what clears a prior escalation's leftover answer: `discard_stale_answer` runs exactly once per raise, immediately after `write_escalation_raised` (`emit-event.sh:659-662`), and its own comment states the reason ("stale leftover state from an earlier escalation"). Decision 2's no-TUI branch makes **no `emit-event.sh escalation` call at all**, so nothing discards. Escalation #2 in a no-TUI run therefore hits `concertino answer` → `EEXIST` → `already answered`, exit 2. Multiple escalations per run are the norm, not an edge case (Planning ESCALATION, final-gate, and the step-4 one-shot follow-up at `orchestrator.md:1030-1051`). Worse, the documented handling of that refusal (`orchestrator.md:1309-1313`) is "the dashboard won the race … continue your normal `--wait-only` loop from step 2" — a loop the no-TUI branch by construction never entered. Design.md Decision 3's assertion that this branch "never races a second writer in practice (no dashboard is attached to write one)" is refuted by the previous escalation's own file. The design must specify who clears `answer.json` on a no-TUI raise (and record the equivalent of `escalation.answer_discarded`), and what the refusal branch means when there is no polling loop to fall back to.

3. **False claim that the branch being replaced already writes through `concertino answer`.** Decision 2 says recording via `concertino answer` is "exactly the same call the TUI-attached timeout-fallback path already uses today … not a new write path"; `specs/escalation-bubble-up/spec.md`'s third requirement repeats it ("identical to the write path used in the TUI-attached branch's chat-fallback case"). Ground truth: there are **two** different fallbacks. The root's bubbled-resolution procedure does use `concertino answer` (`orchestrator.md:1298-1304`), but the directly-raised `--await` timeout fallback — the one Decision 2 is actually replacing — records with `scripts/concertino/emit-event.sh escalation.answered ticket=… role=orchestrator answer=…` (`orchestrator.md:1215-1225`). So this *is* a write-path change for that branch, not a promotion of an existing call, and the design must say so and justify it (note `concertino answer` also creates `answer.json` and hardcodes `role=orchestrator` in `recordAnswered`, `lib/cli/answer.js:57-61` — interacting directly with item 2). Correct both the design and the spec text; a claim of "unchanged write path" that is false is the kind of confidently-wrong documentation that gets copied into the implementation.

4. **False claim about `kill -0` and EPERM.** Decision 1 step 3 states "bash's `kill -0` itself already folds 'exists but owned by another user' into a zero exit, matching `pidAlive`'s own EPERM handling", and task 1.2/5.1 direct the implementer to write that rationale into the script header. Measured: as uid 1000, `bash -c 'kill -0 1'` exits **1** and writes `kill: (1) - Operation not permitted` to stderr. It does not match `pidAlive` (`watch-lock.js:46-52`, which returns `true` on EPERM). The divergence lands in the safe direction (false "no TUI"), so this need not change the mechanism — but the stated equivalence, and the "the two implementations can never disagree" argument built on it, must be corrected rather than shipped into a header comment. Also specify stderr suppression so a foreign-owned pid does not spray `kill:` errors into agent transcripts.

5. **Decisions 2 and 3 compose into an indefinite poll on an escalation that was never raised.** Decision 3 / the spec's "Liveness is re-checked fresh" scenario mandate a fresh check at resolution time. If a dashboard attaches between a no-TUI raise (no `escalation.raised` ever written) and resolution, the root takes the `TUI_ATTACHED=1` path and enters the `--wait-only` loop. Ground truth (`emit-event.sh:616-647`): with no `escalation.raised` for the ticket, `RAISED_AT` is empty, `REAL_DEADLINE_MS` is deliberately left unset ("a caller error, not a case this call can usefully treat as timed out"), and every call exits 2 — the loop can never terminate on a deadline. The dashboard also shows nothing, since `lib/ui/reducer.js:243` only populates `run.escalation` from `escalation.raised`. Net: a hang against a screen that has no question on it. The design needs an explicit rule for this transition (e.g. the resolution-time re-check only upgrades to the polling loop if this escalation was actually raised, or a late raise is emitted at that point).

### Non-blocking notes

- Root-resolution mismatch: `tui-attached.sh` is specified to resolve the lockfile via `git rev-parse --git-common-dir` (main checkout), while `concertino watch` writes it under `resolveOut(args)` (`lib/cli/watch.js:43`), i.e. cwd/`--out`. Identical for the normal `concertino watch` at the repo root; divergent for `--out=DIR`. Worth one sentence in the design acknowledging the assumption. (`concertino answer`'s `--out` default of `.` has the same pre-existing property — a no-TUI orchestrator invoking it from a worktree would write `answer.json` under the worktree, not the main checkout where `emit-event.sh` keeps `runs/`; pre-existing, but the no-TUI branch makes it the ordinary road.)
- The rejection rationales for the heartbeat-file and env-var alternatives (Decision 1) are well grounded and check out against `watch-lock.js`'s own design note; keep them.
- Tasks 4.1-4.7 are unusually strong (red-before-green with real mutation, timing evidence rather than branch-taken assertions, an explicit non-testable item). No changes requested there beyond covering items 2 and 5.
