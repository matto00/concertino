## Skeptic Report — design gate (round 2, skeptic-design-2.md)

### What I verified (with evidence)

- **Round 1's bare-`--help`/`-h` fix genuinely resolves the contradiction, verified empirically against ground truth, not just by reading prose.**
  Read the revised proposal.md (line 11 new bullet), design.md (new Decision 5), specs/cli-subcommand-help/spec.md (new "Bare invocation `--help`/`-h`..." requirement + 3 scenarios), and tasks.md (new §5, plus 6.4–6.6 and 7.3). Then traced the actual mechanism against the real `bin/concertino` and `lib/cli/shared.js#parseArgs` by running it in `node` (not by reasoning alone):

  ```
  argv=[]              -> args={_:[]}, cmd='watch'; bare-check fires:false -> dispatches cmdWatch; its hasHelpFlag=false -> dashboard (unaffected, matches spec's "Bare invocation without help flags is unaffected")
  argv=['--help']       -> args={_:[],help:true}, cmd='watch'; bare-check fires:true -> help(); exit (matches "Bare long flag shows aggregate help")
  argv=['-h']            -> args={_:['-h']}, cmd='-h'; bare-check fires:false (args._[0]='-h' is truthy, so !args._[0] is false) -> falls to dispatch, cmd='-h' matches no branch -> else help() (matches "Bare short flag shows aggregate help" — same aggregate output -h always produced, confirmed against round-1's own evidence that this fallthrough already existed pre-change)
  argv=['watch','--help'] -> args={_:['watch'],help:true}, cmd='watch'; bare-check fires:false (args._[0]='watch' truthy) -> dispatches cmdWatch; its own hasHelpFlag=true -> prints watch usage, exits (matches "Explicit watch subcommand still gets its own usage")
  argv=['watch']          -> dispatches cmdWatch; hasHelpFlag=false -> dashboard normally
  ```
  All five traces match the five scenarios design.md/spec.md now claim, exactly. The key subtlety I specifically checked (since it's the one place this could have silently broken) is that `!args._[0] && hasHelpFlag(args)` correctly does *not* fire for bare `-h`, because `parseArgs(['-h'])` puts `-h` into `args._[0]` (a truthy string, not empty) — so the new check doesn't need to (and doesn't) handle `-h`'s case; the pre-existing `else help()` fallthrough (verified in round 1 to already exist) does. Design.md's own alternative-considered writeup (Decision 5) states this correctly. Round 1's contradiction is resolved, not just asserted-away.

- **The engineering plan otherwise remains sound** — re-checked round 1's other verified claims (14 `cmd*` functions, `parseArgs` not handling `-h`, `cmdAnswer`'s divergent raw-argv parsing, `help.js` as one monolithic string) against the current files; nothing has regressed and the artifacts still describe them accurately.

- **Found a new, real gap: the `cli-default-command` "Modified Capability" declared in proposal.md has no corresponding spec delta, and the mechanism openspec uses to merge deltas on archive is filename-based, not prose-based — so this isn't cosmetic.**
  proposal.md's "Capabilities" section lists `cli-default-command` under **Modified Capabilities** (proposal.md:20-22), describing exactly the new bare `--help`/`-h` carve-out behavior. But `openspec/changes/per-subcommand-help-flags/specs/` contains **only** `cli-subcommand-help/spec.md` — there is no `specs/cli-default-command/` directory at all (`find .../specs -type f` returns exactly one file). The three new bare-invocation scenarios were instead appended to `cli-subcommand-help/spec.md`, which is entirely under a single `## ADDED Requirements` header (`grep -n "^## " specs/cli-subcommand-help/spec.md` → only line 1) — i.e. they are declared as new requirements of the brand-new `cli-subcommand-help` capability, not as a modification of the existing `cli-default-command` capability whose actual behavior they change.
  I confirmed this is not a stylistic nit but a real mechanical problem: I read `/usr/lib/node_modules/@fission-ai/openspec/dist/core/archive.js` (the installed `openspec` binary this repo uses — `openspec validate` and `openspec archive --help` both ran successfully against this worktree). Line 194 shows `archive.js` derives the target capability purely from `path.basename(path.dirname(update.target))` — i.e. from the spec delta's **folder name** inside the change's `specs/` directory, with no reference to proposal.md's prose "Capabilities" section at all. I also confirmed the established repo convention for a real Modified Capability: `openspec/changes/archive/2026-07-28-emit-gate-result-on-fail/` declares Modified Capabilities: `gate-telemetry` and ships a matching `specs/gate-telemetry/spec.md` delta (with a `## MODIFIED Requirements` header) that `openspec archive` merges into the canonical `openspec/specs/gate-telemetry/spec.md`. This change does not follow that pattern for `cli-default-command`.
  Consequence if unfixed: when this change is archived, the canonical `openspec/specs/cli-default-command/spec.md` (which I read — its existing "Bare `concertino` launches the fleet dashboard" requirement's "`help` and `--version` remain explicit" scenario says nothing about `--help`/`-h`) will be left completely untouched, permanently under-documenting the new bare-`--help`/`-h` carve-out this change actually ships. Instead, that behavior will live stranded inside the new `cli-subcommand-help` capability, which is about per-subcommand help, not the default-command dispatch rule. This is exactly the "missing contract update" failure mode the design gate is meant to catch, and `openspec validate --strict` passing does not catch it (validate only checks each delta file is internally well-formed, not that it's filed under the right capability name).

### Verdict: REFUTE
