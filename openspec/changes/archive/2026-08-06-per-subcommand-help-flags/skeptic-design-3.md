- **Found a new, real defect in how the `cli-default-command` delta is formed: it declares an entire second, untouched requirement as "MODIFIED."** `specs/cli-default-command/spec.md`'s single `## MODIFIED Requirements` section contains *two* `### Requirement:` blocks: "Bare `concertino` launches the fleet dashboard" (genuinely changed) and "Every registered subcommand is discoverable" (about completion/README/help-text coverage — nothing to do with this ticket). I diffed that second block against the canonical `openspec/specs/cli-default-command/spec.md`'s copy: `diff` reports **zero differences** — it is a verbatim, unmodified copy. My `sim.mjs` run confirms the mechanical consequence: `buildUpdatedSpec` reports `counts: { added: 0, modified: 2, removed: 0, renamed: 0 }` for this file — i.e. `openspec archive` will print `~ 2 modified` for `cli-default-command` and permanently record in the change's archive history that this ticket modified the "discoverability" requirement, when it did not touch it at all.
  I checked this against the repo's own established convention rather than asserting it from principle: I scanned every archived change under `openspec/changes/archive/*/specs/*/spec.md` that has a `## MODIFIED Requirements` section (26 files) and compared, for each, the count of `### Requirement:` blocks inside that section against the total requirement count in the corresponding canonical spec. **Every single one** modifies strictly fewer requirements than the canonical spec contains — e.g. `2026-08-01-configurable-base-remote-doctor/specs/main-fast-forward/spec.md` modifies exactly 1 of 5 requirements in `main-fast-forward`; `2026-08-06-agent-merge-permission-preflight/specs/agent-merge/spec.md` modifies 1 of 11 in `agent-merge`. None of the 26 ever reproduces an entire canonical spec's requirement set inside `## MODIFIED Requirements`. This change's `cli-default-command` delta is the only one that would dump 100% of a canonical spec's requirements into `MODIFIED` (2 of 2), and the second of those two is provably untouched. This is not build-breaking (the merge still succeeds and produces correct final content for the requirement that *is* actually changing), but it is a real defect in how the delta is authored: it misattributes a change to a requirement this ticket never touches, contrary to `openspec`'s own semantics (MODIFIED = "this requirement's behavior changed") and contrary to every precedent in this repo.
