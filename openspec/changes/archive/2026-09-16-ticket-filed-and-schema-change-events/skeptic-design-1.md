**Decision 1 (self-reference, item 1 of your list).** Read Decision 2 closely. The distinction claimed — a manual emission for a *source-side* schema change vs. the automated digest path for *rendered-copy drift* — is real, not rationalization: the digest mechanism (Decision 3/4) is explicitly keyed on rendered-copy content diverging from a sync-time baseline, and this delivery changes `core/` source, which by construction changes the baseline itself rather than diverging from it. A digest comparison structurally cannot flag "the framework changed its own script," only "a repo's copy stopped matching the framework." So no digest-based mechanism could have caught this case even if it existed. The reasoning is sound. It is fair to independently call this "ceremony" in style (a hand-run task, not a mechanically enforced consequence of touching `emit-event.sh`), but it is not a self-exemption or a paper-over — it is the only channel that *could* have carried this information, and the design says so plainly rather than hiding a manual step behind automation language. Non-blocking: the design does not commit to a policy for *future* source-side changes to event emission (will every future PR to `core/scripts/emit-event.sh` require the same manual step, and who enforces that it isn't skipped?). That's a real durability gap but out of this ticket's stated scope (it only had to resolve the self-reference for *this* delivery, which `ticket.md`'s binding note requires, and it did).

**Decision 5/6 (role allowlist, item 2 of your list) — independently re-audited, not trusted.**

Confirmed: `script` is the emitter's own default (`emit-event.sh:228`) and is used literally by `assert-phase.sh`, `start-servers.sh`, `setup-worktree.sh`, `cleanup.sh` (including the `run.end` that makes a run terminal, `cleanup.sh:789`). Confirmed `orchestrator`/`executor`/`evaluator`/`skeptic`/`auditor` are all literal in `core/roles/*.md`.

Grepped for any other `role=$...` / `CONCERTINO_ROLE=$...` interpolation anywhere in `core/`, `lib/`, `bin/` — one hit, an unrelated local shell variable in `check-merge-readiness.sh` with no connection to `emit-event.sh`. The audit's "only dynamic producer" claim holds.
- **One inaccuracy found, not fatal.** The design's stated reason for including `dashboard` in the closed set is "the corpora contain `dashboard` emissions [through emit-event.sh]." I traced this and found `lib/ui/session.js`'s `writeSpawnEvent`/`writeOverrideEvent` — the actual source of `role: 'dashboard'` events (`run.spawn`, `run.override`) — write directly to `events.jsonl` via `fs.appendFileSync`, **bypassing `emit-event.sh` entirely** (the file's own header comment says so: "without going through emit-event.sh"). So `emit-event.sh`'s role validation will never actually see `role=dashboard` as an argument in practice; admitting it to the allowlist is inert, not load-bearing. This does not make the design wrong — including a value that's never exercised through this path is harmless, and arguably forward-compatible if the dashboard's writer is ever routed through the validated emitter — but the stated rationale ("the corpora contain `dashboard` emissions") implies a mechanism that isn't actually there. **Non-blocking note, not a required revision**: the design should say "the closed set includes `dashboard` because historical/dashboard-authored events carry it, even though those are written in-process rather than through this emitter" rather than implying `emit-event.sh` itself has been observed accepting it.

**Decision 3/4 (digest mechanism vs. AC1) — traced against the spec, not just the design.** `instrumentation-provenance/spec.md`'s scenarios map directly onto AC1's literal wording ("detectable from that repository's own event log alone... with no reference to the framework repository's history required"). The mechanism is structurally correct for the CON-128 scenario: sync writes a render-time baseline into the *consuming* repo; a post-sync local patch to a rendered script makes the next run's live digest disagree with that locally-stored baseline; `schema.change` fires naming the affected scripts, entirely from local state. "No baseline is not drift" is the right call — the alternative (treating absence as drift) would false-positive on every unsynced repo including helio, which is explicitly out of scope for this batch by owner ruling. This does leave helio "blind" until it syncs, but that blindness is a pre-existing, owner-ruled condition of this batch, not something this design could fix without violating the "do not sync helio" constraint — correctly scoped as a Non-Goal-adjacent consequence, not silently dropped. One aggregate digest for the `run.start`/AC2 comparison plus affected-script names carried separately on `schema.change` is sufficient: AC2 only needs a yes/no "same instrumentation," and per-script identification is explicitly deferred to the `schema.change` event, which requires the sync-time manifest to retain per-file digests internally (implied by tasks 3.3/3.4's "confirming the event appears with that script named" — the aggregate alone couldn't name a script, so a per-file manifest is a necessary, if not fully spelled-out, implementation detail). This is a reasonable level of specificity for a design doc; tasks.md's verification steps will force it out during implementation.

The deviation is real, flagged explicitly rather than silently substituted, content-preserving, and consistent with the one existing precedent rather than inventing a second embedding convention. This is a sound engineering call for a `k=v` emitter interface, not a corner cut — no revision needed.
