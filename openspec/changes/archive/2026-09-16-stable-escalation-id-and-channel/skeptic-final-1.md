### A race the design's own stated invariant doesn't fully close (non-blocking, but worth recording)

`design.md` Decision 5 and `metrics.js`'s own comment assert "a timeout can never occur after an answer already resolved the escalation" — true within a single `--await` process (the poll loop exits on `try_resolve()` success before ever reaching the timeout write), but `core/roles/orchestrator.md`'s own documented root procedure (step 2/3, lines ~1778-1822) explicitly allows a chat answer to land via `concertino answer --channel=chat` *while a `--wait-only` polling loop is still concurrently in flight*, stopping the loop only after observing the resolution. If a `--wait-only` call's own real-deadline check fires in the narrow window between the chat answer being typed and the orchestrator's next scheduled `--wait-only` call observing it, the reverse order (`escalation.answered` then `escalation.timeout`, same id) is possible, and `buildEscalationHistory`'s "last event wins" walk would then overwrite the answer with `timedOut: true, decision: null` — the exact data loss this ticket exists to prevent, in the one narrow ordering the code doesn't defend against. This is a genuinely narrow race (the escalation's real ~60-minute deadline must land inside a human's chat-reply latency), it is not what CON-188 was scoped to eliminate, and I do not believe it should block delivery — but it is a real, reproducible-in-principle edge case that neither the design doc nor the test suite discloses or covers, and should be flagged for a future ticket if the corpus ever shows a `timedOut:true` entry with a later `resolvedAt`.

### Non-blocking notes

- The race described above (chat answer + concurrent `--wait-only` real-deadline overtaking it) is real but narrow and out of CON-188's stated scope; flag for a follow-up if the corpus ever surfaces it.
- `random_hex()` uses 3 bytes (24 bits) of entropy per millisecond bucket; collision probability under concurrent same-millisecond raises for the same ticket is low but non-zero and unlocked. Acceptable given the design's own stated reasoning (no call-stack to thread a lock through, and a collision only degrades to the id-less fallback's pre-existing positional-pairing behavior, not data loss) — not a blocker.
