## Context

`lib/ui/frame.js` is a pure, stateless differential-diff renderer with named terminal-control constants (`ALT_SCREEN_ENTER`/`ALT_SCREEN_EXIT`, `CURSOR_HIDE`/`CURSOR_SHOW`) that are textually paired on entry/exit — a guarantee CON-17/CON-27 established and later work (`computeLiveEscalations`, `splitKeys`) has kept intact. `lib/ui/watch.js` owns the actual terminal lifecycle: `stdin.setRawMode(true)` on entry (line ~908), and `setRawMode(false)` at exactly three existing exit sites — `quit()` (line ~925), and the two suspend-for-attach functions, `doAttach`/`doAttachTarget` (lines ~975, ~1015) — plus a `stdin.on('data', ...)` handler (line ~1085) that runs `splitKeys(chunk)` and feeds each resulting key through `router.handleKey(key, state)`.

**Ground truth correction:** there is currently no `process.on('uncaughtException', ...)` handler anywhere in this codebase (`grep -rn "uncaughtException" lib/ bin/` returns nothing), and `watch.js`'s own comment at lines 288-291 documents this as a known, unaddressed gap: an uncaught throw from `onKey`/`applyAction` (which have no try/catch of their own) already skips `quit()`'s terminal restore today, leaving the user's terminal in raw mode and the alternate screen buffer. An earlier draft of this design incorrectly assumed a third, pre-existing `setRawMode(false)` exit site for "the uncaught-exception handler" — there is no such site to mirror. See Decision 5 for how this change actually satisfies the ticket's crash acceptance criterion.

The screen-router contract (`lib/ui/router.js`) is `render(state, opts) -> string` / `handleKey(key, state) -> action | null`, dispatched by `state.mode`. Screens never mutate state directly — `handleKey` returns an action object, and `lib/ui/controllers/<screen>.js`'s `handle(action, ctx) -> boolean` is what actually mutates `ctx.S`. The fleet screen already has exactly the action shape this change needs: `lib/ui/controllers/fleet.js`'s `case 'jump'` (CON-39, added for the digit-jump feature) sets `S.selected` to an absolute index (clamped to `runs.length - 1`), resets `S.focus`/`S.queueFocus`, and calls the existing `scrollToShow` — i.e. "select run row N" is already a first-class, reusable action independent of how N was derived (digit key vs. a click).

No screen today records its own rendered layout — `renderRun`/`renderFinishedRow`/`renderQueuedRow` (`lib/ui/screens/fleet/rows.js`) return strings only.

## Goals / Non-Goals

**Goals:**
- Enable/disable SGR mouse reporting cleanly, paired on every entry/exit path exactly like the alt-screen buffer already is.
- Parse SGR mouse click sequences off stdin without disturbing existing keypress parsing (`splitKeys`).
- Let a left-click on a rendered run row in the fleet view select that row, via the existing `jump` action — no second action path.
- Record just enough render-pass layout (fleet run rows only) to map a clicked terminal row back to a `runs[]` index.
- Document the behavior, its scope, and the tmux caveat in `docs/dashboard.md`.

**Non-Goals (explicitly deferred, per the escalated scope decision):**
- Any other screen (drilldown, launchpad, settings, sessions, escalation, ticketdraft, docview, launchplan, ticketview) getting click support in this pass.
- Text-entry fields: no click-to-focus and no click-to-position-cursor anywhere in this pass. (Decided: if/when a later pass adds text-entry click support, a click focuses the field only — it does not reposition the text cursor. Recorded for that future work, not implemented here.)
- tmux mouse-mode pass-through verification (`tmux attach` sessions). This pass enables mouse reporting unconditionally; whether tmux's own mouse mode ever swallows or double-delivers those SGR sequences is explicitly left to a follow-up ticket. `docs/dashboard.md` must say so explicitly so this isn't silently assumed to work.
- Right-click, scroll-wheel, drag, or any button/motion event other than a plain left-button press.
- A generic, fleet-wide hit-test layer or a retained layout tree shared across screens. This pass's row-bounding-box tracking lives entirely inside the fleet screen's own render module.

## Decisions

**1. Mouse-mode lifecycle lives in `lib/ui/frame.js` as named constants, enabled/disabled from `lib/ui/watch.js`, mirroring `ALT_SCREEN_ENTER`/`ALT_SCREEN_EXIT`.**
Add `MOUSE_REPORT_ENTER = '\x1b[?1000h\x1b[?1006h'` and `MOUSE_REPORT_EXIT = '\x1b[?1000l\x1b[?1006l'` to `lib/ui/frame.js`, exported alongside the existing cursor/alt-screen constants. `watch.js` writes `MOUSE_REPORT_ENTER` at the same point it calls `stdin.setRawMode(true)` on startup, and `MOUSE_REPORT_EXIT` at each of the three existing `setRawMode(false)` sites — `quit()`, and both directions of the two suspend-for-attach functions (exit mouse mode before handing the terminal to tmux, re-enter it on restore, matching how alt-screen suspend/restore already works). This keeps the "textually paired, one enable, matching disable on every exit" property the existing constants already have to grep-verify, rather than inventing a separate lifecycle convention. The fourth exit path — an uncaught exception — has no existing site to mirror; see Decision 5.
Alternative considered: gate mouse-mode on a config flag. Rejected for this pass — the proposal's scope is a single screen behind no separate toggle; a settings-screen opt-out could be a follow-up if real terminals turn out to need it.

**2. Mouse sequences are parsed as a new key-like token, not folded into `splitKeys`.**
`splitKeys` already special-cases CSI sequences ending in `@`–`~` as a single "key". An SGR mouse sequence (`\x1b[<Cb;Cx;CyM`/`m`) fits that same shape (`\x1b[<...M`) and will already come through `splitKeys` as one token (it ends in `M`/`m`, both in the `@`–`~` range). So no change to `splitKeys` itself is needed — add a new pure recognizer, `parseMouseClick(key) -> {row, col} | null`, in `frame.js` next to `splitKeys`, matching `^\x1b\[<0;(\d+);(\d+)M$` (button code `0` = left-button press; SGR `M` = press, `m` = release — only `M`, i.e. press, is handled this pass). `watch.js`'s stdin handler tries `parseMouseClick` first for each split key; on a match it resolves the target screen's row->index mapping and dispatches, else falls through to the existing `router.handleKey` keypress path unchanged.
Alternative considered: a stateful mouse-mode parser tracking partial sequences across chunk boundaries. Rejected — `splitKeys`'s existing CSI-run scanning already handles a sequence arriving as one `data` chunk (the common case for a single click) the same way it already handles arrow keys; a click sequence split across two `data` chunks is a pre-existing class of raw-stdin edge case (arrow keys have the same theoretical exposure today) and not something this pass needs to newly solve.

**3. Row bounding boxes are tracked only inside the fleet screen's own render module, keyed by terminal row -> `runs[]` index.**
`lib/ui/screens/fleet/render.js`'s `renderFleet(runs, opts)` already iterates `runs` to build each row's string via `rows.js`'s `renderRun`/`renderFinishedRow`. Extend that loop to also build a plain `{ [terminalRow]: runsIndex }` map as a side output (e.g. `renderFleet` returns `{ text, rowIndex }` instead of a bare string, or the map is computed by a small new pure function `computeRowIndex(runs, opts)` called alongside `renderFleet` with the same layout inputs — implementation detail for the executor to settle against the existing `visibleWindow`/`scrollOffset` math, since that's what already determines which `runs[]` slice is on-screen and at which row). `watch.js` stores this map on the current render pass (alongside `prevLines` in the existing frame-diff state) and looks it up when a click's `row` falls inside the fleet screen's row-list band.
Alternative considered: a shared, screen-agnostic hit-test registry (e.g. a generic `bounds.js` module every screen contributes to). Rejected for this pass per the proposal's explicit scope decision — building that generic layer before validating the single-screen pattern is exactly the premature-architecture risk the escalation flagged.
Implementation note for whoever builds this: the terminal-row offset is not just `visibleWindow`/`scrollOffset` math — each section's `contentLines` also passes through `layout.box()` (border/title padding overhead) before reaching final terminal rows, so the row-index map must be built post-box, from the same coordinates the frame diff actually writes to, not from the raw pre-box `contentLines` index.

**4. A click resolves to the existing `jump` action, not a new action type.**
Given a clicked terminal row, `watch.js` looks it up in the fleet row-index map; if it resolves to a valid `runs[]` index, dispatch `{ type: 'jump', index }` — the identical action CON-39's digit-jump already produces and `lib/ui/controllers/fleet.js`'s `case 'jump'` already handles (sets `S.selected`, resets focus/queueFocus, scrolls into view). Selecting-only (not opening drilldown) satisfies the acceptance criterion ("clicking to select/focus") without inventing new state.
Alternative considered: dispatch `open-drilldown` directly on click (single click both selects and opens). Rejected — the ticket's acceptance criteria ask only for select/focus, and conflating click-to-select with click-to-open would make a single click behave differently from the equivalent two-step keyboard path (`j`/`k` then `l`/Enter), which is exactly the "second, parallel action path" the ticket explicitly warns against.
A click outside the row-list band (header, banner, QUEUED/QUICK START sections, metrics) or that doesn't resolve to a mapped row is a no-op this pass — it is silently ignored, not an error.

**5. Add a genuine top-level `process.on('uncaughtException', ...)` handler that restores full terminal state (not mouse mode alone), to actually satisfy the ticket's crash acceptance criterion.**
The ticket's AC — "no leaked terminal mouse-reporting state after `q` or a crash" — cannot be met by "mirror the existing exit sites" (Decision 1), because no crash-handling site exists today (see Context's ground-truth correction): an uncaught throw currently leaves the terminal in raw mode AND the alternate screen buffer, silently, with no test or code path guarding against it. This change adds one `process.on('uncaughtException', handler)` registration (installed once, alongside the `stdin.setRawMode(true)` startup site) whose handler runs the same terminal-restore sequence `quit()` already runs — `setRawMode(false)`, `ALT_SCREEN_EXIT + MOUSE_REPORT_EXIT + CURSOR_SHOW` — then re-throws (or writes the error to stderr and calls `process.exit(1)`, matching whatever this codebase's existing non-TUI error-exit convention is) so the crash itself is never swallowed or hidden from the user.
This deliberately restores the *entire* terminal, not just mouse-reporting: writing a handler that fixes only the new mouse-mode leak while knowingly leaving the pre-existing raw-mode/alt-screen leak in place on the very same crash path would be an incoherent partial fix, not a narrower one — the handler has to touch the terminal exactly once regardless of how many escape sequences it emits in that one write. This does incidentally close a pre-existing (documented, unticketed) bug as a side effect of correctly satisfying this ticket's own AC; it is not itself new scope this change is going out of its way to fix.
Alternative considered: narrow the ticket's crash AC to mean "the same crash-handling coverage that already exists" (i.e. none) and document mouse-mode as best-effort on crash. Rejected — the AC's wording ("no leaked terminal mouse-reporting state ... after ... a crash") is unambiguous and was not itself part of the escalated scope questions; narrowing it would mean shipping a documented AC violation rather than the small, well-contained fix above.
Alternative considered: only catch exceptions inside `onKey`/`applyAction` (a local try/catch at the stdin `data` handler) rather than a process-level `uncaughtException` handler. Rejected as insufficient — it would not cover a throw from the polling `setInterval` callback (`draw()`) or any other async path outside the stdin handler, whereas a process-level handler covers every source uniformly, matching the AC's unqualified "a crash."

**Listener lifecycle: the new `uncaughtException` handler MUST be explicitly removed in `quit()`, unlike the pre-existing `process.stdout.on('resize', ...)` listener (line ~890), which is never removed and is a known, already-accepted leak `test/watch.test.js` works around externally (park/restore around each of its ~62 sequential `watch()` calls, e.g. lines 1657-1658, 1684-1685, 3723-3724, 3827-3828).** A stale `resize` listener merely triggers a redundant/no-op redraw against a torn-down `S`; a stale `uncaughtException` listener is materially more dangerous left unmanaged — a second `watch()` call in the same process (the exact pattern the test suite already exercises) would accumulate one handler per call, and an unrelated later error could trigger an *earlier* call's handler, writing raw escape sequences to stdout and calling `process.exit(1)` well outside that handler's own intended lifetime. In production this specific accumulation never occurs (`lib/cli/watch.js` calls `watch()` exactly once per process), but the test suite's existing sequential-call pattern makes it a real, reachable hazard, not merely theoretical — confirmed live: `node --test test/watch.test.js` already emits `MaxListenersExceededWarning` for the unmanaged `resize` listener, and the same accumulation would apply here without cleanup. Hold a reference to the handler function and call `process.removeListener('uncaughtException', handler)` inside `quit()`, guarded by the same `quitting` re-entrancy flag `quit()` already uses, so removal happens exactly once per `watch()` call and a caller invoking `watch()` again afterward starts with a clean slate. This is a narrower, explicit fix scoped to the one new listener this change adds — it does not attempt to also retrofit removal onto the pre-existing `resize` listener, which remains this codebase's existing accepted trade-off, unchanged by this ticket.
Alternative considered: also fix the pre-existing `resize` listener leak while touching this code. Rejected as out of scope — it's a separate, already-documented trade-off with its own existing test-level workaround, not something this ticket's AC requires touching.

## Risks / Trade-offs

- [Terminals/multiplexers that don't support SGR mouse mode (`?1006`) send legacy X10 coordinates instead, which `parseMouseClick`'s regex won't match] → clicks are silently ignored on those terminals this pass; no crash, no garbled input, since unmatched sequences fall through to the ordinary keypress path (harmless there too, as they won't match any bound key). Documented as a known limitation in `docs/dashboard.md` rather than solved now.
- [tmux mouse-mode conflicts, deferred per the scope decision] → a `tmux attach` session may see swallowed or duplicated click events; explicitly called out in `docs/dashboard.md` as unverified, with a follow-up ticket to be filed for full cross-terminal verification.
- [Leaked mouse-reporting (and pre-existing raw-mode/alt-screen) state on an uncaught exception] → mitigated by Decision 5's new `process.on('uncaughtException', ...)` handler, which did not exist before this change; verified by task 1.5's test.
- [A double-restore write if `uncaughtException` fires after `quit()` has already run] → the handler mirrors `quit()`'s own re-entrancy guard (the per-`watch()`-call `quitting` closure flag checked before writing), so a throw during shutdown itself cannot double-write the restore sequence.

## Migration Plan

No data migration. Purely additive: new escape-sequence constants, a new pure parser, a new per-frame layout side-channel scoped to one screen, and reuse of an existing action type. No existing behavior changes for keyboard-only usage — a terminal that never sends a mouse sequence behaves identically to today.

## Open Questions

None outstanding — the three decisions the ticket flagged for escalation (first-pass scope, text-entry click behavior, tmux compatibility) were resolved by the ticket owner before this design was written (fleet row list only; text-entry click would be focus-only if/when added, not implemented this pass; tmux verification deferred to a follow-up ticket).
