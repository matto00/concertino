### Verdict: REFUTE

### Change Requests

1. **`sectionHeight`'s needs-you special case has no fallback for a missing `opts.cols`, contradicting the design's own "can never drift" guarantee.** Design.md's Decision (and tasks.md 2.2) computes `innerCols = Math.max(0, opts.cols - BOX_BORDER_PADDING_COLS)` directly off `visibleWindow`'s `opts` parameter, then feeds it to `renderRun(...).length`. But `opts.cols` is optional in this function: every other field `visibleWindow` reads (`rows`, `selected`, `scrollOffset`, `queueState`) has an explicit `(opts && opts.X) || default` guard, while `cols` (a new read, introduced by this change) would not. There is an existing call site with no `cols` and `rows > 0` — `test/fleet.test.js:2148`: `visibleWindow(manyRuns, { rows: 12, selected: 0 })` — which currently avoids the problem only because that test's `manyRuns` are all `status: 'done'` (empty needs-you group short-circuits `sectionHeight` at `if (!s.group.length) return ...`). If a needs-you run were present under such a call (or any future caller that omits `cols`), `opts.cols` is `undefined`, so `Math.max(0, undefined - 4)` is `NaN`. Feeding `NaN` into `renderRun` then into `f.truncate(text, NaN - 8)` and `textwrap.wrap(text, NaN)` does not throw, but silently misbehaves: `truncate`'s `n <= 0` guard is skipped (`NaN <= 0` is `false`) and `wrap`'s line-break condition `visibleLength(candidate) > w` is always `false` when `w` is `NaN`, so `wrap()` never breaks the line at all. That means the estimate computed by `sectionHeight` in this path will not match what the real render pass (which always has a real `cols`, defaulted via `Math.max(40, (opts && opts.cols) || 80)` at `renderFleet`/`renderRun` sites) actually produces — reintroducing exactly the drift-between-estimate-and-reality bug class this whole Decision exists to eliminate, just for a different input than the one it defends against. Required revision: design.md/tasks.md must specify a `cols` fallback identical to the rest of the codebase's convention, e.g. `const cols = Math.max(40, (opts && opts.cols) || 80); const innerCols = Math.max(0, cols - BOX_BORDER_PADDING_COLS);`, before computing the needs-you estimate.

2. **Appending the `stale`/`keys` suffix onto the wrapped question's last line, unbounded, can overflow the box border for questions that fit under the wrap budget alone but not combined with the suffix — the exact regression the ticket's own acceptance criteria warns against.** design.md's Decision and tasks.md 2.1 direct: wrap only `run.escalation.question` against `opts.cols - 8`, then "append the `stale`/`keys` suffix onto the last pushed line (not a new line)." Today, `f.truncate(question + stale + keys, opts.cols - 8)` truncates the *combined* string, so the rendered line's visible length can never exceed `opts.cols - 8` and the box border is always safe. The proposed replacement only bounds the *question* against that width; nothing bounds the final line once `stale`/`keys` (which can run to `' [stale]   [a]pprove / [d]eny'`-scale) is appended afterward. Concretely: a question 5 columns under the wrap width will `wrap()` to a single, un-broken line (since nothing needed clipping), and appending, say, 20+ more characters of suffix pushes that line past `opts.cols - 8` with no truncation at all — overflowing the NEEDS YOU box's border, which is precisely the "box layout... without corrupting the box borders" failure the ticket's acceptance criteria calls out. design.md's own risk-mitigation paragraph for this ("for a question that already fits within width, wrapped output is a single line identical to today's truncated output ... verified explicitly by the ticket's 'short questions... unaffected' criterion") only covers the case where the *combined* question+stale+keys string already fit before this change — it silently assumes "question fits the wrap width" implies "question+suffix fits the wrap width," which is false whenever the question is close to (but under) the budget. Required revision: design.md/tasks.md must specify how the last line is kept within `opts.cols - 8` once the suffix is appended — e.g. reserve the suffix's width when deciding the wrap budget for the question's last line (wrap against `opts.cols - 8 - suffixWidth` and only widen back out if the question turns out to be single-line), or re-truncate the composed last line back down to `opts.cols - 8` after appending — before this is implementable without introducing a new border-corruption bug.
