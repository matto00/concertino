Premise validation (`.concertino/runs/CON-165/evidence/premise-validation.md`) found Fix 1 (worktree path required positionally) already fully satisfied across `core/scripts/`, so this design covers only the reuse-path identity check (an extension of Fix 3, informed by the still-live CON-155 gap) and the role-doc prohibition (Fix 2). `start-servers.sh` is not part of the `.husky/pre-commit` gate chain (verified directly against `.husky/pre-commit`), so the CON-132 Gate-Chain Implications Checklist does not apply to this change.

## Goals / Non-Goals

**Goals:**
- Make the reuse path in `start-servers.sh` verify process identity (cwd under `WORKTREE_PATH`) before adopting a healthy-but-unverified server.
- State the bare-invocation prohibition explicitly in the three role docs that actually start/verify servers.
- Provide mutation-failable coverage: a bare server on a colliding port, started from outside the worktree, must cause a refusal/report, not a silent reuse.

**Non-Goals:**
- Fix 4 (fail-closed tooling, e.g. requiring `PORT` with no fallback) — evaluated, explicitly deferred; too invasive for ordinary local dev per the ticket's own caution.
- Detecting or blocking a bare invocation that happens to land on a *different*, non-colliding port (that failure mode is already loud today: `assert-phase.sh servers`/`start-servers.sh` timeout on the pinned port).
- Any change to `setup-worktree.sh`, `squash-branch.sh`, `cleanup.sh` — already positional-only, verified during premise validation.

## Decisions

**Decision 1 — identity check via `/proc/<pid>/cwd`, not a new lockfile.** `start_one()` has no port parameter (`label cwd cmd health timeout log`) — the port to check is derived by parsing host+port out of the **resolved** `$url` (the same `url` already computed at line 80 via `eval "echo \"$health\""`), never from `$DEV_PORT`/`$BACKEND_PORT` directly, since those are not guaranteed to appear in `$health` (the existing test suite passes `0 0` while pointing `$health` at an unrelated port). If the parsed URL has no explicit port, or its host is not `127.0.0.1`/`localhost`/an address configured locally, no identity check is meaningful — skip it and keep today's behavior (see the "no local pid" case in Decision 2, same code path). Given a local host:port, find the pid(s) listening on it (`lsof -ti :$PORT`, falling back to a `/proc/net/tcp{,6}` inode→pid parse where `lsof` is unavailable — a genuinely new dependency for these scripts, noted as a risk below), and resolve each candidate's cwd via `readlink -f /proc/<pid>/cwd`. Rejected alternative: a run-scoped lockfile written by `start-servers.sh` itself — this only detects a server started via `start-servers.sh` from a *different* worktree, not a genuinely bare `npm run dev`, which never touches a lockfile at all. The `/proc` check works against both cases because it inspects the actual OS-level process regardless of how it was started.

**Decision 2 — the mismatch/degrade boundary, stated as one rule, not two.** A mismatch (loud `FAIL`, same shape as the existing timeout failure) is raised **only when**: exactly one pid is found listening on the parsed local port, **and** that pid's `/proc/<pid>/cwd` is readable, **and** the resolved cwd does not fall under `realpath "$WORKTREE_PATH"`. (Multiple pids on the same port is itself an ambiguous case — degrade, do not guess which one is authoritative.) Every other case — no pid found, `/proc/<pid>/cwd` unreadable (permissions, non-Linux, or a proxied/containerized process whose cwd is meaningless, e.g. `/`), or a non-local health URL — degrades to today's trust-the-health-check behavior, with a note on stderr, never a hard failure. This resolves the earlier draft's self-contradiction (which separately said "no matching pid is still a mismatch") in the direction that avoids a new false-BLOCKER class: Concertino runs arbitrary `CONCERTINO_*_START` commands for arbitrary projects, and a containerized/proxied backend routinely yields no discoverable local pid or a cwd that resolves to `/` — a run that works fine today must keep working. This exact rule is captured as its own spec scenario (not left as an implementation detail) so the boundary is contract, not something an implementer re-derives.

**Decision 3 — role-doc wording lives next to the existing `start-servers.sh` call sites**, not as a standalone new section, so it's read at the exact point an agent might otherwise reach for a bare command.

**Decision 4 — the existing reuse-branch test coverage is affected and must be restructured, not just re-pointed.** `test/scripts/start-servers.test.sh` (wired into `npm test`) currently starts a single, module-level `node` HTTP listener **once**, at lines 23-27, before any test repo exists — its cwd is the test script's own process cwd, never under any `$WT`. That one listener is then shared, via its fixed `$LISTENER_PORT`, across **five** separate reuse-branch blocks, each with its own `mktemp`-created `$WT`: `HEL-1` (~line 48), the ms-resolution loop reusing `HEL-3` (~line 123), `TICK-9` (~line 158), the no-explicit-id block (~line 181), and `CON-79` (~line 202). Under the new rule every one of these five turns red — a single shared process cannot have a cwd that resolves under five different, sequentially-created `$WT` directories, so "start the listener under `$WT`" is not executable against today's structure.

The fix is structural: remove the module-level shared listener entirely and give each of the five reuse blocks its **own** listener, started via a small helper (`start_listener_in "$WT"` — spawns `node -e 'require("http")...'` with `cd "$WT" &&` before it, picks a free port, returns the port and pid, registers cleanup) so its `/proc/<pid>/cwd` genuinely resolves under that block's own `$WT`. This preserves every block's original intent (exercise the reuse branch, assert its telemetry/ticket-id behavior) while making the listener's identity actually match the worktree the test claims it belongs to — the same invariant the production code now enforces. This is tracked as its own task (tasks.md §1.3, naming all five blocks explicitly) and is exactly the coverage a mutation-failable new test (tasks.md §2) must be added alongside, using its own separate, deliberately-foreign-cwd listener — never the shared one, which no longer exists after this restructuring.

## Risks / Trade-offs

[Risk: the mutation test's precondition could itself guarantee the assertion passes — e.g. if the test always starts its foreign process on a port unrelated to `DEV_PORT`, the check is never actually exercised] → Mitigation: the test must start the foreign process from outside the worktree *on the exact port `start-servers.sh`'s resolved health URL points at* for that run, and must first prove the check fails/goes red against the pre-fix script (checked out at the merge-base revision) before asserting it passes post-fix — per this batch's own "assertion whose precondition guarantees it" trap.

[Risk: `lsof` unavailable in a minimal CI image] → Mitigation: fall back to parsing `/proc/net/tcp{,6}` for the listening socket's inode → pid mapping when `lsof` is absent, matching the existing pattern of graceful degradation elsewhere in these scripts (e.g. `now_ms()`'s node fallback).

[Risk: prompt-level role-doc change alone is insufficient, as this batch has found three times] → Mitigation: the role-doc change is explicitly non-load-bearing here — the mechanical reuse-path check is what actually converts the class from silent to loud; the role-doc wording is a stated, subordinate deterrent, not the fix.
