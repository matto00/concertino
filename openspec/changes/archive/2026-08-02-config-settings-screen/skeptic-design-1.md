### Verdict: REFUTE

The proposal/spec are well-written and the router/screen-seam/prompt-overlay/save-discard plumbing (Decisions 1, 4, 5, 6) are sound and correctly grounded in the actual codebase. However, three concrete, verifiable gaps in `design.md`/`tasks.md` mean an implementer following the design literally will produce a screen that either silently omits required sections or silently writes invalid config — both of which contradict explicit ticket ACs. These are not nitpicks; they are specific, checkable technical claims that don't hold up against the code I read.

### Change Requests

1. **`flattenSchema` (Decision 3 / task 2.1) never mentions resolving `$ref`/`$defs`, or handling `additionalProperties`-keyed maps — yet 4 of the 16 required top-level sections depend on exactly that.**
   `config/concertino.schema.json`'s `models.properties['claude-code']`, `models.properties.codex`, `modelTiers.properties['claude-code']`, `modelTiers.properties.codex` are all `{ "$ref": "#/$defs/roleModelMap" }` / `{ "$ref": "#/$defs/tierMap" }` (schema.json:153-154, 162-163); `devServers.properties.backend/frontend` are `{ "$ref": "#/$defs/server" }` (schema.json:74-75); and `speeds` has no `properties` key at all, only `"additionalProperties": { "$ref": "#/$defs/speed" }` (schema.json:169). A flattener that (as literally described) "walks properties/nested properties" and stops there will produce **zero leaf fields** for `models.*`, `modelTiers.*`, `devServers.*`, and **all of `speeds`** — because those sections' actual field shapes only exist behind an unresolved `$ref`, and `speeds`' very key names (`default`, `fast`, `slow`, ...) are data-driven (present only in the on-disk config instance), not schema-declared, so a schema-only walk can never discover them at all. This directly contradicts `specs/settings-screen/spec.md`'s explicit requirement that `models`/`modelTiers`/`speeds` per-role/per-name entries are editable leaf fields, and task 3.1's expectation that every section's field pane is populated. **Required revision:** `design.md` Decision 3 and `tasks.md` 2.1 must explicitly describe `$ref`/`$defs` dereferencing, and must separately describe how `speeds`' dynamic key set is discovered (walking the *config instance's* `speeds` object, not the schema, then applying `$defs/speed`'s shape to each discovered key) before this is buildable as specified.

2. **Decision 3's claim that reading "the withDefaults()-shaped config" is sufficient for "an unset field visibly shows the same default withDefaults would apply" is empirically false for the entire `dashboard` section (and partially for `ui.tool`).**
   I read `withDefaults()` in full (`bin/concertino:331-356`): it defaults `harnesses`, `project.baseBranch/baseRemote`, `ticketProvider.idExample`, `specProvider.changeDir`, `worktree.base/envFiles/linkModules/hooks`, `canonicalDocs`, the whole `ui` object (only when entirely absent — a partially-set `ui` with no `tool` is NOT backfilled to the schema's `tool: "playwright"` default), `budgets`, `models`/`modelTiers`/`speeds` (via `withModelDefaults`), `agentMerge`, `commitTrailer`. **It never touches `dashboard` at all.** Confirmed by grep: `dashboard.retentionDays`, `dashboard.maxConcurrent`, `dashboard.launchPad.enabled/backlog` defaults are each applied ad hoc, independently, at their own call sites (`lib/ui/retention.js:25`, `bin/concertino:1150-1151`, `lib/ui/linear.js:384/466/473`) — never centrally. A settings screen that (per task 2.2) "reads a dotted path off a withDefaults()-shaped config for display" will show `undefined`/blank instead of `concertino` / `2` / `8` / `30` / `false` / `true` for `dashboard.tmuxSession/maxConcurrent/escalationTimeoutMinutes/retentionDays/launchPad.enabled/launchPad.backlog` whenever a project hasn't set them — directly failing `specs/settings-screen/spec.md`'s own scenario "An unset field shows its schema default" for an entire required section. **Required revision:** the current-value resolver (task 2.2) must fall back to the *flattened schema's* `default` directly whenever the raw config path is unset, independent of whatever `withDefaults()` happens to cover — not assume `withDefaults()` is a complete per-field default source, which it demonstrably is not.

3. **`collectConfigIssues` (Decision 2 / task 1.1), as a verbatim, mechanical lift of `cmdValidate`'s *today's* checks, has zero validation coverage for `budgets` and (aside from one incidental `teamKey` warning) `dashboard` — yet this ticket is precisely what makes those two sections editable via free-text-prompted, unconstrained integer/string fields for the first time.**
   I read all of `cmdValidate` (`bin/concertino:1400-1599`): its sections are exactly Structure / Project / Integrations / Worktree / Gates / Models / UI & dev servers / Canonical docs — matching task 1.1's own enumerated list verbatim. There is no Budgets section and no Dashboard section (only the one `cfg.dashboard.launchPad.enabled` / `teamKey` cross-check at line 1461). `budgets.executionCycles/skepticDesignRounds/skepticFinalRounds/debugAttempts` and `dashboard.tmuxSession/launchCommand/maxConcurrent/escalationTimeoutMinutes/retentionDays` are all editable via the free-text prompt path (Decision 5's third bullet — no enum, so no UI-side value constraint), and `coerce()` (`bin/concertino:393-398`) passes any non-`/^\d+$/` string straight through unchanged. Concretely: typing `abc` into `budgets.executionCycles`, or `-5` into `dashboard.retentionDays` (schema minimum 1, schema.json:127) or `dashboard.maxConcurrent` (schema minimum 1, schema.json:125), and pressing save would run `collectConfigIssues` (which checks neither section at all) and **write the invalid value to disk with no error shown** — a direct violation of the ticket's own explicit AC: "Invalid edits (fails schema validation) are rejected with a visible error, not silently written or crash-inducing." Design.md's Risks section only pre-emptively excuses drift for fields *added to the schema later* ("a pre-existing property of cmdValidate today... out of scope to fix here") — that framing doesn't cover this case, since `budgets`/`dashboard` are not newly-added schema fields, they are *existing* schema sections this ticket is choosing to newly expose to direct, unconstrained editing for the first time, while simultaneously promising a validation backstop. **Required revision:** either (a) `collectConfigIssues` must gain type/`minimum` checks for `budgets.*` and `dashboard.*` (the two sections this ticket newly makes editable that today's `cmdValidate` doesn't check), or (b) the design must explicitly narrow the editable-field list in `specs/settings-screen/spec.md`'s "Scalar and enum leaf fields are editable in place" requirement to exclude fields with no corresponding validation, and justify why that's an acceptable read of "not re-implementing schema validation." Silently shipping neither is not acceptable given the explicit AC.

### Non-blocking notes

- Decision 4's categorization of `devServers` alongside `harnesses`/`gates`/`canonicalDocs` as "array-of-object sections" is technically imprecise (`devServers` is a fixed object with up to two named sub-objects, not an array) — doesn't block implementation since it's consistently excluded from editing in both `design.md` and `spec.md`, but worth tightening the language when this is revised.
- Once Change Request 1 is resolved, the design should also explicitly note that `models`/`modelTiers`' top-level keys (`claude-code`, `codex`) are schema-declared as literal properties (so those two ARE staticaly enumerable even after fixing $ref-resolution), whereas only `speeds`' third-level keys are fully dynamic — worth spelling out so the executor doesn't over-generalize the fix.
