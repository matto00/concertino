## Context

`concertino.config.json` is validated today only by `bin/concertino`'s `cmdValidate` (`bin/concertino:1400`), a hand-rolled section-by-section checker (Structure/Project/Integrations/Worktree/Gates/Models/UI & dev servers/Canonical docs) that prints ✓/!/✗ lines and exits non-zero on error. It is not a generic JSON-Schema (ajv or similar) validator run against `config/concertino.schema.json` — there is no schema-validation library in this project's dependencies. `config/concertino.schema.json` (draft-07) is the source of truth for field `description`/`type`/`enum`/`default`, but only `bin/concertino` code reads it today (indirectly, by hand-coding the same checks the schema encodes); the TUI has never read it.

Every TUI screen shares one seam (`lib/ui/router.js`): a `SCREENS` map keyed by `state.mode`, each entry `{ render(state, opts) -> string, handleKey(key, state) -> action|null }`. `watch.js` owns all mutable state and is the only place actions are applied; screens are pure. `fleet.js` is the home screen and already has an unclaimed `s` key (confirmed in the ticket). Two existing screens are the closest analogs to what this screen needs:
- `launchpad.js`/`drilldown.js`: two-pane navigation (a list on one side, detail on the other), `focus` field switching which pane's keys apply.
- `fleet.js`'s `prompt` overlay (`promptKey`, `open-prompt`/`prompt-type`/`prompt-backspace`/`submit-prompt`/`cancel-prompt`): free-text single-line input as a state overlay layered on top of the underlying screen.

## Goals / Non-Goals

**Goals:**
- Browse every field in `concertino.config.json`, grouped by the schema's own top-level keys, with description/current-value/type-or-enum shown per field.
- Edit fields in place, staged in memory; explicit save validates against the schema and writes to disk; Escape discards.
- Reuse the schema-driven validation `bin/concertino` already performs — extracted into a shared function — rather than hand-rolling a second, divergent validator inside the TUI.
- Leave `concertino update`/`concertino validate`'s CLI behavior byte-for-byte unchanged.

**Non-Goals:**
- Editing `harnesses`, `gates`, `canonicalDocs`, `devServers` as structured array-of-object editors with full add/remove/reorder UI. These are still browsable (their fields render read-only with a "edit via `concertino update`/hand-edit `concertino.config.json` for structural changes" hint) — only scalar/enum/boolean leaf fields under object-shaped sections (`project`, `worktree.ports`, `ui`, `dashboard`, `budgets`, `agentMerge`, `commitTrailer`, per-role `models`/`modelTiers` entries, `speeds`) are editable in this slice. Array-of-object sections are exactly the shapes `concertino update`'s dotted-path `key=value` syntax already struggles to express well, and building a general array/object structural editor is a materially larger scope than "view and edit config" as the ticket frames it.
- A JSON-schema validation library (ajv, etc.) as a new dependency. `withValidationErrors` (Decision 2) is a hand-rolled function mirroring `cmdValidate`'s own existing hand-rolled checks, not a generic schema interpreter — consistent with how `cmdValidate` already works today.
- Live-reloading a running dashboard's already-resolved config (ports, harness, etc.) after a save. A save updates `concertino.config.json` on disk; picking up structural changes (e.g. a new gate) still requires `concertino sync` / a fresh session, exactly as it does today after a hand-edit.

## Decisions

### Decision 1: New `mode = 'settings'` screen, entered only from the fleet screen's `s` key

`router.js` gets one more `SCREENS` entry, `settings: { render: settings.render, handleKey: settings.routeHandleKey }`, following `docview`/`ticketdraft`'s existing registration pattern exactly. `fleet.js`'s `handleKey` gets one more binding, alongside `N` → `open-launchpad`:
```js
if (key === 's') return { type: 'open-settings' };
```
`watch.js` adds `openSettings()`/`backToFleet()` symmetry (mirroring `openLaunchPad()`/`backToLaunchPad()`): entering builds a fresh in-memory `settings` state object every time (unlike `launchPad`, which deliberately survives a round trip — Decision 4 below explains why settings does NOT reuse that pattern), and leaving via Escape (no unsaved changes) or a successful save both return to `mode = 'fleet'`.

Alternative considered: piggyback on the existing `docview` screen (already a generic "read a scrollable body" pane) and add editing on top of it. Rejected — `docview`'s entire contract (design.md Decision 3a in its own history) is "exactly one real caller, the evidence reader, generic content lines only" for a reason: bending it to also carry structured, editable, per-field schema metadata would break that invariant for a screen already relied on for something else, and gains nothing over a small dedicated screen — this codebase's existing convention is one purpose-built screen per concern (`ticketdraft.js`, `launchplan.js`, ...), not consolidation.

### Decision 2: `bin/concertino` grows a shared `collectConfigIssues(cfg)` extraction; `cmdValidate` is refactored to call it, not reimplemented — extended with `budgets`/`dashboard` checks this ticket newly requires

`cmdValidate` today interleaves checking with `console.log` side effects (the `ok`/`warn`/`fail` closures print immediately). This is refactored into a pure function `collectConfigIssues(cfg)` that returns `{ errors: [{ path, message }], warnings: [{ path, message }] }` by running the exact same checks (Structure/Project/Integrations/Worktree/Gates/Models/UI & dev servers/Canonical docs) against an in-memory candidate object, with no I/O and no process.exit. `cmdValidate` itself becomes a thin wrapper: call `collectConfigIssues`, then print each returned issue through the same `ok`/`warn`/`fail` console helpers it uses today, in the same order, then `process.exit(1)` iff `errors.length` — so its stdout output and exit code are unchanged for every existing input. `bin/concertino` exports `collectConfigIssues` (alongside its existing `loadConfig`/`withDefaults`) so `lib/ui/settings.js` (a `require('../../bin/concertino')`-style reuse, or a small refactor moving `collectConfigIssues`/`withDefaults` into a `lib/config.js` shared module `bin/concertino` itself now requires — see Open Questions) can call it on a candidate object before writing.

**Skeptic design-gate round 1 finding (addressed here):** today's `cmdValidate` has zero checks for `budgets` and (aside from one `dashboard.launchPad`/`teamKey` cross-check) `dashboard` — because neither section has ever been directly, unconstrained-ly editable before. This ticket's Decision 5 free-text-prompt path makes `budgets.executionCycles/skepticDesignRounds/skepticFinalRounds/debugAttempts` (schema: `type: integer`, no explicit minimum) and `dashboard.maxConcurrent`/`escalationTimeoutMinutes`/`retentionDays` (schema minimums 1/0/1 respectively) editable as raw typed text for the first time, and `coerce()` (`bin/concertino:393-398`) passes any string not matching `/^\d+$/` straight through unchanged — so without new checks, `abc` into `budgets.executionCycles` or `-5` into `dashboard.retentionDays` would save with no error, violating the ticket's own AC ("Invalid edits ... are rejected with a visible error, not silently written"). `collectConfigIssues` therefore gains two new sections, run against the same schema-declared constraints already present in `config/concertino.schema.json` (not invented ad hoc):
- **Budgets**: each of `executionCycles`/`skepticDesignRounds`/`skepticFinalRounds`/`debugAttempts`, when present, must be an integer (`Number.isInteger`); fail otherwise (schema declares `type: integer`, no `minimum`, so no lower-bound check beyond "is an integer" is invented here).
- **Dashboard**: `tmuxSession`/`launchCommand`, when present, must be strings; `maxConcurrent` (min 1), `escalationTimeoutMinutes` (min 0), `retentionDays` (min 1) must be integers at-or-above their schema `minimum`; `launchPad.enabled`/`launchPad.backlog`, when present, must be booleans. These mirror the exact `minimum` values already declared in `config/concertino.schema.json` (schema.json:123-133), not new constraints invented for this feature.

This closes the gap for exactly the two sections this ticket newly exposes to unconstrained free-text editing; it is not a general "validate every field against every schema constraint" effort (Decision 2's scope is still a hand-rolled, section-by-section check mirroring `cmdValidate`'s existing style, same as before this revision — see the Risks section for why a schema-drift gap elsewhere is knowingly out of scope).

Alternative considered: have the settings screen shell out to `concertino validate --config <tmp-candidate-path>` and parse its stdout/exit code. Rejected — spawning a subprocess per keystroke-adjacent save is slower and far more fragile (parsing colored console output) than calling a function directly, and the ticket explicitly asks to reuse the logic, not wrap the CLI.

### Decision 3: Schema metadata (`description`/`type`/`enum`/`default`) is read once per settings session directly from `config/concertino.schema.json`, flattened to a lookup by dotted path — resolving `$ref`/`$defs`, and separately walking the config instance for `speeds`' dynamic keys

**Skeptic design-gate round 1 finding (addressed here):** a naive "walk `properties`/nested `properties`" flattener, as originally described, produces zero leaf fields for `models.*`, `modelTiers.*`, and `devServers.*` (each defined as `{ "$ref": "#/$defs/roleModelMap" | "#/$defs/tierMap" | "#/$defs/server" }`, schema.json:74-75/153-154/162-163) and for all of `speeds` (`additionalProperties: { "$ref": "#/$defs/speed" }`, schema.json:169, with no static `properties` key at all). Revised design:

`flattenSchema(schema, configInstance) -> Map<dottedPath, { description, type, enum, default }>` walks `properties`/nested `properties` exactly as before, but resolves any `{ "$ref": "#/$defs/<name>" }` node by substituting `schema.$defs[<name>].properties` in its place before continuing the walk (a plain, local `$ref` resolver — this schema has no external/remote `$ref`s to support, so a full JSON-Reference implementation is not needed). Concretely:
- `models.claude-code` / `models.codex` / `modelTiers.claude-code` / `modelTiers.codex`: these four keys are themselves schema-declared literal properties (only their *contents* are behind `$ref`), so they are statically enumerable; each resolves through `$defs/roleModelMap` (five role keys) or `$defs/tierMap` (three tier keys) respectively.
- `devServers.backend` / `devServers.frontend`: likewise statically enumerable, each resolving through `$defs/server` (`cwd`/`start`/`health`/`timeoutSec`).
- `speeds`: has no schema-declared key names at all — its named presets (`default`, `fast`, `slow`, ...) exist only in the config *instance*, under `additionalProperties`. `flattenSchema` therefore takes the loaded config instance as a second input specifically for this section: it enumerates `Object.keys(configInstance.speeds || {})`, and for each discovered name resolves that name's fields through `$defs/speed`'s `properties` (`budgets.*`, `roleTiers.*`, `secondFinalGateSkeptic`, `evaluatorCleanWorktree`) exactly as any other `$ref`-resolved section. A project with no `speeds` key at all (schema/`withDefaults()` synthesizes an implicit `default` speed in that case — see `speeds`' own schema `description`) shows a single synthesized `default` entry rather than an empty section, matching what `withDefaults()` already does at resolution time elsewhere in this codebase.

Built once when the settings screen opens (schema does not change mid-session; the config instance is re-read fresh each time per Decision 4), not re-walked per keypress/render.

Current values: for every section **other than `dashboard`**, values come from `loadConfig()`'s already-`withDefaults()`-shaped object for display (so an unset field visibly shows the same default `withDefaults` would apply). **Skeptic design-gate round 1 finding (addressed here):** `withDefaults()` (`bin/concertino:331-356`, confirmed by direct reading) never touches `dashboard` at all — its defaults (`tmuxSession`, `maxConcurrent`, `escalationTimeoutMinutes`, `retentionDays`, `launchPad.enabled`/`launchPad.backlog`) are applied ad hoc, per call site, elsewhere in the codebase (`lib/ui/retention.js:25`, `bin/concertino:1150-1151`, `lib/ui/linear.js:384/466/473`), not centrally — and `ui.tool` is only backfilled when the entire `ui` object is absent, not when `ui` is present but `tool` specifically is unset. So the current-value resolver does **not** trust `withDefaults()` as a complete per-field default source: for every field, it first reads the raw on-disk value at that dotted path; only when that path is genuinely absent does it fall back directly to the *flattened schema's own* `default` (from Decision 3's `flattenSchema` output, sourced from `config/concertino.schema.json` itself) — never routed through `withDefaults()`'s partial, section-specific coverage. This is a single, uniform fallback rule applied identically to every section (including `dashboard`), rather than a `dashboard`-specific special case, so it can never again silently miss a section `withDefaults()` doesn't cover.

The **candidate object actually validated and written on save is the raw, pre-`withDefaults()` on-disk shape** with only the user's in-session edits applied — `withDefaults()` output (and the schema-default fallback above) is a read/display convenience, never itself written back (writing a fully-defaulted config back to disk would silently balloon `concertino.config.json` with every default value materialized, a regression `concertino update`'s existing raw-JSON read-modify-write, `bin/concertino:1649`, deliberately avoids).

### Decision 4: Two-pane layout — section list (left) + field list (right) — with a `focus: 'sections' | 'fields'` cursor, no persistent cross-session state

Modeled directly on `drilldown.js`'s/`launchpad.js`'s existing box-per-pane, `focus`-gated key routing (fleet.js's own `focus === 'queue'`/`focus === 'quickstart'` blocks are the nearest sibling pattern already in this codebase). Left pane lists the schema's top-level keys in schema-declaration order (`harnesses, project, ticketProvider, specProvider, worktree, devServers, gates, canonicalDocs, ui, dashboard, budgets, models, modelTiers, speeds, agentMerge, commitTrailer`); right pane lists that section's leaf fields (dotted sub-path, current value, type/enum badge) once a section is selected/focused.

Unlike `launchPad` (which the existing code deliberately keeps alive across a trip back to the fleet screen — `backToLaunchPad()`/`openLaunchPad()`'s own `if (!launchPad)` guard), the settings session is rebuilt fresh every time `s` is pressed: config on disk can change between visits (a hand-edit, another `concertino update`, or a previous settings-screen save), and there is no equivalent to launch-pad's expensive network refresh to avoid repeating — re-reading a local JSON file plus the static schema is cheap, so freshness wins over any caching concern here.

### Decision 5: Editing is a `fleet.js`-style single-line prompt overlay, keyed per field-type

Reuses the exact `prompt = { value, error }` / `promptKey`-style overlay convention `fleet.js` already has for its `n` (open-prompt) flow, rather than inventing a second input mechanism:
- **boolean**: no prompt — `Enter`/`Space` toggles true/false directly (no free-text entry needed for a two-value domain).
- **enum** (schema `enum` present): `Enter`/`Space` cycles to the next enum value (mirrors `launchplan.js`'s existing `cycleConcurrency`-style value-cycling for a small fixed value set) — no free-text entry, so an edit can never produce a value outside the enum.
- **string/number/integer with no enum**: `Enter` opens the single-line text-prompt overlay (seeded with the field's current value as editable starting text, unlike `fleet.js`'s own always-starts-empty prompt), `Escape` cancels the field edit (returns to the field list with the value unchanged), `Enter` again commits the typed text into the in-memory candidate at that field's dotted path (coerced to number/integer via the same `coerce()` helper `cmdUpdate` already uses, so "5" typed for an integer field becomes `5`, not `"5"`).
- **array/object-shaped fields excluded per Non-Goals** render read-only (dimmed, with the "edit via `concertino update`" hint) and do not respond to `Enter`.

Each committed field edit is staged directly into an in-memory candidate config (a working copy of the raw on-disk JSON), not validated field-by-field as it's typed — validation happens once, on save (Decision 2), against the whole candidate, since some fields' validity depends on siblings (e.g. `ui.triggers` non-empty only matters when `ui.enabled` is true) and re-running the full `collectConfigIssues` pass on every keystroke would be wasteful and would surface misleading errors mid-edit (e.g. flagging `ui.triggers` as empty while the user is still one keystroke into typing a value into a *different* field).

### Decision 6: Save (`S`) and discard (`Escape`) are the screen's only two exit-with-effect actions; a third, distinct key opens the free-text edit prompt

Bound as: `Escape` (no field prompt open) → `back` action, discarding all staged edits, returning to fleet, matching the ticket's "Escape returns to the fleet screen without requiring a save" acceptance criterion exactly. Capital `S` → `save` action: runs `collectConfigIssues(candidate)`; if `errors.length`, the screen shows those errors inline (a dismissible banner in the field pane, not a crash, not a silent partial write — matching "Invalid edits ... are rejected with a visible error, not silently written or crash-inducing") and stays open with edits still staged; if clean, writes `JSON.stringify(candidate, null, 2) + '\n'` to `concertino.config.json` (identical serialization to `cmdUpdate`'s own write, `bin/concertino:1664`) and returns to fleet. The footer always shows both hints (`esc discard  ·  S save`), per the ticket's "explicit save action ... shown in the screen's footer/help hint" criterion.

Lower-case `s` is deliberately NOT reused as the in-screen save key (it would collide with the fleet screen's own entry key if a user's muscle memory carried over, and — more importantly — this codebase already reserves the capital/lowercase split for exactly this kind of "distinct, deliberate action" pairing, e.g. `n`/`N` for single-ticket-launch vs. launch-pad).

## Risks / Trade-offs

- **[Risk]** Extracting `collectConfigIssues` out of `cmdValidate` risks subtly changing `concertino validate`'s output ordering or wording if the refactor isn't purely mechanical. → **Mitigation**: the refactor moves the existing checks verbatim into the pure function and re-wires `cmdValidate` to print from its returned arrays in the same order the checks currently run in; the evaluator/skeptic gates re-run `concertino validate` (and, where present, existing tests) against known-good and known-bad fixture configs to confirm output is byte-identical to pre-refactor.
- **[Risk]** A schema change (`config/concertino.schema.json`) in the future could drift from `collectConfigIssues`'s hand-rolled checks (they are not generated from the schema, just informed by it) — a field could be added to the schema with a description but no corresponding check, so it would display correctly but never be validated. → **Mitigation**: this is a pre-existing property of `cmdValidate` today (its checks are already hand-written against the schema's shape, not generated from it), not a regression this change introduces. Where this ticket itself newly exposes a previously-unchecked section to direct editing (`budgets`, `dashboard` — see Decision 2), new checks were added specifically to close that gap; any *other* section this ticket does not newly expose to editing is left at today's existing (pre-ticket) coverage level, which is out of scope to improve here.
- **[Risk]** Non-Goal-excluded array/object fields (`gates`, `harnesses`, `canonicalDocs`, `devServers`) being read-only in this screen could read as an incomplete/broken editor to a user expecting to edit everything. → **Mitigation**: the read-only hint text names the CLI path (`concertino update`/hand-edit) explicitly, so it reads as "not yet supported here" rather than a bug.
- **[Trade-off]** Rebuilding settings state fresh on every `s` (Decision 4) means no in-memory "you had unsaved edits, come back to them" recovery across an Escape-then-reopen — this is intentional (Escape means discard, per the acceptance criteria) but is worth naming as a deliberate trade-off, not an oversight.

## Migration Plan

Purely additive — no existing config, CLI command, or screen changes behavior for an operator who never presses `s`. No data migration. Rollout is just shipping the new screen/keybinding; rollback is reverting the commit (no persisted state format introduced).
