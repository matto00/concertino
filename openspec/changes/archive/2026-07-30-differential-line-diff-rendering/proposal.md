## Why

CON-17 fixed the dashboard poll loop's flicker with a cursor-home + pad-to-width full-frame overwrite, deliberately deferring true line-diff rendering as a follow-up "if the poll ever gets more expensive." The full-frame rewrite still costs O(total visible rows) of terminal writes on every 1 Hz tick even when only one or two rows actually changed. This change closes that gap: diff the new frame against the previous one line by line, and only write the rows that changed, positioning the cursor per row.

## What Changes

- `buildFrame()` (`lib/ui/watch.js`) gains a differential mode: given the previous frame's rendered lines and the new frame's rendered lines, it computes which row indices differ and emits per-row cursor positioning (`\x1b[<row>;1H`) plus that row's padded content only for the rows that changed, instead of homing the cursor once and rewriting every line. This is now the mechanism used for **every** frame except one: a frame taller than the terminal's current row count. There is exactly one case that still uses the original full-rewrite (`CURSOR_HOME` + newline-flow join) path — an over-tall frame relies on the terminal's own newline-driven scroll (see `lib/ui/screens/fleet.js`'s deliberate NEEDS-YOU overflow), which absolute row addressing cannot reproduce.
- The very first frame of a session, and the frame immediately following a terminal resize, both still go through the diff path above — NOT the full-rewrite path — but with the previous-frame cache deliberately invalidated first, so every row of that one frame is treated as "changed" and gets rewritten. For the first frame this is an emergent property of starting from an empty cache; for a resize it is explicit: the resize listener replaces every entry of the cache with a sentinel value that can never equal real content, while preserving the cache's own length (see below for why length must survive).
- The dashboard's own frame-cache state is explicitly invalidated in two places, both required for the diff to stay correct rather than just "usually correct" — but by two different mechanisms, because the two events are not the same kind of invalidation: returning from `tmux attach` resets the cache to empty (`\x1b[?1049h` genuinely clears the alternate screen buffer, so there is no stale tail left to blank); a resize replaces the cache's *content* with a sentinel while preserving its *length* (a resize does not clear anything, and the existing shrink-cleanup logic still needs to know how many trailing rows the previous, pre-resize frame had, in case the new frame is shorter).
- The existing shrink-cleanup behavior (blanking stale trailing rows when the new frame has fewer lines than the previous one) is preserved unchanged for the normal (non-overflow) diff path — it is itself now just "the changed row range that includes every trailing row down to the previous, taller frame's last line," and it keeps working after a resize specifically because the resize invalidation above preserves the cache's length rather than discarding it.
- The terminal cursor, which the dashboard has never hidden, is explicitly parked at the end of the frame's last row whenever any row was rewritten this tick — matching where it already, incidentally, comes to rest today — so it does not visibly jump to whichever row happened to change most recently on a given tick.
- `lastFrameLines` (today: a line count) is replaced by `prevFrameLines` (the previous frame's own array of already-padded lines) — one variable, not a count plus a parallel array — so a real per-line diff has actual previous content to diff against.
- No change to *what* text is rendered — `router.render()`, every `lib/ui/screens/*` module, and `lib/ui/banner.js` stay pure, string-returning, and untouched, exactly as CON-17 preserved this boundary.

## Capabilities

### New Capabilities
(none)

### Modified Capabilities
- `dashboard-render-loop`: the redraw requirement changes from "each poll redraw homes the cursor and overwrites every rendered line" to "each poll redraw writes only the rows whose content changed since the previous frame, each positioned via its own per-row cursor placement, with the cursor explicitly parked at the frame's last row afterward; only a frame taller than the terminal's row count still does a full newline-flow rewrite via cursor-home." The existing padding-by-visible-width and shrink-cleanup requirements carry over unchanged for the normal diff path, now expressed as a special case of the diff (every row from the shrink point onward counts as "changed"). The existing "Attach suspends and restores..." and "Resizing mid-run reflows..." requirements are also modified: both now additionally invalidate the frame diff cache (attach: reset to empty; resize: content invalidated, length preserved) so the first redraw after either event repaints every row, not a partial diff against stale pre-event content.

## Impact

- `lib/ui/watch.js` only (`buildFrame()`, its call site in `draw()`, the `prevFrameLines` state it threads through, the `doAttach()` restore callback, and the `process.stdout.on('resize', ...)` listener) — per the ticket's explicit scope note, `lib/ui/router.js` and every `lib/ui/screens/*` module remain untouched.
- `test/watch.test.js` — existing `buildFrame` tests assert byte-for-byte behavior for the full-rewrite path, including asserting on the literal `CURSOR_HOME` byte prefix; they need rewriting (not just signature adjustment) for the new diff path (unchanged frame writes nothing new, a single changed row writes only that row plus the trailing cursor-park write, growth/shrink still work, an over-tall frame still falls back to a full rewrite) without breaking the guarantees CON-17 already locked in (no `\x1b[2J`, still cursor-positioned not cleared, still padded by visible width).
- `openspec/specs/dashboard-render-loop/spec.md`'s "Attach suspends and restores..." and "Resizing mid-run reflows..." requirements ARE modified by this ticket (frame-cache invalidation), contrary to an earlier draft of this proposal — both are covered in this change's specs delta.
