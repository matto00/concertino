## Context

`lib/ui/watch.js`'s `draw()` calls `buildFrame(rendered, cols, lastFrameLines)` on every 1 Hz poll tick. Today `buildFrame` always writes `CURSOR_HOME + lines.join('\n')` — the whole frame, every tick, regardless of how many rows actually changed — then blanks any stale trailing rows if the new frame is shorter than `lastFrameLines` (a line *count*, not the actual previous content). This is CON-17's deliberately cheaper (1)+(2) fix; this ticket is the deferred (3).

Every rendered line already passes through `format.padTo()`, which pads to *visible* column width (ANSI-aware) exactly `cols` columns, before being written — CON-17 established this and it does not change here.

Switching from newline-flow writes to absolute per-row addressing (`\x1b[<row>;1H`) is not a drop-in optimization of the same behavior — it changes what the terminal does in two situations the original relative-flow writer handled for free, and this design's round-1 skeptic review (see `skeptic-design-1.md`) is what surfaced both:

- **`tmux attach`/detach.** `doAttach()` (`watch.js:648-672`) exits the alternate screen buffer before handing the terminal to tmux, and re-enters it (`\x1b[?1049h`) once tmux returns. Entering the alternate screen buffer *clears it*, and tmux has fully owned the terminal in between — so nothing about the pre-attach frame is still on screen, even though this file's own `prevFrameLines` state does not know that.
- **Over-tall frames.** Not every screen bounds its own output to `process.stdout.rows`: `ticketview.js`, `drilldown.js`, `escalation.js` and `launchplan.js` never read `opts.rows` (only `fleet.js` and `launchpad.js` do), and `fleet.js` itself *deliberately* lets its NEEDS YOU section overflow past the terminal height rather than trim it ("if it alone overflows the terminal we lose the header, which is the right thing to lose" — `fleet.js:286-288`). Today, an over-tall frame relies on the terminal's own newline-driven auto-scroll to make that trade-off happen; verified directly (`ticketview.render(..., { rows: 24 })` returns 131 lines). Absolute row addressing cannot reproduce a scroll — a `\x1b[<row>;1H` write for a row beyond the terminal's height clamps onto the last row instead, and after any scroll has happened, this file's own `prevFrameLines` no longer describes what is physically on screen at those row positions.

This design treats both as first-class cases that fall back to the original newline-flow writer, rather than editing `screens/*` to bound their own output (out of scope — the ticket's scope note requires `router.js`/`screens/*` stay untouched).

## Goals / Non-Goals

**Goals:**
- Only write terminal rows whose content actually changed since the previous frame, in the common case where the frame fits the terminal and nothing has intervened since the last poll.
- Preserve every existing guarantee in `openspec/specs/dashboard-render-loop/spec.md`: no `\x1b[2J`, visible-width padding, stale-trailing-row cleanup on shrink, correct behavior across resize and attach — including the two behaviors named in Context above, which must come out of this change no worse than they are today.
- Keep the change confined to `lib/ui/watch.js` (`buildFrame`, its `draw()` call site, the state threaded between polls, `doAttach()`'s restore callback, and the resize listener).

**Non-Goals:**
- Sub-row (character-range) diffing. This diffs whole rows only — the ticket's own scope note calls out "colour-escape boundaries mid-line" as exactly the kind of edge case a sub-row diff invites, and there is no perf motivation for it (a single `\x1b[<row>;1H<content>` write per changed row is already cheap).
- Making every screen respect `process.stdout.rows` (fixing `ticketview.js`/`drilldown.js`/`escalation.js`/`launchplan.js` to bound their own output). Out of scope per the ticket's scope note; this design instead makes `watch.js` defensive against screens that don't.
- Any change to `router.js` or `screens/*` — they remain pure, string-returning, untouched.
- A generic/reusable diff utility — this stays a `watch.js`-local concern, matching the proposal's scope.

## Decisions

**Decision 1 — Represent "previous frame" as the array of previously-written padded lines, not a count.**
Replace `lastFrameLines: number` with `prevFrameLines: string[]` (initialized to `[]`) in `watch()`'s closure state. A count is enough to blank stale trailing rows, but a real per-line diff needs the previous content to compare against, not just how many lines there were. `buildFrame`'s signature becomes `buildFrame(text, cols, rows, prevLines)` (see Decision 6 for the new `rows` parameter), returning `{ bytes, lines }` (the lines to store as `prevFrameLines` for the next call — see Decision 6 for why this is not always simply "the new frame's own padded-line array") instead of `{ bytes, lineCount }`.
*Alternative considered:* keep `lastFrameLines` as a count *and* add a second array — rejected as redundant state that can drift; the array's own `.length` already is the count.

**Decision 2 — Diff by strict string equality per line index, on already-padded content.**
Each new line (post-`padTo`) is compared with `prevLines[i]` via `!==`. A changed (or new, i.e. `prevLines[i] === undefined`) row is written as `\x1b[<row>;1H` + that row's full padded content; an unchanged row is skipped entirely. This reuses `padTo` exactly as CON-17 already does — no new ANSI-parsing logic — and keeps the diff itself trivial (row-granularity, not character-range), per the Non-Goals above. This is the path used only when Decision 6's fallback conditions do not apply.

**Decision 3 — The first frame of a session, and any frame following a resize, still repaint every row — the first frame as an emergent property of the diff, a resize via content-only cache invalidation that preserves the previous frame's LENGTH.**
Seeding `prevFrameLines = []` at session start already makes every row of the very first frame count as "changed," so the first frame needs no special code path — this part is an emergent, correct property of the diff itself, not a decision that needs separate machinery.
Resize needs an explicit decision, and round 2 of this design's own skeptic review found the first version of it (unconditionally resetting `prevFrameLines = []` in the resize listener, mirroring Decision 7's attach handling) to be a regression: `[]` throws away the previous frame's *length*, not just its content, and the existing shrink-cleanup loop (Decision 2's shrink case) is driven entirely by `prevLines.length` — with the cache emptied, that loop can never fire on the resize-triggered redraw, so a rows-shrinking resize (verified: `fleet`'s own render goes from 27 lines at 30 rows to 18 lines at 20 rows) leaves stale trailing rows on screen, which is exactly the corruption the existing "no stale content from the larger, pre-resize frame" spec requirement was written to prevent.
The fix is to invalidate CONTENT while preserving LENGTH: `padTo` pads every line to *exactly* `cols` visible columns (verified against `format.js:300-303`), so a **cols** change is already a guarantee (not a probabilistic "will essentially never compare equal") that every row's padded bytes differ from the stale `prevFrameLines`, and the diff repaints everything correctly on its own with no help needed. A **rows-only** resize (dragging the bottom edge, a tmux pane resize/split) leaves `cols` unchanged, so unchanged screen content pads to byte-identical strings and the diff would (incorrectly) skip repainting rows whose backing terminal dimensions have, in fact, just changed. To force a full repaint here WITHOUT losing the length the shrink loop needs, the resize listener (`watch.js:589`) replaces every entry of `prevFrameLines` with a sentinel value (`null`) that `padTo`'s output can never equal, keeping `prevFrameLines.length` exactly what it was — `prevFrameLines = prevFrameLines.map(() => null)` — immediately before calling `draw()`, for every resize event. Every row then diffs as "changed" (`lines[i] !== null` is always true) and gets rewritten via the ordinary diff path, while the untouched `.length` still drives the shrink loop correctly for any row the new, resized frame no longer has.
*Alternative considered:* reset to `[]` (Decision 7's attach mechanism) — rejected for resize specifically, and this is the one place this design draws a real distinction between the two invalidations: entering the alternate screen buffer (`\x1b[?1049h`, attach) *actually clears the terminal*, so there is no stale tail left to blank and `[]` is correct there; a resize does not clear anything, so the previous frame's length remains meaningful and must be preserved for the shrink loop to keep doing its job.
*Alternative considered:* rely on the `cols`-change argument alone and special-case only a detected rows-only resize — rejected: strictly more code for a case (rows-only resize) that is common in practice (e.g. any tmux pane-height change) and where getting the detection wrong (e.g. `process.stdout.rows` briefly stale mid-resize) silently reintroduces stale content, which is exactly the bug class this ticket must not add.

**Decision 4 — Shrink cleanup is unconditional for rows beyond the new frame's length, exactly as today.**
Rows from `lines.length + 1` through `prevLines.length` (when the previous frame was taller) have no corresponding new-frame row to diff against, so they are blanked unconditionally — this is the same behavior `buildFrame` already has today, just now framed as "there is nothing to compare, so always blank," not "diffed and found different." This applies only within Decision 2's normal diff path (i.e., when Decision 6's fallback does not apply).

**Decision 5 — An unchanged frame writes zero bytes, and the write is skipped, not just empty.**
When no row differs and the frame did not shrink, `bytes === ''`. `draw()`'s call site guards the write itself — `if (frame.bytes) process.stdout.write(frame.bytes);` — rather than writing unconditionally, so "an unchanged tick touches stdout not at all" is literally true, not merely "writes zero bytes to a stream call." This is the ticket's "close to free" goal for the common case where most of the dashboard is unchanged between ticks.

**Decision 6 — An over-tall frame falls back to the original full newline-flow rewrite, never absolute row addressing, and its cache entry is the terminal's actual visible tail, not the whole frame.**
`buildFrame` takes a new `rows` parameter (`process.stdout.rows || 0`, i.e. the *whole* terminal height — not the screen-content sub-budget `screenRows` that `draw()` already computes for `router.render()`, since the terminal's own auto-scroll behaves on total rows, and the rendered text passed to `buildFrame` already includes the banner). Define `overflow = rows > 0 && lines.length > rows`. This is the ONLY condition for the fallback — round 1 of this design's review also considered a second condition (`prevLines.length > rows`, "the previous write left the terminal in a scrolled state") for the case immediately after an overflow, but round 2 found it self-contradictory (at `rows === 0` it fires on every single frame, directly contradicting this same Decision's "never triggers when `rows` is unknown," and is exactly the condition `test/scripts/watch-smoke.test.sh` runs under, since it redirects stdout to a file). It is also unnecessary: the very next paragraph's truncation already keeps `prevLines.length <= rows` after every overflow write, so `overflow` alone already reaches the fallback again whenever the current frame is still too tall, and Decision 3's resize invalidation (or Decision 7's attach invalidation) already forces a full repaint through the *ordinary* diff path for the "just came back from a scrolled/cleared state" case — a second, redundant path to the same outcome was removed for simplicity rather than kept "just in case."
When `overflow` is true, `buildFrame` does not diff at all: it writes `CURSOR_HOME + lines.join('\n')` (today's exact full-rewrite bytes, including today's own trailing-row shrink-blanking, computed against `prevLines.length` exactly as it is today), which lets the terminal's own newline-driven scroll happen exactly as it does today — this is what preserves `fleet.js`'s deliberate "NEEDS YOU stays visible, header scrolls off" behavior unchanged. When `rows` is `0` (falsy — `process.stdout.rows` is unset for a non-TTY stdout, matching how `draw()`'s own `screenRows` computation already treats `totalRows <= 0`), `overflow` is always `false`, unconditionally, and this fallback never triggers — preserving today's test-harness behavior of calling `buildFrame` without a real TTY, and specifically the smoke gate's redirected-stdout runs.
The `lines` value `buildFrame` returns for the caller to store as `prevFrameLines` is, in the overflow-fallback case, **not** the full `lines` array — it is `lines.slice(Math.max(0, lines.length - rows))`, i.e. only the last `rows` lines, because those are the lines the terminal's auto-scroll actually leaves visible at physical rows `1..rows` once the scroll settles. Storing the truncated tail (instead of the full array) is what lets a *later*, back-within-bounds frame resume trustworthy per-row diffing — an absolute row `i` genuinely corresponds to `prevFrameLines[i]` again once this invariant is restored. In the normal (non-overflow) case, the returned `lines` is the full new-frame array exactly as before.
*Alternative considered:* clamp/truncate `lines` to the first `rows` entries before diffing, instead of falling back to newline-flow — rejected: this would keep the header on screen and cut off the tail, the *opposite* of `fleet.js`'s deliberate "lose the header, keep NEEDS YOU visible" trade-off, silently changing user-visible behavior for exactly the case (an unanswered escalation) where a human is watching the dashboard for something to act on.

**Decision 7 — `doAttach()`'s restore callback resets the frame cache to `[]`, on both the normal and throwing paths, for free.**
Inside the `attachAndRestore(() => session.attach(ticket), () => { ... })` call in `doAttach()` (`watch.js:666`), the restore callback (second argument) already runs unconditionally — including when `session.attach()` throws — because `attachAndRestore` itself is a try/finally (see its own header comment / `design.md` from CON-17). Adding `prevFrameLines = []` inside that same restore callback therefore covers both the normal-return and exception paths with one line, matching the same "textually paired, exception-safe" discipline the raw-mode and alternate-screen restores in that callback already use. `[]` (not Decision 3's length-preserving sentinel) is correct specifically here, unlike resize: `\x1b[?1049h` genuinely clears the alternate screen buffer, so there is no stale tail on screen to blank — the shrink loop has nothing to do, and an empty array correctly makes every row of the next frame count as "changed" while contributing nothing to a shrink comparison that would otherwise (harmlessly, since there's nothing to blank) run against a stale length. The very next `draw()` after control returns to the dashboard then does a full rewrite through the ordinary diff path (an emergent property of `prevFrameLines = []`, exactly like the first-frame case) — correctly repainting a screen that `\x1b[?1049h` just cleared.

**Decision 8 — After any tick that writes at least one row, the cursor is explicitly parked at the last row, so it does not visibly jump around the dashboard tick to tick.**
Today, `bytes = CURSOR_HOME + lines.join('\n')` always ends with the last line's content, so the cursor rests at the bottom of the frame after every single tick — a fixed, stable position, invisible in practice because it never moves relative to the frame. The dashboard never hides the cursor (`grep -rn "25l|25h"` over the whole repo returns nothing), so this is directly visible. Under the diff path, the last byte written on an ordinary tick is whichever changed row happened to have the highest index (the clock, an idle timer, a progress bar) — varying tick to tick, which would make the cursor visibly jump around the dashboard once a second, a regression of the exact "visual stillness" property CON-17 and this ticket both exist to improve.
Fix: whenever the normal diff path's `bytes` is non-empty (i.e., at least one row actually changed this tick), unconditionally append one more write — `\x1b[<lines.length>;1H` + the last row's own padded content — after the per-row diff loop and the shrink-blanking loop. This reproduces today's exact resting position (end of the last row) regardless of which row(s) changed, at the cost of one extra `cols`-byte row write on ticks that already wrote something (never on a fully unchanged tick, so Decision 5's "an unchanged tick touches stdout not at all" is completely unaffected). If the last row happened to already be part of the changed set, it is simply written twice — accepted as negligible, not worth the extra branch to avoid.
This write is not purely cosmetic — it is also what keeps the diff cache correct in one specific edge case created by Decision 3's resize sentinel. The resize sentinel deliberately preserves a pre-resize `prevFrameLines.length` that can exceed the new, post-resize `rows` (e.g. a 30-row terminal showing a 30-line frame, resized to 20 rows with a 20-line frame): the shrink-blanking loop (task 1.6) then targets rows up to the OLD length, and `\x1b[<row>;1H` for a row beyond the terminal's actual height clamps onto the last real row (`rows`) instead — meaning the shrink loop's own blanking, if it runs after the diff loop wrote that same last row, would overwrite it with blank spaces. Because task 1.7's park write is specified to run AFTER the shrink loop, it repairs exactly this: the last row ends up with its real content, not a trailing blank. Skipping the park write when the last row happens to already be in the changed set (an "optimization" it may be tempting to add later) would silently reintroduce a permanently blank bottom row in this case — the write must stay unconditional whenever `bytes` is non-empty.
*Alternative considered:* hide the cursor for the session (`\x1b[?25l` on entry, `\x1b[?25h` restored on every exit path) — rejected as a broader behavior change with its own restore-on-every-exit-path obligation (mirroring the alternate-screen-buffer discipline `watch.js:86-92` already documents for exactly two other sequences), which this ticket's scope note does not obviously cover; parking the cursor is a strictly smaller change that fully addresses the regression.

## Risks / Trade-offs

- [Risk] A sub-row diff would be marginally more precise (e.g. only a status word changed mid-row) → Mitigation: explicitly out of scope (Non-Goals) — row-granularity is the ticket's own suggested edge, and a whole-row `\x1b[<row>;1H<content>` write is already cheap at typical terminal widths.
- [Risk] The existing `buildFrame` tests in `test/watch.test.js` assert byte-for-byte on the old always-full-rewrite behavior, including asserting `frame.bytes.startsWith(CURSOR_HOME)` and slicing `CURSOR_HOME.length` (3 bytes, `\x1b[H`) off the front — the new per-row prefix for row 1 is `\x1b[1;1H` (7 bytes), a different byte sequence, not a version of the same one → Mitigation: tasks.md spells out the exact new expected prefix so these are treated as semantic rewrites, not signature/offset adjustments.
- [Risk] `buildFrame`'s parameters change shape (a 3rd `number` argument becomes a 3rd `number` (`rows`) plus a 4th `array`), a breaking signature change → Mitigation: it has exactly one production call site (`draw()`) and is otherwise exported only for `test/watch.test.js` (per `watch.js`'s own trailing comment) — both are updated in this same change.
- [Risk] The `CURSOR_HOME` constant is a public export (`watch.js:1237`) still imported by `test/watch.test.js` and still used by the Decision 3/6 fallback paths (first frame, resize, overflow) → Mitigation: `CURSOR_HOME` is **kept**, both as the full-rewrite prefix in the fallback path and as its existing export — nothing about its greppability guarantee (`watch.js:86-92`'s "exactly one `\x1b[?1049h`... one `\x1b[H`... never reappears under a different spelling") changes; this ticket does not remove `\x1b[2J` avoidance machinery, it adds a second writer mode alongside it.
- [Risk] Prose comments in `watch.js` describing the old always-full-rewrite mechanism (`buildFrame`'s own header at `:97-110`, the `draw()` call-site comment at `:540-543`, the `lastFrameLines` comment at `:226-229`) become factually wrong once this ships → Mitigation: tasks.md includes explicitly rewriting these comments, not just the code, since this codebase's comments carry real design rationale that later readers rely on.
- [Risk] `proposal.md` (the capability-level statement of this contract) drifting out of sync with `design.md`/`tasks.md`/the spec delta on which frames use the diff path vs. the full-rewrite fallback — this happened twice during this design's own review (round 1's R4, recurring in round 2's R3) → Mitigation: proposal.md's "What Changes" section is the last thing updated after any further change to Decisions 3/6, and states the mechanism split exactly once, in one place, rather than repeating a paraphrase that can drift.
- [Risk] Decision 8's cursor-park write duplicates the last row's content when that row was already part of the diff (an extra `cols`-byte write, never more than once per tick) → Mitigation: accepted as negligible — the "close to free" goal this ticket targets is the fully-unchanged-tick case (Decision 5), which Decision 8 does not touch at all; a tick that already wrote something paying a few extra bytes is not the case being optimized.

## Migration Plan

None needed — single-file, internal implementation change behind the existing `buildFrame` export, no data model, no external dependency, no rollout sequencing. Ships as one PR; a revert is a plain `git revert`.
