## 1. Implement the diff-based `buildFrame`

- [x] 1.1 Change `buildFrame(text, cols, prevLineCount)` to `buildFrame(text, cols, rows, prevLines)` in `lib/ui/watch.js`, where `rows` is the whole terminal row count (`process.stdout.rows || 0`, may be `0`/falsy) and `prevLines` is an array of the previous frame's own padded-line strings, or sentinel values (may be `[]`).
- [x] 1.2 Build the new padded-line array (`lines`) exactly as today (`text.split('\n').map((line) => format.padTo(line, cols))`).
- [x] 1.3 Compute `overflow = rows > 0 && lines.length > rows`. This is the ONLY fallback condition — do not add a second condition based on `prevLines.length` (design.md Decision 6 explains why an earlier draft's `prevLines.length > rows` disjunct was both redundant and, at `rows === 0`, self-contradictory with "the fallback never triggers when rows is unknown"). When `overflow` is true, skip the diff entirely and produce `bytes = CURSOR_HOME + lines.join('\n')` plus the existing trailing-row shrink-blanking loop (computed against `prevLines.length`, exactly as `buildFrame` does today) — this is today's full-rewrite behavior, unchanged, deliberately preserving the terminal's own newline-driven scroll for an over-tall frame.
- [x] 1.4 In the overflow-fallback branch, the `lines` value returned for the caller to store as the next `prevFrameLines` is `lines.slice(Math.max(0, lines.length - rows))` (only the tail actually left visible by the terminal's scroll), not the full `lines` array. This branch is only reached when `overflow` is true, which already requires `rows > 0`, so no separate falsy-`rows` case is needed here.
- [x] 1.5 In the normal (non-overflow) case, for each row index `i` in `lines`: if `lines[i] !== prevLines[i]` (true when `prevLines[i]` is `undefined`, a sentinel value such as `null`, or genuinely different content), append `\x1b[<i+1>;1H` + `lines[i]` to `bytes`; otherwise write nothing for that row.
- [x] 1.6 Keep the existing shrink-cleanup loop for the normal (non-overflow) case unchanged in shape: blank rows from `lines.length + 1` through `prevLines.length` (when the previous frame was taller), reusing the same per-row `\x1b[<row>;1H` + blank-of-width-`cols` construction it already has.
- [x] 1.7 After the diff loop (1.5) and the shrink loop (1.6), in the normal (non-overflow) case only: if `bytes` is non-empty, append one more write parking the cursor at the last row — `\x1b[<lines.length>;1H` + `lines[lines.length - 1]` — so the cursor always ends up at the same fixed position (the end of the frame's last row) regardless of which row(s) actually changed this tick (design.md Decision 8). This write MUST run unconditionally whenever `bytes` is non-empty, never skipped as an "optimization" when the last row is already in the changed set — it is not purely cosmetic: because the resize sentinel (task 2.4) can leave `prevLines.length` greater than the current `rows`, the shrink loop (1.6) can blank a row that clamps onto the same physical last row the diff loop (1.5) just wrote, and this write is what repairs that by running after it (design.md Decision 8 — see its note on why this is load-bearing, not just cosmetic). Do NOT add this when `bytes === ''` (an entirely unchanged tick must still write nothing at all — design.md Decision 5) and do NOT add it in the overflow-fallback branch (task 1.3's `CURSOR_HOME + lines.join('\n')` already ends at the last row exactly as it does today — note that if that branch's own shrink-blanking also fires, the cursor ends on a blanked row there too, same as today's pre-existing behavior; this is not a regression and needs no change).
- [x] 1.8 Return `{ bytes, lines }` (per tasks 1.4/1.5, not always the raw new-frame array) instead of `{ bytes, lineCount }`.
- [x] 1.9 Keep the `CURSOR_HOME` constant and its existing export (`module.exports` at the bottom of `watch.js`) — it is still used by the overflow-fallback path in task 1.3, and is still imported by `test/watch.test.js`. Do not remove it.
- [x] 1.10 Rewrite `buildFrame`'s own header comment (currently describing "Cursor-home + pad-to-width overwrite — never a full-screen clear" as the *only* behavior) to describe the diff path (including the cursor-park write from task 1.7) and the over-tall full-rewrite fallback, matching design.md Decisions 2, 6 and 8.

## 2. Wire the new state through `draw()`, attach, and resize

- [x] 2.1 Replace the `lastFrameLines` (number) closure variable in `watch()` with `prevFrameLines` (array), initialized to `[]`. Rewrite its declaration comment (currently describing "the previous frame's line count") to describe the new array-of-lines meaning.
- [x] 2.2 Update `draw()`'s call site: compute `const totalRows = process.stdout.rows || 0;` (reusing/renaming the existing `totalRows` local already computed for `screenRows` if present, rather than adding a second read), then `const frame = buildFrame(rendered, cols, totalRows, prevFrameLines); if (frame.bytes) process.stdout.write(frame.bytes); prevFrameLines = frame.lines;` — the `if (frame.bytes)` guard is required by design.md Decision 5 (an unchanged frame must not call `process.stdout.write` at all, not merely write zero bytes). Rewrite the comment immediately above this call site (currently describing "Cursor-home + pad-to-width overwrite, never a full-screen clear... and blank any trailing rows left stale by a frame that shrank") to describe the new diff-plus-fallback behavior.
- [x] 2.3 In `doAttach()`'s `attachAndRestore` restore callback (the second argument, `watch.js:666`), add `prevFrameLines = [];` alongside the existing `ALT_SCREEN_ENTER`/raw-mode/`running = true` restoration, so both the normal-return and throwing paths invalidate the frame cache (design.md Decision 7). Note in a comment why `[]` (not a length-preserving sentinel) is correct here specifically: entering the alternate screen genuinely clears it, so there is no stale tail to blank.
- [x] 2.4 In the `process.stdout.on('resize', ...)` handler (`watch.js:589`), immediately before the `if (running) runs = draw();` call, replace every entry of `prevFrameLines` with a sentinel value (e.g. `prevFrameLines = prevFrameLines.map(() => null);`) — this forces every row to diff as "changed" on the next redraw while preserving `prevFrameLines.length` exactly, so every resize (width change, height change, or both) forces a full repaint AND the existing shrink-cleanup loop (task 1.6) still knows how many trailing rows the pre-resize frame had (design.md Decision 3). Do NOT reset to `[]` here — that discards the length the shrink loop needs and reintroduces the stale-trailing-row regression design.md Decision 3 documents in detail (a 30→20 row resize taking a real `fleet` render from 27 to 18 lines is the concrete case this must not break). Note in the code why: a rows-only resize would otherwise leave byte-identical padded content undiffed against a terminal that has, in fact, just changed shape, and unlike attach, a resize does not clear anything.
- [x] 2.5 Confirm no other reference to the old `lastFrameLines` name or the old `{ lineCount }` shape remains in `lib/ui/watch.js`.

## 3. Tests

- [x] 3.1 Rewrite `test/watch.test.js`'s existing `buildFrame` tests for the new `(text, cols, rows, prevLines) -> { bytes, lines }` contract. This is a semantic rewrite, not a signature adjustment: the tests currently asserting `frame.bytes.startsWith(CURSOR_HOME)` and slicing `CURSOR_HOME.length` (3 bytes, `\x1b[H`) off the front of `frame.bytes` must instead account for the new row-1 prefix `\x1b[1;1H` (7 bytes) wherever a full-rewrite frame (first frame — empty `prevLines`) is being asserted on. Pass `0` for `rows` in every test that is not specifically testing overflow fallback (tasks 3.7/3.8), so those tests exercise the normal diff path and never the overflow branch. The existing growth test (`test/watch.test.js:80-82`, "a frame that grows... blanks nothing") currently asserts `doesNotMatch(grown.bytes, /\x1b\[\d+;1H/)` — under the new diff path, growth writes per-row placements, so this specific assertion must be inverted (`match`, not `doesNotMatch`), not merely left in place expecting it to still pass.
- [x] 3.2 Add a test: calling `buildFrame` twice with the second call's `prevLines` argument set to the first call's returned `.lines` unchanged (same `text`, `cols`, `rows`) produces `bytes === ''` on the second call.

- [x] 3.4 Add a test: a second call whose `text` has more lines than the first call's `prevLines` writes every new row via its own per-row cursor placement (not a single cursor-home + join).

- [x] 3.8 Add a test: a second `buildFrame` call whose OWN frame fits within `rows`, but whose `prevLines` came from a call that returned the truncated tail per task 1.4/3.7, resumes normal per-row diffing correctly against that truncated `prevLines` (i.e. it does not re-trigger the overflow fallback merely because a previous overflow happened, once `prevLines.length <= rows`).
- [x] 3.9 Add a test for the resize-invalidation mechanism itself (task 2.4's `prevFrameLines.map(() => null)`): given a `prevLines` array of some length N mapped to `null` entries, a `buildFrame` call whose new frame is shorter than N still blanks trailing rows `newLength+1..N` (proving the sentinel-mapping approach preserves length for the shrink loop, not just forces a repaint) — this is the regression design.md Decision 3 documents in detail and must not recur.
