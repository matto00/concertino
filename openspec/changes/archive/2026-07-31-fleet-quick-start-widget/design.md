## Context

CON-40's ticket body itself poses three design questions rather than a spec. This document answers each explicitly, against the existing fleet/launch-pad/queue machinery (`lib/ui/screens/fleet.js`, `lib/ui/screens/launchpad.js`, `lib/ui/queue.js`, `lib/ui/watch.js`), rather than guessing.

`fleet.js` already carries one precedent for "a section whose rows are not runs and must never perturb the run row-index space": `QUEUED` (CON-28/CON-29/CON-39). It renders as an `unselectable: true` section with its own independent focus cursor (`focus: 'queue'`, `queueFocus`), entered via digit-jump (CON-39) or its own toggle, with `j`/`k`/`f`/Escape reinterpreted while that focus is active. QUICK START reuses this exact shape rather than inventing a second one.

## Goals / Non-Goals

**Goals:**
- A fast, in-fleet path to start the single most urgent ticket, without opening the launch pad.
- Reuse `queue.createQueue`/`queue.tick` as the only admission path into a running batch — no second queuing mechanism.
- Never compete for fleet's already-tight vertical budget by default — hidden unless explicitly opened.
- Never perturb the row-index space `state.selected`/`runs[state.selected]` depends on (the same invariant `QUEUED` already guarantees).

**Non-Goals:**
- No per-epic scoping for this widget — top priority is flattened across all epics, per the ticket's own resolution of that question.
- No new config surface (no `quickStart.count` or similar) — a fixed constant, matching `fleet.js`'s own `MAX_FINISHED = 5` precedent.
- No changes to the launch pad's own UI or to `QUEUED`'s rendering/persistence contract (`fleet-queue-visibility` is unmodified).
- The sibling ticket (launch pad IN QUEUE status / explicit add-to-queue action) is out of scope here; this change only introduces the one shared primitive (`queue.enqueueOne`) it names as something the two should share, so that ticket can build on it later rather than inventing its own.

## Decisions

### Decision 1: Hidden by default, toggled on demand — a dedicated key, not a persistent section

Per the ticket's own framing ("shortcut in front of, not a replacement for, the launch pad" + fleet's vertical budget already being tightly accounted for per CON-28), QUICK START is **not** one of the always-rendered sections (`NEEDS YOU`/`RUNNING`/`FAILED`/`DONE`). It is controlled by a new boolean, `quickStartVisible` (state, default `false`), toggled by a new key, capital `Q` — the one letter unclaimed anywhere in `fleet.js`'s `handleKey` (digits `1`-`9`, `j`/`k` + arrow aliases, Enter, `l`/right-arrow, `n`, `N`, `q`/Ctrl-C, `c` — `CONFIRM_RESTORED_QUEUE_KEY` — and, only within queue-focus, `f`/Escape).

**Alternative considered:** always render it, like `QUEUED`. Rejected — `QUEUED` is *evidence of an action the operator already took* (a batch they already confirmed) and must never be hideable; QUICK START is a *suggestion*, and per the ticket's own design question, screen real estate is the resource CON-28 was careful about. An always-on sixth section for a suggestion is exactly the accretion the ticket asks to avoid.

### Decision 2: Section placement — after RUNNING, before QUEUED

When `quickStartVisible`, `buildSections()` inserts a `QUICK START` entry between `RUNNING` and the (already-conditional) `QUEUED` entry: `NEEDS YOU` (attention) → `RUNNING` (active work) → `QUICK START` (what to start next, if opened) → `QUEUED` (already-committed-but-not-yet-running) → `FAILED` → `DONE`. This reads top-to-bottom as "what's wrong" → "what's happening" → "what you could start" → "what's about to start" → history, and keeps `QUEUED`'s own position (after RUNNING, before FAILED, per `fleet-queue-visibility`) valid whether or not QUICK START is currently shown.

### Decision 3: Row-index safety — `unselectable: true` + its own focus cursor, exactly like QUEUED

QUICK START rows are tickets, not runs — they must never consume a slot in the flat `runs[]`-indexed selection space `watch.js` resolves `state.selected` against (the same invariant `fleet-queue-visibility`'s "Inserting QUEUED never perturbs the row-index" requirement already states for `QUEUED`). The section is therefore built with `unselectable: true`, `linesPerRow: 1`, and its own independent cursor: `focus: 'quickstart'` (a third value alongside today's `'runs'`/`'queue'`), `quickStartFocus` (an index into the rendered ticket list). Entered via digit-jump (extends `sectionJumpTargets()`, itself generic — no change needed to `fleet-section-jump`'s own requirements) emitting `focus-quickstart`, or directly by the `Q` toggle when it *opens* the panel (toggling on both shows and focuses it in one keypress, since the point is "get to the action fast"). While focused: `j`/`k` move `quickStartFocus` (clamped to the rendered list's bounds), `a` emits `quickstart-add` unconditionally (see the note on this below), bare Escape emits `exit-quickstart-focus` (returns `focus` to `'runs'`, panel stays **visible** — only `Q` hides it). `Q` while already in quickstart-focus hides the panel outright (`quickStartVisible: false`, `focus: 'runs'`) — a single key both opens+focuses and, pressed again, fully closes, mirroring the toggle's own symmetry.

**Alternative considered:** fold QUICK START rows into the ordinary `selected` index space (selectable like a run row), with a distinct key for "add" scoped to when a QUICK START row is selected. Rejected — this is exactly the same trap `QUEUED` already hit and solved: a ticket row has no run, no phase, no gates, no elapsed time, so admitting it into the same index space either fabricates fields for it or forces every downstream `runs[selected]` consumer (drilldown, attach, kill/restart) to special-case a shape that was never a run. Reusing `QUEUED`'s already-solved pattern is strictly simpler than re-deriving it.

**`handleKey` has no ticket data to gate `a` on, and must not pretend otherwise.** `router.handleKey(key, currentState())` (see `router.js`) is called with `state` only, never the render-time `opts` — `queuedTitles`/`quickStartTickets` are `opts`-only fields, never part of `currentState()` (this is deliberate: see Decision 4 below on why the eligible list is computed in `draw()`, not stored in `state`). That means `fleet.js`'s `handleKey`, unlike `buildHeadTail`/`renderFleet` which do receive `opts`, cannot see the eligible ticket list at all, and so cannot mirror `focus === 'queue'`'s `f`-branch pattern (which resolves `state.queueState.pending[queueFocus]` — `queueState` genuinely lives in `state`) to refuse `a` when nothing is highlighted. `handleKey`'s `focus === 'quickstart'` branch therefore emits `{ type: 'quickstart-add', index: quickStartFocus }` **unconditionally** whenever that focus is active and `a` is pressed, with no highlighted-ticket check — the same "no data, no gate" constraint the digit-jump branch already accepts for QUICK START's own group length (see Decision 4). The single point that resolves `index` against an actual ticket id — and no-ops if it doesn't resolve to one (an empty or since-shrunk list) — is `watch.js`'s `quickstart-add` handler (Decision 5), which re-derives the eligible list fresh at handling time and already has to do exactly this resolution regardless.

**Discriminating QUEUED from QUICK START at the digit-jump site.** `handleKey`'s existing digit-jump branch collapses *any* `unselectable` section to `{ type: 'focus-queue', index: 0 }` — correct today because `QUEUED` is the only `unselectable` section that can exist. With QUICK START added, a second `unselectable` section can be on screen at the same time, so this collapse needs a discriminator. `buildSections()` therefore tags every section object with a stable `kind` field (`'needs-you' | 'running' | 'quickstart' | 'queued' | 'failed' | 'done'` — distinct from the existing `statusKey`, which QUICK START and QUEUED do not otherwise need one of, but `kind` is added uniformly to every section for symmetry rather than as a special case). The digit-jump branch reads `target.section.kind` and emits `focus-quickstart` for `'quickstart'`, `focus-queue` for `'queued'`, `jump` (as today) for everything else. Matching on `s.title` was considered and rejected — `QUEUED`'s title is a dynamic string carrying a live pending count (`QUEUED (3, running 1 at a time)`), not a stable key.

### Decision 4: Eligible-ticket list — computed in `watch.js`'s `draw()`, not inside the screen

Mirrors `queuedTitles`'s existing pattern (built fresh every `draw()` call from `cache.read(root)`, passed in as a plain `opts` field — `fleet-queue-visibility`'s own design note). When `quickStartVisible`, `draw()` computes:

```
eligible = launchpadScreen
  .sortByPriority(cache.read(root).tickets || [])
  .filter(t => launchpadScreen.isSelectable(t, runs))
  .filter(t => !inQueue(t.identifier))      // see below
  .slice(0, QUICK_START_COUNT)               // QUICK_START_COUNT = 5, fleet.js-local const
```

`inQueue(id)` checks `queueState && (queueState.pending.includes(id) || queueState.inFlight.has(id))` — a ticket already on the active queue (whether added via this widget or the full launch pad) must not be re-offered, exactly as `isSelectable` already excludes a ticket with a *live run*. Without this second check, a ticket added moments ago (still `pending`, no run object yet) would still show up and `a` could be pressed on it again, silently duplicating it in `queue.pending` (guarded against separately by `enqueueOne`'s own dedupe — see Decision 5 — but excluding it from the visible list is the more honest fix, matching the project's "don't offer an action that would be a no-op" discipline already used by `isSelectable` itself).

A cold cache (`cache.isCold`, nothing fetched yet) or an eligible list emptied entirely by filtering renders the section anyway (when `quickStartVisible`) with a one-line hint (`no tickets cached yet — press N to fetch`, or `nothing left to quick-start` when the cache has tickets but all are filtered out) instead of disappearing — an empty QUICK START while explicitly toggled on is itself informative, the same "absent data must not render as silence" discipline `renderQueuedRow`'s own header comment and the launch pad's cold-cache branch already apply. This is the one deliberate divergence from `buildSections`' existing "only non-empty groups render" convention (which is correct for `RUNNING`/`FAILED`/`DONE`, whose emptiness is genuinely uninformative).

**Concrete mechanism — this divergence touches several existing call sites, all named explicitly here so `tasks.md` does not leave any implicit:**

1. `buildSections()` sets `forceRender: true` and `emptyHint: <string>` on the QUICK START section object whenever `quickStartVisible` is true, regardless of `group.length` (`emptyHint` is `'no tickets cached yet — press N to fetch'` when the cache is cold, otherwise `'nothing left to quick-start'` when `group.length === 0`; unset/unused otherwise). No other section ever sets `forceRender`.
2. `visibleWindow`'s `sectionHeight(s, w)` currently opens with `if (!s.group.length) return 0;` — a section with nothing to show costs nothing. This becomes `if (!s.group.length) return s.forceRender ? 3 : 0;` — a forced-render empty section costs exactly one hint content line plus its 2-row border (`1 + 2`, matching the `contentLines.length + 2` a populated box costs elsewhere in this same file), so it still participates in the height-budget trim loop truthfully rather than being invisible to it.
3. `renderFleet`'s per-section loop currently opens with `if (!s.group.length) return;` — the section is skipped outright. This becomes: when `!s.group.length`, render nothing (`return`) **unless** `s.forceRender`, in which case render a normal bordered box (the same `layout.box`/`layout.degrade` path every other populated section already takes) whose sole content line is `s.emptyHint`.

4. `sectionJumpTargets()` filters `buildSections(...)`'s output to `s.group.length > 0` before numbering digits — a fourth call site, easy to miss, that would otherwise disagree with the first three: a `forceRender`-flagged, zero-eligible QUICK START *is* rendered on screen (per point 3) but has `group.length === 0`, so this filter must become `s.group.length > 0 || s.forceRender`, or a visibly-rendered empty QUICK START would consume no digit at all while a populated one below it silently shifts up — the exact "digit numbering disagrees with what's on screen" defect `fleet-section-jump`'s own header comment treats as a correctness bug.

**None of `buildSections`' three call sites forward `opts` today — all three need an explicit fix, not just the one already named.** `buildSections(buckets, queueState, opts)` (point 1 above) reads `quickStartVisible`/the eligible list off a third `opts` argument. Ground truth in `fleet.js` today: `visibleWindow(runs, opts)`'s own internal call is `buildSections(buckets, queueState)` (line 375 — two arguments, `opts` NOT forwarded despite `visibleWindow` itself receiving a real `opts` parameter); `renderFleet(runs, opts)`'s own internal call is `buildSections(bucketRuns(runs), queueState)` (line 529 — same gap, same story); and `sectionJumpTargets(runs, queueState)` has no `opts` parameter at all, called from exactly one place, `handleKey`'s digit-jump branch, where `handleKey(key, state)` itself is called by `router.handleKey(key, currentState())` with **no `opts`**, ever (the same constraint Decision 3's "handleKey has no ticket data" note already establishes for the `a` key). All three gaps must be closed, or QUICK START silently never appears via whichever call site is left unfixed — even while correctly toggled/focused via the others:

1. `visibleWindow`'s internal call becomes `buildSections(buckets, queueState, opts)` — trivial, `opts` is already in scope as `visibleWindow`'s own parameter.
2. `renderFleet`'s internal call becomes `buildSections(bucketRuns(runs), queueState, opts)` — same, `opts` is already `renderFleet`'s own parameter. Skipping this one specifically means the QUICK START section is never built inside `renderFleet` at all, so it is never drawn on screen regardless of `quickStartVisible`/focus/digit-jump all being individually correct elsewhere — the single most load-bearing of these three fixes.
3. `sectionJumpTargets` grows a third parameter, `quickStartVisible` (the boolean alone — not the ticket list, which `handleKey` has no access to either, and does not need, since only inclusion/exclusion of the section is being decided here), which it forwards into `buildSections`'s `opts` argument as `{ quickStartVisible }`. This also requires: (a) `quickStartVisible` added to `currentState()` (alongside `quickStartFocus`, per Decision 3's `focus`/`quickStartFocus` state) so it is reachable as `state.quickStartVisible` inside `handleKey`; (b) `handleKey`'s digit-jump call site changed from `sectionJumpTargets(runs, queueState)` to `sectionJumpTargets(runs, queueState, state.quickStartVisible)`.

5. **`renderFleet`'s per-row content loop is written specifically for QUEUED and must be told, explicitly, to branch for QUICK START.** Today, the loop's only discriminator for a populated (non-empty-`group`) `unselectable` section is `s.unselectable` itself: it assumes `s.group[k]` is a ticket-id string (true of `QUEUED`'s `group: queueState.pending`) and calls `renderQueuedRow(ticket, k + 1, title, innerCols, { focused: focus === 'queue' && queueFocus === k, ... })`, looking the title up via `queuedTitles.get(ticket)`. QUICK START's `group` is `opts.quickStartTickets` — full ticket **objects** (`{ identifier, title, priority, ... }`, matching `launchpad.js`'s `sortByPriority`/`isSelectable`/`ticketRow` shape), not id strings. Calling `renderQueuedRow` on a ticket object would be structurally wrong (`queuedTitles.get(ticketObject)` never matches; the object itself is passed where an id string is expected). This loop must therefore branch on `s.kind` (the same field point 1/Decision 3 already add to every section), not merely `s.unselectable`: `kind === 'queued'` routes to the existing `renderQueuedRow` path unchanged; `kind === 'quickstart'` routes to a new row renderer operating directly on the ticket object (no `queuedTitles` lookup needed — the object already carries `.title`), passed `focused: focus === 'quickstart' && quickStartFocus === k` so the highlighted row under `a` gets the same kind of visual marker `renderQueuedRow`'s own `opts.focused` already gives QUEUED's focused row. The row renderer itself (priority label + identifier + title, per Decision 4's eligible-list shape) therefore takes a `focused` parameter from the start, not as a later addition.
6. **The QUICK START section object needs an explicit `cap`, exactly like every other section.** `visibleWindow`'s unselectable-section branch computes `shown = Math.min(groupLen, s.cap)` — every section `buildSections()` already builds names a real `cap` (`Infinity` for `NEEDS YOU`/`RUNNING`, `MAX_FINISHED` for `QUEUED`/`FAILED`/`DONE`). QUICK START's section object sets `cap: QUICK_START_COUNT` — the eligible list is already capped to this length before it ever reaches `buildSections` (Decision 4's `eligible` computation), so this is consistent, not a second independent limit. Leaving `cap` unset would make `Math.min(groupLen, undefined)` evaluate to `NaN`, silently breaking `shown` and the height arithmetic that depends on it — an omission failing quietly rather than loudly, exactly the kind of gap this design document exists to close before implementation rather than during it.

Neither existing call site's behavior changes for `RUNNING`/`FAILED`/`DONE`/`NEEDS YOU` — `forceRender` is `undefined` (falsy) for all of them, so `!s.group.length` alone still governs their existing "skip when empty" behavior exactly as today, and their row-dispatch (`kind` not `'queued'`/`'quickstart'`) and `cap` values are unchanged. `QUEUED` also never sets `forceRender` — an empty `QUEUED` correctly continues to not render at all, per `fleet-queue-visibility`'s own "no queue, no section" requirement, which this change does not touch.

### Decision 5: Add-to-queue — `queue.enqueueOne`, a new small primitive, not a hand-rolled push in `watch.js`

`queue.js` gains one function:

```js
function enqueueOne(queue, ticket) {
  if (!queue) return null; // caller creates a fresh queue via createQueue instead
  if (queue.pending.includes(ticket) || queue.inFlight.has(ticket)) return queue; // no-op, already accounted for
  return Object.assign({}, queue, { pending: queue.pending.concat([ticket]) });
}
```

`watch.js`'s `quickstart-add` handler receives `{ type: 'quickstart-add', index }` (per Decision 3, `handleKey` emits this unconditionally with no ticket-existence check). The handler is therefore the one place that actually resolves `index` to a ticket: it re-derives the eligible list fresh (the identical computation `draw()` performs — see Decision 4 — against the current `cache`/`runs`/`queueState`, not a value cached from a previous frame), and no-ops entirely (`return true` with no state change) if `index` is out of bounds for that freshly-derived list — covering both "nothing was ever eligible" and "the list shrank since this frame was drawn" (e.g. the highlighted ticket started running by hand in the interim). Once resolved to a real ticket id:
- No active queue (`queueState` is `null`): `queueState = queue.createQueue([ticket], 1, launchCommand); queueSessionId = crypto.randomUUID();` — reusing the exact `launchCommand` `const` already computed once, at `watch()`-function scope (not literally module-scope — `watch()` runs once per process, so this is effectively a singleton in practice, but the precise term is function-scope), the plain `n` prompt and restart already use, so a quick-started ticket picks up the same default harness/agent-merge-config-default behaviour as any other default-path launch. `maxConcurrent: 1` — a lone ticket has no concurrency to speak of, and keeps any *later* quickstart-add appended to this same queue sequential unless the operator separately opens the full launch pad.
- An active queue exists (confirmed or not — `enqueueOne` does not gate on `confirmed`; appending to `pending` is safe either way, since an unconfirmed restored queue's `pending` array is exactly what the operator is being shown and asked to confirm, and picking up one more ticket into it does not change that): `queueState = queue.enqueueOne(queueState, ticket) || queueState`.

Persistence (`queueCache.write`) needs no new call site — it already runs every `draw()` cycle inside the existing `queue.shouldTick(queueState)` branch, which fires on the very next poll regardless of *why* `queueState.pending` changed.

**Alternative considered:** open the launch plan review screen pre-populated with the one ticket, requiring a second Enter to confirm. Rejected — this is exactly the "leaving the fleet view entirely" detour the ticket exists to avoid; the whole point of the widget is skipping that review step for the common case, trusting the same defaults the plain `n` prompt already trusts unreviewed.

This is also the shared primitive the proposal's Impact section flags for the sibling ticket (launch pad IN QUEUE status / explicit add-to-queue action) to build on, rather than that ticket inventing its own append-to-queue logic independently.

### Decision 6: `QUICK_START_COUNT = 5`, no new config

The ticket's own language ("next 3-5 tickets") is a range, not a tunable; a fixed constant (`fleet.js`-local, alongside the existing `MAX_FINISHED = 5`) is the minimal-plumbing choice consistent with the proposal's own framing ("a shortcut UI in front of existing plumbing, not new plumbing"). A config knob can be added later if this proves too rigid — no evidence in the ticket that it needs to be tunable from day one.

## Risks / Trade-offs

- **[Risk]** A third `focus` value (`'quickstart'`, alongside `'runs'`/`'queue'`) adds another branch every `focus === 'queue'`-style check in `handleKey` must not silently mishandle. → **Mitigation:** every existing `focus === 'queue'` branch in `fleet.js` is reviewed and given an explicit `focus === 'quickstart'` sibling (never an `else` that assumes only two values); a unit test asserts `j`/`k`/Enter/`l`/`n`/`N` are all suppressed (or correctly reinterpreted) while `focus === 'quickstart'`, mirroring the existing queue-focus test coverage.
- **[Risk]** `enqueueOne`'s dedupe (`pending.includes` / `inFlight.has`) is an O(n) scan per call — negligible at queue sizes this project ever produces (single-digit batches), so no risk in practice, but called out since `tick()`'s own admission loop is O(n) too and nobody has needed to optimize it.
- **[Trade-off]** Appending to an *existing* queue via `enqueueOne` inherits that queue's `maxConcurrent`/`launchCommand` rather than the operator getting to choose per-add — accepted, since re-litigating those per ticket would reintroduce the review-screen detour Decision 5 explicitly avoids; an operator who wants different settings uses the full launch pad instead.
- **[Trade-off]** QUICK START's `eligible` list is recomputed (sort + two filters) every `draw()` call while visible, same cost class as `queuedTitles`'s existing per-draw cache read — accepted as consistent with the rest of this file's "cheap enough to recompute every frame" convention, not something this change needs to introduce caching for.

## Migration Plan

Additive only — no persisted state shape changes (`quickStartVisible`/`quickStartFocus` are in-memory `watch.js` state, not written to `queue.json` or any cache file), no config schema changes. Ships and reverts as a single self-contained commit; no rollback steps beyond reverting the change.

## Open Questions

None outstanding — the ticket's three named design questions are resolved by Decisions 1, 6 (epic-flattening, per Non-Goals), and 5 respectively.
