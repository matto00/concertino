## 1. `queue.js`: shared add-to-queue primitive

- [x] 1.1 Add `enqueueOne(queue, ticket)` — appends `ticket` to `queue.pending` if not already present in `pending` or `inFlight`; returns `null` when `queue` is falsy (caller creates fresh via `createQueue` instead); returns the same `queue` unchanged (no-op) when the ticket is already accounted for.
- [x] 1.2 Export `enqueueOne` from `lib/ui/queue.js`'s `module.exports`.

## 2. `fleet.js`: QUICK START section — build, render, height budget

- [x] 2.1 Add `QUICK_START_COUNT = 5` constant, alongside the existing `MAX_FINISHED`.
- [x] 2.2 Add `QUICK_START_TOGGLE_KEY = 'Q'` constant (header comment naming why it doesn't collide, matching `CONFIRM_RESTORED_QUEUE_KEY`'s existing precedent).
- [x] 2.3 Extend `buildSections(buckets, queueState, opts)` (or add a parallel helper called alongside it, whichever keeps `visibleWindow`/`renderFleet`/`sectionJumpTargets` sharing one implementation) to insert a `QUICK START` entry between `RUNNING` and the conditional `QUEUED` entry, `unselectable: true`, `linesPerRow: 1`, `cap: QUICK_START_COUNT` (design.md Decision 4, mechanism step 6 — every other section already names a real `cap`; leaving it unset makes `visibleWindow`'s `Math.min(groupLen, s.cap)` evaluate to `NaN`), included whenever `quickStartVisible` is true regardless of the eligible-ticket count (per design.md Decision 4's deliberate divergence from "only non-empty groups render"). Also add a stable `kind` field to every section object this function builds (`'needs-you' | 'running' | 'quickstart' | 'queued' | 'failed' | 'done'`, per design.md Decision 3's digit-jump discriminator note) — not just QUICK START/QUEUED, so both the digit-jump branch (3.3) and the row-dispatch branch (2.7) have one uniform field to read regardless of section type.
- [x] 2.4 Add a row renderer for a QUICK START ticket taking a full ticket **object** (not an id string — `s.group` for this section is `opts.quickStartTickets`, an array of ticket objects, unlike QUEUED's array of id strings) plus a `focused` boolean, rendering priority label, identifier, title (truncated to width), mirroring `ticketRow`'s layout conventions from `launchpad.js` (reuse `launchpadScreen.priorityLabel`, do not reimplement) and `renderQueuedRow`'s `opts.focused` convention for how a highlighted row is visually marked (design.md Decision 4, mechanism step 5).
- [x] 2.5 On the QUICK START section object, set `forceRender: true` and `emptyHint: <string>` whenever `quickStartVisible` is true and `group.length === 0` — `emptyHint` is the cold-cache hint (`'no tickets cached yet — press N to fetch'`) when the ticket cache has never been fetched, else the fully-filtered hint (`'nothing left to quick-start'`) (design.md Decision 4 / spec's "empty or cold" requirement). No other section ever sets `forceRender`.
  **Known open gap, accepted for implementation-time resolution (design gate round 5 REFUTEd on this; human accepted proceeding without a fully-specced fix — see `skeptic-design-5.md`):** `buildSections()` is a pure function with no access to the `cache` module, so it cannot itself distinguish "cache never fetched" from "cache fetched but every ticket filtered out" — both currently produce an empty `group`. The executor must design and wire the missing data path (e.g. a new opts field such as `quickStartCold`, computed once in `watch.js`'s `draw()` via `cache.isCold(cache.read(root))`, gated on `quickStartVisible`, added to the object literal at the `router.render(currentState(), {...})` call site in `watch.js`, and read here to pick `emptyHint`'s text) as part of real implementation, consistent with every other data-flow decision already made in this document (Decision 4's other opts fields, `quickStartTickets`/`quickStartVisible`/`quickStartFocus`, follow the identical pattern). Only `renderFleet`'s own `buildSections` call actually needs this field — `visibleWindow` only needs `forceRender` for the fixed height cost, `sectionJumpTargets` only needs `quickStartVisible` for jump-numbering, neither reads `emptyHint`'s text.
- [x] 2.6 Change `visibleWindow`'s `sectionHeight(s, w)` from `if (!s.group.length) return 0;` to `if (!s.group.length) return s.forceRender ? 3 : 0;` (design.md Decision 4, mechanism step 2) — verify this does not change costed height for any section other than a `forceRender`-flagged, empty QUICK START.
- [x] 2.7 Change `renderFleet`'s per-section loop from unconditionally skipping when `!s.group.length` to: skip (as today) unless `s.forceRender`, in which case render the normal bordered box (`layout.box`/`layout.degrade` path, same as any populated section) with `s.emptyHint` as its sole content line (design.md Decision 4, mechanism step 3). For the populated (non-empty `group`) case, change the loop's per-row dispatch from branching on `s.unselectable` alone to branching on `s.kind` (added in 2.3): `kind === 'queued'` keeps calling the existing `renderQueuedRow` path unchanged (ticket-id strings, `queuedTitles` lookup, `focused: focus === 'queue' && queueFocus === k`); `kind === 'quickstart'` calls the new row renderer from 2.4 directly on the ticket object (`s.group[k]`, no `queuedTitles` lookup — the object carries `.title` itself), passed `focused: focus === 'quickstart' && quickStartFocus === k` (design.md Decision 4, mechanism step 5 — QUICK START's `group` holds ticket objects, not id strings, so reusing `renderQueuedRow` as-is would be structurally wrong, not just cosmetically).
- [x] 2.8 Update `sectionJumpTargets`' filter from `s.group.length > 0` to `s.group.length > 0 || s.forceRender` (design.md Decision 4, mechanism step 4) — a `forceRender`-flagged, zero-eligible QUICK START is still visibly rendered and must still consume a digit, or digit numbering would disagree with what's on screen.
- [x] 2.9 Give `sectionJumpTargets(runs, queueState)` a third parameter, `quickStartVisible`, and forward it into `buildSections`'s `opts` argument as `{ quickStartVisible }` (design.md Decision 4's "`sectionJumpTargets` cannot see `quickStartVisible`" note). Without this, `sectionJumpTargets`'s own call to `buildSections` (inside itself, distinct from `visibleWindow`'s and `renderFleet`'s calls) never learns `quickStartVisible` and silently never builds the QUICK START section for jump-numbering purposes, even while it is genuinely visible via the other two call sites.
- [x] 2.10 Change `visibleWindow`'s own internal call from `buildSections(buckets, queueState)` (`fleet.js:375`) to `buildSections(buckets, queueState, opts)` — `opts` is already `visibleWindow`'s own parameter, just not forwarded today (design.md Decision 4's corrected "none of `buildSections`' three call sites forward `opts`" note, point 1). Without this, `visibleWindow`'s own height-budget arithmetic never sizes a QUICK START entry into the terminal-row budget, regardless of `quickStartVisible`.
- [x] 2.11 Change `renderFleet`'s own internal call from `buildSections(bucketRuns(runs), queueState)` (`fleet.js:529`) to `buildSections(bucketRuns(runs), queueState, opts)` — `opts` is already `renderFleet`'s own parameter, just not forwarded today (design.md Decision 4, point 2 — the single most load-bearing of these three fixes: skipping it means QUICK START is never drawn on screen at all, even though `Q`/digit-jump/focus would all work correctly around an invisible section).

## 3. `fleet.js`: QUICK START focus and key handling

- [x] 3.1 Extend the `focus` state contract to a third value, `'quickstart'`, alongside `'runs'`/`'queue'`.
- [x] 3.2 In `handleKey`: pressing `Q` with `quickStartVisible` false emits an action that sets `quickStartVisible: true` and `focus: 'quickstart'` in one step; pressing `Q` while `focus === 'quickstart'` emits an action that sets `quickStartVisible: false` and `focus: 'runs'`.
- [x] 3.3 In `handleKey`'s digit-jump branch, change the `sectionJumpTargets(runs, queueState)` call to `sectionJumpTargets(runs, queueState, state.quickStartVisible)` (per 2.9 and 4.1's new `state.quickStartVisible` field — `handleKey` has no `opts`, only `state`, so this is the only way it can learn whether QUICK START is currently shown). Then replace the blanket `if (target.section.unselectable) return { type: 'focus-queue', index: 0 };` with a switch on `target.section.kind` (added in 2.3): `'queued'` → `focus-queue`, `'quickstart'` → `focus-quickstart` (index 0), everything else → `jump` (as today) — without altering `state.selected`/`state.scrollOffset` for either focus case.
- [x] 3.4 Add a `focus === 'quickstart'` branch (sibling to the existing `focus === 'queue'` branch, not folded into it): `j`/`k`/arrow aliases → `move-quickstart-focus`; `a` → `{ type: 'quickstart-add', index: quickStartFocus }` emitted **unconditionally** whenever this focus is active — `handleKey` has no access to the eligible ticket list (it is `opts`-only, never part of `currentState()`; see design.md Decision 3's "handleKey has no ticket data" note), so it cannot check whether a ticket is actually highlighted the way the `queue`-focus `f` branch checks `queueState.pending[queueFocus]`. Resolution and the no-op-if-nothing-resolves check both happen in `watch.js`'s `quickstart-add` handler (4.4) instead. Bare Escape → `exit-quickstart-focus`; `Enter`/`l`/right-arrow/`n`/`N` → suppressed (return `null`), matching queue-focus's existing suppression list.
- [x] 3.5 Verify (and adjust if needed) that `forceStartConfirm`/`quitConfirm` gating still short-circuits before any of the above, unchanged — QUICK START must never be reachable while either confirmation gate is open.
- [x] 3.6 Update the footer hints line (`buildHeadTail`) to advertise `Q quick start` only when it does something this frame (unconditionally bindable — it's a toggle — so this can simply always show, matching `n`/`N`'s own unconditional hints).

## 4. `watch.js`: state, per-draw eligible-ticket list, and the `quickstart-add` action

- [x] 4.1 Add `quickStartVisible` (default `false`) and `quickStartFocus` (default `0`) to `watch.js`'s local state, and add both to `currentState()` (alongside `focus`/`queueFocus`) so they are reachable as `state.quickStartVisible`/`state.quickStartFocus` inside `handleKey` (3.3/3.4 both depend on this — `handleKey` only ever receives `state`, never `opts`).
- [x] 4.2 In `draw()`, when `quickStartVisible` is true, compute the eligible ticket list once per call: `cache.read(root).tickets` → `launchpadScreen.sortByPriority` → filter `launchpadScreen.isSelectable(t, runs)` → filter not already in `queueState.pending`/`queueState.inFlight` → `.slice(0, QUICK_START_COUNT)`. Pass it to the fleet screen as a new `opts` field (e.g. `quickStartTickets`), alongside `quickStartVisible`/`quickStartFocus`, mirroring how `queuedTitles` is threaded today — add these to the same object literal at the `router.render(currentState(), {...})` call site `queuedTitles` is already on. Also compute and thread a cache-coldness field (e.g. `quickStartCold: cache.isCold(cache.read(root))`) at this same call site — needed by task 2.5's `emptyHint` selection (see that task's "Known open gap" note; this was accepted as an implementation-time detail rather than fully specced at design time).
- [x] 4.3 Handle `toggle-quickstart` / `focus-quickstart` / `move-quickstart-focus` / `exit-quickstart-focus` actions in the action switch: update `quickStartVisible`/`focus`/`quickStartFocus` per design.md Decision 1/3 — no queue/tmux side effects for any of these four.
- [x] 4.4 Handle `quickstart-add`: `action.index` arrives unresolved (per 3.4, `handleKey` emits it unconditionally with no ticket check) — re-derive the eligible list fresh here, from the current `cache`/`runs`/`queueState` (not a stale value from a previous `draw()` call, matching how `open-launchplan`/`confirm-launch` re-derive against the latest `runs` at their own entry points), and no-op (`return true`, no state change) if `action.index` is out of bounds for that freshly-derived list. Once resolved to a real ticket id: if `queueState` is absent, `queueState = queue.createQueue([ticket], 1, launchCommand); queueSessionId = crypto.randomUUID();`; if `queueState` is present, `queueState = queue.enqueueOne(queueState, ticket) || queueState;`. No direct `submitTicket` call here — the existing `queue.tick()` call site in `draw()` (already gated by `queue.shouldTick`) performs the actual launch and persistence write on the next poll, unchanged.
- [x] 4.5 Clamp `quickStartFocus` defensively wherever the eligible list can shrink out from under it (a ticket added, or one that started running by hand) — same clamping discipline `move-queue-focus`/`queueFocus` already applies.

## 5. Tests

- [x] 5.1 `fleet.js` unit tests: QUICK START section appears only when `quickStartVisible`; positioned between RUNNING and QUEUED; cold-cache hint vs. fully-filtered hint render distinctly (via `forceRender`/`emptyHint`, 2.5/2.7); `sectionHeight` costs a `forceRender`-empty QUICK START exactly 3 rows and an absent/hidden one 0 (2.6); `sectionJumpTargets` includes a `forceRender`-empty QUICK START (2.8); a populated QUICK START row renders via the new ticket-object row renderer (not `renderQueuedRow`) with the correct `focused` row under `quickStartFocus`, while a populated QUEUED row still renders via the unchanged `renderQueuedRow` path in the same test suite (2.7); a populated QUICK START section's `shown`/height are computed correctly with `cap: QUICK_START_COUNT` set (not `NaN`, 2.3); **`renderFleet(runs, { ...opts, quickStartVisible: true, quickStartTickets: [...] })`'s own returned string actually contains a rendered QUICK START box/hint (not just that `sectionJumpTargets` or `visibleWindow` account for it) — this pins down 2.10/2.11's fix at the one call site (`renderFleet`'s own internal `buildSections` call) whose omission would otherwise leave the section entirely undrawn despite every other piece being individually correct**; row-index space unaffected by a visible QUICK START section (mirroring `fleet-queue-visibility`'s own existing row-index tests); height-budget trimming includes QUICK START like any other non-pinned section.
- [x] 5.2 `fleet.js` key-handling unit tests: `Q` toggles open+focus / closes as specified; digit-jump correctly discriminates `kind: 'quickstart'` vs `kind: 'queued'` vs an ordinary runs-backed section (3.3); a digit-jump against `state` with `quickStartVisible: true` actually reaches QUICK START (i.e. `sectionJumpTargets(runs, queueState, state.quickStartVisible)` — not the old two-argument call — is what `handleKey` invokes, per 2.9/3.3) and, conversely, `quickStartVisible: false` means it is correctly absent from jump targets even though `renderFleet` was never involved in this test; `j`/`k` move `quickStartFocus` clamped to bounds; `a` emits `{ type: 'quickstart-add', index: quickStartFocus }` unconditionally while focused, even when the eligible list is empty (3.4 — `handleKey` performs no existence check); Escape exits focus without hiding the section; Enter/`l`/`n`/`N` are no-ops while focused on QUICK START.
- [x] 5.3 `queue.js` unit tests for `enqueueOne` (see 1.3).
- [x] 5.4 `watch.js` integration-style tests (matching this file's existing test patterns for `confirm-launch`/`open-launchplan`): `quickstart-add` with no active queue creates a single-ticket `maxConcurrent: 1` queue using the default launch command; `quickstart-add` with an active queue appends via `enqueueOne` and preserves that queue's `maxConcurrent`/`launchCommand`; adding an already-queued ticket is a no-op; an out-of-bounds `action.index` (empty or shrunk eligible list) is a no-op that leaves `queueState` unchanged (4.4); the eligible list excludes tickets already `pending`/`inFlight` as well as already-live tickets.
