## Why

An escalation today is dashboard-first, chat-on-timeout-only: `emit-event.sh escalation --await` blocks polling `answer.json` for up to `escalationTimeoutMinutes`, and only presents the question in the raising agent's own transcript after that wait fails. Worse, in the default (non-inline) `/concertino-deliver` topology, `concertino-orchestrator` runs as a Claude Code subagent, so its blocking `--await` call is invisible to the parent chat session until the *entire orchestrator turn* returns — an escalation raised deep in a run cannot reach the human's real chat window while it is still open, no matter how long the human waits there. A real incident (CON-71, 2026-08-05, cited in the ticket) shows the cost: a dashboard-answered `fold-in` decision never reached chat, and the top-level session — seeing only the timeout-fallback path from an earlier escalation — wrongly concluded the answer had been fabricated and ordered a revert of correct work.

## What Changes

- **Immediate chat presentation.** The raising agent posts the escalation's question/options/context into its own transcript at raise time, before blocking — not only after a timeout. This alone closes the gap whenever the raiser already owns the live chat channel (an `--inline` run, or the top-level `/concertino-deliver` session itself).
- **New non-blocking raise mode.** `scripts/concertino/emit-event.sh escalation --raise-only` writes `escalation.raised` (full context-handling/truncation/persist-evidence behavior, identical to today's `--await` write path) and returns immediately with exit 0, printing nothing to wait on — no polling loop.
- **Bubble-up when the orchestrator is a subagent.** When `concertino-orchestrator` needs to raise an escalation and is itself running as a Claude Code subagent (the default, non-inline topology), it uses `--raise-only` instead of `--await`, persists a **pending escalation** record in `workflow-state.md` (question, options, context ref, raised-at timestamp, resume point), and returns control to its parent carrying an `ESCALATION-PENDING` result instead of blocking its own turn. **BREAKING (internal contract):** a `concertino-orchestrator` subagent invocation can now legitimately return before the ticket is delivered, carrying this signal — the calling convention documented in `adapters/claude-code/command.md` changes to expect and handle it.
- **Recursive relay.** The same carve-out is expressed once, generically, in `core/roles/orchestrator.md` (reused at every nesting depth per its own "Harness resume model" framing: "a fleet driver, a queue runner, or another orchestrator dispatched you"), so an intermediate orchestrator that itself receives an `ESCALATION-PENDING` result from a child it spawned re-propagates the same signal to its own parent rather than presenting or resolving it — only the genuine root (a session with no parent of its own) presents to real chat and waits.
- **Single authoritative resolution across channels.** A new `concertino answer <ticket> <value>` CLI command (`lib/cli/answer.js`) thinly wraps `lib/ui/store.js`'s existing `writeAnswer`/`writeSubAnswer` — already safe for a second, non-dashboard caller via their `O_EXCL`/rename-based first-write-wins semantics. A dashboard-given answer keeps going through the dashboard's own existing write path (`lib/ui/controllers/escalation.js`, unchanged); a chat-given answer the root relays goes through `concertino answer`. Both hit the same `O_EXCL`/rename-guarded functions, so a dashboard answer and a chat answer racing the same escalation can never both apply — the loser's write is refused with `reason: 'answered'`, and `concertino answer` itself records `escalation.answered` when its own write is the one that resolves the escalation (see design.md Decision 4a), so the dashboard's `needs-you` status clears correctly regardless of which channel won.
- **Resume with provenance.** Once resolved, the root `SendMessage`-resumes the orchestrator subagent (warm resume, the same mechanism already used for executor/evaluator across cycles) with the question, the answer, which channel resolved it, and the timestamp — so the resumed orchestrator (and anything it explains to the human afterward) can state exactly what was asked and answered, regardless of which channel won.
- **Narrow, explicit carve-out into `orchestrator-turn-discipline`.** "Returning control specifically to bubble a pending escalation to a parent that will resume you" is added as an explicit, narrowly-worded exception to "never end your turn while a spawned sub-agent is outstanding" — worded so it cannot be read as license for the failure mode CON-10/CON-15 closed off (an orchestrator must still never return while one of *its own* spawned children — executor/evaluator/skeptic/auditor — is outstanding; the only thing it may ever return early for is a pending escalation it is itself bubbling, with everything needed to resume already persisted).
- **Timeout invariant preserved.** A timeout is still never an approval. `--await`'s existing exit-0/non-zero contract, its `TERM`/`INT` trap, and the multi-part wizard path (CON-46) are unchanged for every call site that keeps using `--await` directly (an `--inline` run, or any script-level caller like `cleanup.sh` — see Non-Goals).

## Capabilities

### New Capabilities
- `escalation-bubble-up`: the `--raise-only` mode, the pending-escalation record persisted in `workflow-state.md`, the `ESCALATION-PENDING` return-and-resume protocol between a subagent orchestrator and its parent (recursively, to the root), and the root's own present-immediately/wait-on-both-channels/resolve/resume loop.
- `escalation-answer-cli`: the `concertino answer <ticket> <value>` command and its `lib/cli/answer.js` implementation, wrapping `store.writeAnswer`/`writeSubAnswer`.

### Modified Capabilities
- `orchestrator-turn-discipline`: adds the narrow "bubbling a pending escalation" exception to the existing never-end-your-turn-with-an-outstanding-child rule, with explicit language distinguishing the two so the new exception cannot be read as loosening the original invariant.
- `inline-orchestrator-mode`: clarifies that an `--inline` run never needs bubble-up (there is no subagent hop), so it always uses immediate-chat-presentation plus a normal blocking `--await` — the resume protocol below simply doesn't apply to it.
- `escalation-trust-offramp`: extends "recording an answer is terminal" to explicitly cover a resumed orchestrator receiving an already-resolved answer via `SendMessage` from its own parent — that relay is exactly as authoritative as observing `answer.json` directly, since it traveled through the same `store.writeAnswer` write.

## Impact

- **Scripts:** `scripts/concertino/emit-event.sh` (new `--raise-only` mode, refactored to share `write_escalation_raised()` with `--await`).
- **CLI:** new `lib/cli/answer.js`, new `bin/concertino answer` dispatch entry.
- **Role/command prompts:** `core/roles/orchestrator.md` ("How to raise one" rewritten with a topology branch; "Harness resume model" gets the narrow carve-out), `adapters/claude-code/command.md` (the `/concertino-deliver` calling session gains the root-side present/wait/resolve/resume responsibilities).
- **State:** `core/workflow-state.template.md` gains a pending-escalation block.
- **No changes** to `lib/ui/store.js`'s write semantics, `lib/ui/reducer.js`'s `PHASE_ORDER`/escalation folding, or the dashboard TUI screens — the dashboard channel is unchanged; this proposal adds a second channel that resolves through the exact same file.
- **Non-Goals (explicitly out of scope for this change):** `cleanup.sh`'s own internal `--await` call (Phase 4's fast-forward safety check) keeps today's single-call blocking behavior unchanged — restructuring a shell script's blocking model into a resumable two-phase protocol is a materially different, disproportionate undertaking and is not part of this ticket's grounding incident (which is about Planning-phase and follow-up-triage escalations). A genuinely separate "fleet driver"/"queue runner" agent role, if one is ever authored outside `core/roles/orchestrator.md`'s own reuse, is assumed to need its own explicit adoption of the same `ESCALATION-PENDING` handling — not implemented here since no such role exists in this codebase today.
