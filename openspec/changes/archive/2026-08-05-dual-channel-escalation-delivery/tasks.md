- [x] 1.3 Add `--wait-only max_wait_sec=<n> ticket=<id> ...`: takes `ticket=`; detects multi-part (`sub_questions`/`total`) mode solely by reading the already-logged `escalation.raised` event for this ticket from `events.jsonl` (the same source `raised_at` is read from — never a separately-supplied `total=` argument); skips both the write *and* the stale-answer discard check (both already ran once, in `--raise-only`/`--await`'s own write step — see design.md Decision 1a); polls for up to `max_wait_sec` seconds, checking `answer.json`'s presence directly (no discard/rm) at each attempt; installs **no** `TERM`/`INT` trap (design.md Decision 1c) — a signal simply kills the process with no event written; returns exit 0 (resolved, answer on stdout, `escalation.answered` recorded) if answered within that window, exit 1 (real deadline — `raised_at` read from `events.jsonl` plus `CONCERTINO_ESCALATION_TIMEOUT_MIN` — reached; `escalation.timeout` recorded, terminal) if the *escalation's* deadline (not this call's `max_wait_sec`) has passed, or exit 2 (still open, neither resolved nor timed out — this call's own short budget simply elapsed) otherwise, per design.md Decision 1b.
- [x] 1.4 Add/extend `test/scripts/escalation-loop.test.sh` (or a new sibling test file) covering: `--raise-only` writes and returns immediately; a single `--wait-only` call resolves (exit 0) against a dashboard-written `answer.json`; a `--wait-only` call with no answer yet and time remaining returns exit 2 (not exit 1, and does not discard/rm anything); a `--wait-only` call after the real deadline has passed returns exit 1 and records `escalation.timeout` even though its own `max_wait_sec` hasn't elapsed; a dashboard answer written *between* two separate `--wait-only` calls against the same escalation is picked up by the second call rather than discarded (regression test for the Decision 1a defect); a `--wait-only` process sent `TERM`/`INT` mid-poll exits without writing `escalation.timeout` (or any event), and a subsequent `--wait-only` call against the same still-open escalation behaves as if the killed call never happened (regression test for the Decision 1c defect); existing `--await` behavior — including its own unchanged `on_kill` trap — is unchanged (regression coverage).

## 4. Orchestrator role: raise/bubble/resume protocol

- [x] 4.1 Rewrite `core/roles/orchestrator.md`'s "How to raise one" section with the topology branch: present to chat immediately in every case; if running as a subagent, `--raise-only` + persist `PENDING_ESCALATION` + return `ESCALATION-PENDING` instead of blocking; if `--inline` (or otherwise the root), `--await` directly exactly as today.
- [x] 4.2 Add the recursive-relay instruction: on receiving `ESCALATION-PENDING` from a spawned child, an agent with its own parent re-returns the same payload upward without presenting/resolving; the root (no parent of its own) presents and resolves.
- [x] 4.3 Add the root's resolution procedure: present immediately, then loop short (~30s) `--wait-only` calls, remain able to accept a direct chat reply between calls, write a chat-given answer via `concertino answer`. Per design.md Decision 4a (revised), `concertino answer` itself records `escalation.answered` when its write resolves the escalation — no confirming `--wait-only` call is made. Branch directly on `concertino answer`'s own result: refused → the dashboard won, continue the normal `--wait-only` loop (which is what observes and logs that competing answer); successful and resolving (single-question, or the multi-part sub-answer that completed the last slot) → proceed straight to resuming the orchestrator; successful but not resolving (a partial multi-part sub-answer) → do not resume anything, continue the normal polling loop for the remaining sub-questions. Report which channel's write actually won when both are attempted near-simultaneously.
- [x] 4.4 Add the root's resume procedure: `SendMessage` the waiting `concertino-orchestrator` with the resolution (question, answer, channel, timestamp); fall back to a cold `RESUME — do not start over` re-spawn pointed at `workflow-state.md` if `SendMessage` is unavailable or the agent cannot be resumed.
- [x] 4.5 Add the narrow "Harness resume model" carve-out (design.md Decision 8's wording): ending a turn is permitted only to bubble a `PENDING_ESCALATION` with no outstanding spawned child and full state already persisted; every other case (an outstanding executor/evaluator/skeptic/auditor) remains forbidden exactly as before.
- [x] 4.6 Extend the "How to raise one" corroboration/off-ramp text (escalation-trust-offramp) to state that a `SendMessage`-relayed resolution from the orchestrator's own parent is terminal without re-corroboration, exactly like observing `answer.json` directly.
