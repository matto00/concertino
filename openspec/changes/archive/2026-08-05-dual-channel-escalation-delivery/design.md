## Context

Today `scripts/concertino/emit-event.sh escalation --await` is one function that does two things in sequence: (1) write `escalation.raised` (with context truncation/persist-evidence handling), then (2) block, polling `.concertino/runs/<TICKET>/answer.json` up to a deadline, and report the result. Every escalation in the system — Planning `ESCALATION`s, `BLOCKER` presentations, budget-exhaustion, follow-up triage — goes through this one call, always made by whichever orchestrator instance is currently running (executor/evaluator/skeptic/auditor never call it directly; confirmed by grep — they only ever return `BLOCKER`/`ESCALATE`/`REFUTE` verdicts to the orchestrator that spawned them).

The gap this change closes is specifically about *when* and *where* that call's question becomes visible to a human with a real chat window open, given two topologies `/concertino-deliver` already supports (CON-49):

- **`--inline`**: the top-level chat session plays the orchestrator role directly, in its own turn. There is no spawn hop — whatever this session presents in its own transcript is immediately visible to the human.
- **Default (non-inline)**: the top-level session spawns `concertino-orchestrator` as a Claude Code subagent (`Agent(subagent_type: concertino-orchestrator)`). Per `orchestrator-turn-discipline`, that subagent must never end its own turn while conducting the delivery — so a blocking `--await` call inside it cannot surface anything to the parent's chat window until the *entire orchestrator turn returns*, however long that is.

CON-71's grounding incident is the default topology: a dashboard-resolved `fold-in` answer never reached the top-level session at all, because the orchestrator subagent was still running (and would only relay after returning) — the top-level session's only signal was a *different, earlier* escalation that happened to time out and fall back to chat, and it wrongly generalized from that one data point.

## Goals / Non-Goals

**Goals:**
- A raised escalation is visible in the raiser's own chat transcript *immediately*, not only after a dashboard timeout, in every topology.
- In the default (non-inline) topology, an escalation raised by the orchestrator subagent reaches the true root (the top-level `/concertino-deliver` session) while the wait is still open, not only once the subagent eventually returns.
- A dashboard-given answer and a chat-given answer for the same escalation resolve through exactly one authority (`lib/ui/store.js`'s `writeAnswer`/`writeSubAnswer`), so they can never both apply.
- Once resolved, every agent between the raiser and the root can state what was asked and answered, regardless of which channel resolved it.
- The existing single-channel contract is unchanged for every caller that doesn't need bubble-up: `--await`'s exit-0/non-zero contract, the `TERM`/`INT` trap recording `escalation.timeout`, the multi-part wizard's `complete`-flag resolution, and `--inline` runs.

**Non-Goals:**
- `cleanup.sh`'s own internal `--await` call (the Phase 4 fast-forward safety check) is unchanged. It runs as a single blocking shell-script call inside the orchestrator's own Bash tool invocation, not as a separate agent turn; converting it into a two-phase resumable protocol is a materially different undertaking than bubbling an *agent-level* subagent return, and CON-71's incident is about Planning/follow-up escalations, not this one. Left as an explicit follow-up candidate.
- A genuinely separate "fleet driver"/"queue runner" agent role. No such role exists in this codebase today (`fleet` here only names the dashboard's fleet *view*, confirmed by search) — `core/roles/orchestrator.md`'s own text already anticipates one might exist someday ("a fleet driver, a queue runner, or another orchestrator dispatched you"). Because the bubble-up rule below is expressed once, generically, in that same file, a *future* such role that reuses `orchestrator.md`'s instructions verbatim (as any nested `concertino-orchestrator` spawn already does) inherits the recursive-relay behavior for free. A role authored independently of this file would need its own adoption — out of scope here.
- Full chat-side parity for multi-part (CON-46 wizard) escalations. A bubbled multi-part escalation still presents every sub-question to chat and still resolves through `answer.json`'s existing `{subAnswers, total, complete}` shape and the dashboard's step-through wizard; the new `concertino answer` CLI supports answering one sub-question at a time (`--sub`/`--total`) so chat is not a strictly weaker channel, but no new chat-native wizard UX is built.
- Any change to `lib/ui/store.js`'s write semantics, `lib/ui/reducer.js`'s event folding, or the dashboard TUI screens. The dashboard channel is untouched; this design adds a second channel that resolves through the exact same file and the exact same `O_EXCL`/rename-based first-write-wins guarantees.

## Decisions

### Decision 1: Split `--await` into three composable modes on `emit-event.sh escalation`

- **`--await`** (unchanged): write `escalation.raised` (including the existing stale-`answer.json`-discard safety check, which runs immediately after the write, before polling begins), then block-poll to resolution. Still the only call `--inline` runs and `cleanup.sh` use.
- **`--raise-only`** (new): write `escalation.raised` (identical context-handling/truncation/persist-evidence path — `write_escalation_raised()` is refactored to be shared, not duplicated), **including that same one-time stale-`answer.json`-discard check** (see Decision 1a — this check belongs to the *write*, not the *poll*), then return immediately, exit 0, no polling. Used by a subagent orchestrator that is about to bubble instead of block.
- **`--wait-only`** (new): skip the write *and* skip the discard check (both already ran, once, when the escalation was raised by a prior `--raise-only` or `--await` call), and poll for a resolution keyed on `ticket=`, bounded by a short **per-call** budget distinct from the escalation's real deadline (see Decision 1b). Used by the root once it has relayed an already-raised escalation to chat and is ready to wait on it, called repeatedly (Decision 3).

The write path (`--raise-only`/`--await`) and the poll path (`--wait-only`/`--await`) share their respective single implementations; only which sub-steps run at each call site differs. This keeps the change to `emit-event.sh` additive and low-risk — no existing call site's behavior changes.

#### Decision 1a: The stale-`answer.json`-discard check moves to the write path, and never repeats during a single escalation's `--wait-only` polling

Today's discard-and-`rm` step (immediately after `write_escalation_raised()`, before the poll loop starts) exists to protect against a *different, earlier* escalation's leftover `answer.json` being misread as an answer to the one about to be raised — it is safe **only** because it runs once, immediately after that same call's own raise, before anything could have legitimately answered the escalation that raise just created. Decision 3 has the root call `--wait-only` repeatedly (every ~30s) against the *same still-open* escalation. If the discard check were repeated on every one of those calls (as a naive "reuse the poll loop unchanged" would do), it would treat a genuine dashboard answer that lands in the gap between two polls as "stale leftover state from an earlier escalation," discard it, and keep polling — silently dropping the human's real answer. So the discard check runs **exactly once per escalation, as part of the write** (`--raise-only` or `--await`'s own write step), never as part of `--wait-only`. By the time any `--wait-only` call runs, the discard check has already made `answer.json`'s absence-or-presence meaningful for *this* escalation specifically; `--wait-only` simply checks for its presence at each poll and, if present, resolves — no further discarding.

#### Decision 1b: `--wait-only` takes its own short per-call budget, separate from the escalation's real deadline

`--wait-only max_wait_sec=<n> ticket=<id> ...` polls for up to `<n>` seconds (Decision 3 default: ~25–30s) and then returns one of three outcomes, distinguished by exit code: **0** (resolved — the answer is on stdout, `escalation.answered` is recorded, exactly as `--await` does today), **1** (the escalation's *real* deadline — `raised_at + CONCERTINO_ESCALATION_TIMEOUT_MIN`, Decision 2 — has been reached; `escalation.timeout` is recorded, terminal, exactly as `--await` does today), or **2** (neither: this call's own `max_wait_sec` budget elapsed first, the escalation is still open, and the caller should call `--wait-only` again). Exit code 2 is new and specific to `--wait-only` — `--await` and `--raise-only` never produce it. This is what actually gives Decision 3's chunked-polling architecture a clean way to return every ~30s without prematurely declaring the escalation timed out.

`--wait-only`'s `sub_questions`/`total` detection for multi-part escalations (needed to apply the `complete`-flag resolution logic instead of the single-answer one) is read from the same already-logged `escalation.raised` event in `events.jsonl` that Decision 2's `raised_at` is read from — the same source, the same re-derive-on-every-call discipline — never from a separately-supplied `total=` argument, so there is exactly one mechanism, not a choice between two.

#### Decision 1c: `--wait-only` installs no kill-signal trap — a signal must never write a terminal `escalation.timeout` on its own

`--await`'s existing `on_kill` trap (`emit-event.sh:474-479`) writes a terminal `escalation.timeout` unconditionally on `TERM`/`INT`, which is correct for `--await` because the only ways to kill that single, one-shot blocking call are the harness's own tool timeout or the escalation genuinely having exhausted its wait — "killed" and "should be recorded terminal" coincide. That equivalence does **not** hold for `--wait-only`: Decision 3 has the root spending essentially its entire wait window inside back-to-back active `--wait-only` calls (not in the safe gaps between them), so a harness restart or session eviction lands, almost certainly, *inside* an active call — and the escalation's real deadline (up to `CONCERTINO_ESCALATION_TIMEOUT_MIN`, default well beyond any one `max_wait_sec` chunk) is very unlikely to have actually been reached at that moment. So `--wait-only` installs **no** `on_kill`-style trap at all: a `TERM`/`INT` simply kills the process with no event written, leaving `answer.json` and the escalation's state exactly as they were before that particular poll attempt — safe for the root's next turn (or a cold re-spawn recovering via `workflow-state.md`'s `PENDING_ESCALATION`) to call `--wait-only` again with no state corruption and no falsely-terminal log entry. The real deadline (Decision 1b's exit code 1) remains the only way a `--wait-only`-driven wait is ever marked as genuinely timed out.

*Alternative considered:* a single new flag with a mode enum (`--mode=raise|wait|await`). Rejected only for readability — three explicit long-flags read better at each call site than a `--mode=` string, and match this script's existing convention of dedicated flags (`--await` itself is already this shape).

### Decision 2: `--wait-only`'s *real* deadline is anchored to the persisted raise time, not to any one call's start time

Every `--wait-only` call recomputes the escalation's real deadline as `raised_at + CONCERTINO_ESCALATION_TIMEOUT_MIN`, reading `raised_at` from the `escalation.raised` event already durably logged in `events.jsonl` (never re-derived from wall-clock-at-invocation). This is the deadline that produces exit code 1 (Decision 1b) — it makes the *overall* wait resilient to being split across many short calls (Decision 3) or even a root session restart mid-wait, because it is a property of the escalation itself, not of any one process's uptime. It is distinct from, and outlives, any single call's own `max_wait_sec` (Decision 1b's exit code 2 budget).

### Decision 3: The root polls in short (~30s) `--wait-only` calls across its own turns, not one long blocking call

Rejected: one single `--wait-only` call blocking for the full timeout window (mirroring `--await` exactly). The risk is that a human's *direct chat reply*, typed while that one Bash call is still executing, may not be visible to the session until the tool call returns (harness message-queueing behavior during a long-running tool call is not documented for this environment — see Risks). Chunking the wait into repeated short (`max_wait_sec≈25–30`) `--wait-only` calls, with the root free to end its turn between them (safe: by the time the root is waiting on a bubbled escalation, the subagent that raised it has already returned control and is not an outstanding child — see Decision 5), means a chat reply the human types between polls is processed on the very next ordinary turn, exactly like any other message in an ongoing conversation. Each call returns exit code 2 ("still open, not yet resolved") until either exit 0 (resolved) or exit 1 (the real deadline from Decision 2 was reached) — the root simply calls `--wait-only` again on exit 2, and stops on 0 or 1. This trades a slightly busier prompt-driven loop for not depending on unverified interrupt semantics.

### Decision 4: Single-authority resolution via a new `concertino answer` CLI, not a bash-side re-implementation

`lib/ui/store.js`'s `writeAnswer`/`writeSubAnswer` already have exactly the semantics this needs (`O_EXCL`/rename-based first-write-wins, safe for any second caller — confirmed these take plain `(root, ticket, answer)` arguments with no dashboard-only state). Rather than have a bash script independently construct a same-shaped `answer.json` (risking shape drift from the JS side), add `lib/cli/answer.js` (+ `bin/concertino answer <ticket> <value> [--sub <index> --total <n>]` dispatch) as a thin wrapper calling the same exported functions the dashboard TUI calls. The root writes a chat-given answer through this command; a dashboard-given answer keeps going through `lib/ui/controllers/escalation.js` exactly as today. Both land in the same file through the same guard.

*Alternative considered:* have the root itself construct `answer.json` via a raw bash `printf`+`mv` sequence, mirroring `writeAnswer`'s rename-based approach. Rejected: duplicating the exact JSON shape and atomicity strategy in two languages is precisely the kind of drift the escalation-context/multi-part-escalation specs have already had to guard against once (e.g. `complete` as the sole resolution signal); one canonical implementation is safer.

#### Decision 4a (revised after human-directed rethink, replacing the original Decisions 4a/4b): `concertino answer` self-records `escalation.answered` on a resolving write — no confirming `--wait-only` call

The original version of this decision kept `concertino answer` from ever writing `escalation.answered` itself, and instead had the root make one extra `--wait-only` call after every chat-given answer purely to get the existing poll loop to log it. Four skeptic rounds found two successive defects in that confirming-call machinery (an unconditional-exit-0 assumption that broke for a partial multi-part sub-answer, and the conditional-branch fix that produced). The human directed a rethink of the premise those patches were both built on, rather than a third patch: *why* can't `concertino answer` just log the event itself?

**The actual reason for the existing invariant, found in the code, not assumed:** `writeAnswer`'s own comment (`lib/ui/store.js:199-206`) states plainly: *"`emit-event.sh --await`, blocked in its poll loop, is the reader; it records `escalation.answered` itself once it picks the file up, so this function does not also emit that event — doing both would double it in the log."* This is not a correctness constraint on `answer.json`'s own atomicity (that's `O_EXCL`/rename, unrelated and unchanged) — it is purely about avoiding a *guaranteed* double-write on today's one existing path: **every** dashboard-given answer today is always independently observed by an `--await` call that is, by construction, already actively polling for it, so if `writeAnswer` itself also emitted the event, that event would be logged twice for every single dashboard answer, not just some.

**Why that specific guarantee does not carry over to a chat-given answer under this design:** the root is a single sequential agent turn — it is never simultaneously "blocked inside a `--wait-only` Bash call" and "processing a chat reply from the human." Whichever it is doing, it is doing one at a time (this is exactly why Decision 3 chunks the wait into short calls in the first place — to keep chat responsive between them, not during them). So by the time the root actually invokes `concertino answer` in reaction to a chat message, no `--wait-only` call belonging to *that same root* can be concurrently in flight to also observe and log the same write. Nothing else in this design polls `answer.json` — the dashboard TUI writes it directly (`lib/ui/controllers/escalation.js`) and never polls its own write. So, unlike the dashboard-answer path, there is no second, structurally-guaranteed observer for a chat-given answer at all — the "doing both would double it" premise simply does not apply here.

**The revised mechanism:** `concertino answer`, immediately after a *successful* (non-refused) `writeAnswer`/`writeSubAnswer` call, itself invokes `emit-event.sh`'s existing generic non-blocking event-write path (`emit-event.sh escalation.answered ticket=<id> answer=<value>` — or `sub_answers=<array>` for the multi-part case, reading the just-written `subAnswers` back — with no `--await`/`--raise-only`/`--wait-only` flag; this generic write-one-event-and-exit path already exists today for every event kind, unmodified by Decision 1) — but **only when the write actually resolves the escalation**: unconditionally for a single-question answer, and only when `writeSubAnswer`'s own returned `complete` is `true` for a multi-part sub-answer. A partial multi-part write (`complete: false`) records `answer.json`'s new state exactly as before, but `concertino answer` logs nothing — mirroring precisely the condition the poll loop's own multi-part branch already uses to decide whether to resolve. This reuses `emit-event.sh`'s existing, unmodified event-writing machinery (no new script mode, no duplicated JSON-shape logic in the CLI — consistent with Decision 4's own "delegate to the canonical implementation" principle) and needs zero changes to `store.js`.

**What this does to the root's own procedure:** the confirming `--wait-only` call is deleted outright, along with the exit-0/exit-2 branching it required. `concertino answer`'s own return value already tells the root everything it needs: refused (`reason: 'answered'`, the dashboard won — the root's own already-running or next `--wait-only` call is what will observe and log *that* competing answer, exactly as it always would have) vs. successful-and-resolving (single-question, or the completing multi-part sub-answer — the root proceeds straight to resuming the orchestrator, since `escalation.answered` is already recorded) vs. successful-but-not-yet-resolving (a partial multi-part sub-answer — the root does not resume anything, and simply continues its normal Decision-3 polling loop for the remaining sub-questions, exactly as if the chat reply had been a dashboard wizard step instead). There is exactly one branch here, driven entirely by `concertino answer`'s own return, not two separate mechanisms (a write, then a separate confirming poll with its own exit-code contract) layered on top of each other.

**Alternatives costed out, per the human's request:**
1. *(chosen)* **Relax the invariant** — `concertino answer` writes `escalation.answered` itself, exactly as just described. Costs: one extra subprocess call inside `lib/cli/answer.js` on the resolving path; the invariant's documented rationale (`store.js:199-206`) needed to be read and distinguished from this design's actual structure, not just assumed to still apply — done above. Benefit: deletes the entire confirming-call/conditional-exit-code mechanism (Decisions 4a/4b's original text) outright, which is precisely the machinery all four skeptic rounds' findings orbited; no new script flag needed (reuses `emit-event.sh`'s existing generic write path).
2. **Make dashboard state derivable from `answer.json` directly**, instead of depending on the `escalation.answered` event at all — e.g. have `lib/ui/reducer.js` (or the screens that read `run.escalation`) check `answer.json`'s presence as a side channel rather than folding only from `events.jsonl`. Rejected: this breaks the event-log-is-the-single-source-of-truth architecture the reducer is built on for *every* other piece of run state, not just escalations — a materially bigger, more invasive change than this ticket's own stated Non-Goals allow ("No changes to `lib/ui/reducer.js`'s event folding"), for a benefit (avoiding one small CLI-side event write) that option 1 already achieves more cheaply and with a smaller blast radius.
3. **Keep the invariant exactly as-is** (the original Decision 4a/4b shape). Rejected as the chosen path, but was a legitimate outcome to consider: it does work, at the cost of the confirming-call round-trip and the conditional-exit-code branching that produced two of the four REFUTE rounds. Once the invariant's actual rationale (found above) was shown not to apply to this design's structure, keeping it anyway would have been preserving a rule for its own sake rather than for the reason it was written.

**Re-checking the CON-46 multi-part/wizard path under this revised design:** the dashboard-driven wizard path is completely untouched (still `writeSubAnswer` → the poll loop's existing `complete`-flag resolution, exactly as before this whole ticket). For the new chat-driven path: each partial `concertino answer ... --sub --total` write updates `answer.json` via the same unmodified `writeSubAnswer`; if it is not yet the completing answer, no event is logged and the escalation stays open for either channel to continue — from the dashboard's perspective this is indistinguishable from a partial dashboard wizard step. If it *is* the completing answer, `concertino answer` logs `escalation.answered` with the full `sub_answers` array (read back from the just-written state), exactly mirroring the shape the poll loop's own multi-part resolution already produces, so `lib/ui/reducer.js` folds it identically regardless of which channel supplied the final step.

### Decision 5: The bubble is a narrowly-scoped return, not a new suspend/resume primitive

When a `concertino-orchestrator` instance running as a subagent decides to raise an escalation, at that exact moment it has *no outstanding spawned child* — the executor/evaluator/skeptic/auditor that produced the verdict prompting this escalation has already returned its result before the orchestrator's own reasoning gets far enough to call `--raise-only`. So "return control now, carrying an `ESCALATION-PENDING` payload, to be resumed later via `SendMessage`" is not a new capability — it reuses the exact `SendMessage`-based warm-resume mechanism `orchestrator.md` already documents for resuming the *executor*/*evaluator* across cycles, just in the opposite direction (a parent resuming the orchestrator itself instead of the orchestrator resuming its own children).

The `ESCALATION-PENDING` payload (the orchestrator's literal return text) carries: `TICKET`, `QUESTION`, `OPTIONS` (or `SUB_QUESTIONS`), `CONTEXT_REF` (if any), `RAISED_AT`, and an explicit resume instruction naming itself so the parent can `SendMessage` it back in once resolved. Before returning, the orchestrator persists the same information as `PENDING_ESCALATION` in `workflow-state.md` (new field — see below), so a cold re-spawn recovering from `workflow-state.md` (the existing resume path, used when `SendMessage` is unavailable) can reconstruct and re-emit the same `ESCALATION-PENDING` result rather than losing the pending question.

`core/workflow-state.template.md` gains:

```
# escalation-bubble-up (CON-76). Set only while a --raise-only escalation is
# outstanding and this orchestrator has returned control to its parent,
# waiting to be SendMessage-resumed with the resolution. null otherwise.
PENDING_ESCALATION: {"question":"...","options":"...","context_ref":"...","raised_at":<ms>,"kind":"planning|blocker|budget|followup|final-gate"} | null
```

### Decision 6: The recursive-relay rule is written once, generically, in `orchestrator.md` — not special-cased per topology

Any orchestrator instance, on receiving an `ESCALATION-PENDING` result from a child it spawned (as opposed to raising one itself), applies the identical topology test already used for raising: *is there a parent above me, or am I the root?* If it has its own parent (it is itself a subagent), it immediately persists and re-returns the same payload upward rather than presenting or resolving anything — it never becomes the presenter just because it happens to be an intermediate hop. Only the actual root — the top-level `/concertino-deliver` chat session, or an `--inline` run (which never bubbles in the first place, see Decision 7) — ever presents to chat and calls `--wait-only`/`concertino answer`. This one rule, applied uniformly at every level, is what makes arbitrary nesting depth work without per-level bookkeeping beyond "who is my parent."

### Decision 7: `--inline` never bubbles

An `--inline` run has no subagent hop by construction (CON-49) — the session playing the orchestrator role *is* the root. Its "How to raise one" branch is: present to chat immediately, then call `--await` exactly as today (Decision 1's unchanged mode). No `PENDING_ESCALATION` state, no `ESCALATION-PENDING` return, no bubble. This is stated explicitly in the `inline-orchestrator-mode` spec delta so the two branches (inline vs. default topology) cannot be conflated.

### Decision 8: The `orchestrator-turn-discipline` carve-out is scoped to exactly one return path

Added to `core/roles/orchestrator.md`'s "Harness resume model" section, verbatim intent (final wording lands in the role file, not duplicated here):

> The only circumstance in which this orchestrator may end its turn while artifacts of the current ticket are still incomplete is to bubble a `PENDING_ESCALATION` it has just raised (via `--raise-only`) or received from a child it spawned, up to its own parent — and only after that escalation's full state is durably persisted in `workflow-state.md` so a cold re-spawn can reconstruct it. This is not the same failure mode CON-10 and CON-15 closed off: at the moment of this return, this orchestrator has no outstanding spawned child of its own (the executor/evaluator/skeptic/auditor that led to this escalation has already returned its verdict) — nothing here is orphaned by the return, because everything needed to resume is already on disk and the parent that receives this return is the one now responsible for eventually calling `SendMessage` back in. Ending a turn for any other reason — including while waiting on a spawned executor, evaluator, skeptic, or auditor — remains exactly as forbidden as before.

`escalation-bubble-up`'s spec delta states the corresponding testable requirement; `orchestrator-turn-discipline`'s own spec delta adds this as its one new bullet, worded to make clear it narrows, not loosens, the existing rule.

## Risks / Trade-offs

- **[Risk] Harness message-queueing during a running Bash tool call is unverified.** → Mitigation: Decision 3's short-poll chunking sidesteps needing that guarantee at all — the root is never blocked on Bash for longer than one short poll window at a time.
- **[Risk] A `SendMessage` resume could fail or the child agent could be gone (harness restart, session eviction).** → Mitigation: same fallback already documented for the executor/evaluator warm-resume case — cold re-spawn a fresh `concertino-orchestrator`, prompt beginning `RESUME — do not start over`, pointing it at `workflow-state.md`; `PENDING_ESCALATION` being persisted there means the re-spawned instance can immediately reconstruct and re-emit `ESCALATION-PENDING` (or, if `workflow-state.md` shows the escalation as already answered by then, proceed directly) rather than silently dropping the question.
- **[Risk] A harness restart or session eviction kills the root mid-`--wait-only` call — the same moment `--await`'s inherited `on_kill` trap would write a terminal `escalation.timeout`, even though the escalation's real deadline is nowhere close.** → Mitigation: Decision 1c — `--wait-only` installs no kill-signal trap at all; a signal simply ends the process with no event written, leaving the escalation exactly as open as before that poll attempt, safe for the next `--wait-only` call (or a cold re-spawn) to resume polling with no falsely-terminal log entry.
- **[Risk] A human answers via chat *and* via dashboard for the same escalation, arriving at the root in either order.** → Mitigation: both channels write through `concertino answer`/the dashboard's existing controller, both hitting the same `O_EXCL`/rename-guarded `writeAnswer`/`writeSubAnswer` — whichever lands first wins, the second is refused with `reason: 'answered'`, and the root — having just attempted the write itself when relaying a chat answer — learns immediately whether its own write actually was the one that won, and can say so plainly.
- **[Risk] Relaxing the "only the active poller writes `escalation.answered`" invariant (Decision 4a, revised) could reintroduce the exact double-write the invariant was written to prevent.** → Mitigation: the double-write the invariant guards against requires a second, structurally-guaranteed observer of the same write — true for today's dashboard-answer path (an `--await` call is always already polling) but not for a chat-given answer, since the root is single-threaded and is never concurrently inside a `--wait-only` call while it is the one invoking `concertino answer` (see Decision 4a's full argument). No other process in this design polls `answer.json` at all.
- **[Risk] The `orchestrator-turn-discipline` carve-out is worded loosely enough to be misread as "it's fine to return early sometimes."** → Mitigation: Decision 8's wording is deliberately anchored to a single, checkable precondition ("no outstanding spawned child of its own" + "state durably persisted first") rather than a vague allowance; the spec delta below states this as an explicit MUST/MUST NOT pair, not a soft guideline.
- **[Trade-off] Deeper-than-one-hop nesting (an orchestrator spawned by another orchestrator) is designed generically (Decision 6) but not exercised by any test, since no such topology exists in this codebase today.** → Accepted: the rule is stated once and applies uniformly rather than being special-cased to "exactly one hop," so it is at least not *wrong* for deeper nesting if/when it arises — verified only for the one hop that exists (`/concertino-deliver` → `concertino-orchestrator`).

## Migration Plan

No data migration — `answer.json`'s shape is unchanged, `events.jsonl` only gains new event kinds (`escalation.raised` already carries everything needed; no new kind is strictly required, since `--raise-only`/`--wait-only` reuse `escalation.raised`/`escalation.answered`/`escalation.timeout` verbatim — the dashboard's `lib/ui/reducer.js` needs no changes). Existing in-flight runs (a worktree mid-delivery when this ships) keep working: they were started against the old `emit-event.sh`/`orchestrator.md`, and the new modes are purely additive flags — an old-style `--await` call continues to behave identically. No rollback beyond reverting the change is needed.
