## Context

Concertino renders a delivery workflow (core/roles/*.md → .claude/agents/*, core/scripts/* → scripts/concertino/*) into target repos via `concertino sync`. The incident this ticket addresses happened in a *target* repo (helio) during a delivery run: an executor added a new pre-commit gate script, wired it into `.husky/pre-commit`, and committed all three changes together. The gate's first execution ran live, inherited a hook-exported `GIT_DIR` from a linked worktree, and `git init` inside the gate's own fixture-building code re-initialised the real repo as bare.

Six design-gate rounds, a cold skeptic, and an evaluator reviewed the script's *logic* and none caught it — the defect is in environment inheritance, which is invisible in a diff and only reproducible under a hook-shaped environment that ordinary manual testing (`node script.mjs` from a shell) never recreates. The fix therefore cannot live in "reviewers should look harder" — it needs a script-enforced gate that a run cannot bypass by omission, mirroring how `assert-phase.sh` already gates Setup/Servers/Delivery/Cleanup mechanically rather than by agent recall.

## Goals / Non-Goals

**Goals:**
- Classify a diff touching the target repo's own commit-gate chain (`.husky/**`, or a script that `.husky/pre-commit` invokes) as a live-infrastructure change, mechanically, from the diff itself — no reliance on an agent noticing.
- Require an answered implications checklist (what it executes, what env it inherits and from where, whether it writes outside its own sandbox, linked-worktree vs. main-checkout behavior, first-run behavior) before such a change can reach Delivery.
- Require isolation-test evidence (a single hook-shaped run against a throwaway fixture repo, yielding a pass/fail corruption verdict for the actual target script — see Decision 5 for why this replaced an earlier, unobtainable-for-safe-scripts "red-then-green" formulation) before such a change can reach Delivery.
- Make both requirements a script-enforced Delivery gate failure, not a checklist an agent is merely instructed to fill in — the same mechanical-gate pattern `assert-phase.sh` already uses for every other phase postcondition.
- Ship a reusable isolation-test helper (`test-gate-in-isolation.sh`) so exercising a gate under a hook-shaped environment is one command, not bespoke per-ticket scripting — every prior review of this exact incident's script failed to do this ad hoc, so make the correct path the easy path.

**Non-Goals:**
- Fixing the underlying `GIT_*` env-leak itself — already addressed on the helio side (`git-child-env-hardening`, CON-133) and out of scope here.
- Detecting every conceivable "live-infrastructure" change (e.g. CI workflow files, deploy scripts) — scope is deliberately the commit-gate chain named by the ticket (`.husky/**` and scripts it invokes), the exact class that caused this incident. Broader live-infra classification is a plausible follow-up, not this ticket.
- Re-implementing the design-gate/final-gate skeptic loop — this adds one additional mechanical Delivery-time check plus earlier Planning-time guidance, it does not restructure Phase 1/Phase 2.

## Decisions

**1. Classification is a script, not a role-doc instruction.**
`scripts/concertino/check-gate-chain-change.sh <worktree> <base-remote/branch>` computes the changed paths (`git diff --name-only <merge-base>...HEAD`, falling back to `git_child` env hardening exactly as `assert-phase.sh` already sources `lib/git-child-env.sh`) and flags the change as gate-chain-touching if any changed path:
  - matches `^\.husky/`, or
  - is referenced (by relative path, resolved through `package.json`'s `scripts` map) from `.husky/pre-commit`'s own command list.
The second rule is what catches "a script the hook invokes" without the diff itself touching `.husky/`, per the ticket's own scope item 1. Implemented as a small, dependency-free bash+node routine (repo already requires node); false negatives on obscure invocation styles are accepted (documented as a known limitation) rather than building a shell parser.

Alternatives considered: doing this classification as an LLM judgment inside the orchestrator's Planning phase alone. Rejected as the sole mechanism — it is exactly the "checklist an agent is merely instructed to fill in" pattern the ticket's hardest acceptance criterion calls out. Kept as a *complementary*, earlier signal (Planning-time), not a substitute for the mechanical Delivery gate.

**2. Enforcement point: `assert-phase.sh delivery`, called before PR creation.**
`assert-phase.sh delivery` already runs before the orchestrator pushes/creates the PR (Phase 3 step 3) and already fails the phase transition on missing preconditions. Add one more check there: `assert-phase.sh delivery` calls `check-gate-chain-change.sh` to classify the diff, and — still inside `assert-phase.sh delivery` itself, not inside the classifier script — if flagged, require durable evidence to already exist **for every gate-chain-touching script path the diff actually contains** (see Decision 3's evidence-destination-naming rule — this is what prevents an unrelated script's passing transcript from satisfying the gate for a different, newly-touched script), or fail the phase (`FAIL gate-chain implications checklist / isolation-test evidence missing for <script path>`) — blocking Delivery exactly as every other `assert-phase.sh` precondition already does. `assert-phase.sh delivery`'s existing signature is `<WORKTREE_PATH> <BRANCH> [TICKET_ID]`; TICKET_ID is already passed by the orchestrator, so no new argument is required — evidence lookup keys off `TICKET_ID` plus the specific script paths `check-gate-chain-change.sh` reports.

Alternatives considered: gating at the design-skeptic step instead (Phase 1). Rejected as the *sole* gate because Planning happens before the diff exists in many cases (the executor writes the gate script during Execution, not Planning) — the mechanical check must run against the actual diff, which is only complete once Execution has produced it. Design-time guidance is added as a second, earlier, advisory signal (see Decision 5) but the hard block is at Delivery, against the real diff.

**3. Evidence must be durable and outlive `openspec archive`.**
Phase 3 archives the change directory (step 2) *before* pushing and running `assert-phase.sh delivery` (step 3) — so evidence cannot live only inside `openspec/changes/<change>/design.md` in the worktree, or it would already be relocated/inaccessible in a predictable path by the time the gate runs. Evidence is instead split:
  - The **answered implications checklist** lives in `design.md` under a required heading `## Gate-Chain Implications Checklist` (so it's part of ordinary design review, and the design-gate skeptic can hold the executor to it during Planning/Execution) — but the mechanical Delivery check does **not** depend on reading the (possibly-already-archived) `design.md` path directly. Instead, `persist-evidence.sh` is re-run on `design.md` a **second time**, immediately before Phase 3's archive step, in addition to the existing Phase 1 step 6 call — see the re-persist note below; this is what makes the durable copy reflect a checklist the executor filled in during Execution, not only whatever `design.md` looked like at the end of Planning. `assert-phase.sh delivery` checks *that* (freshest) durable copy (using `check-gate-chain-change.sh` only to classify whether the diff is gate-chain-touching in the first place).
  - The **isolation-test evidence** transcript, one per gate-chain-touching script, is written by `test-gate-in-isolation.sh` to a fixed, predictable, per-script destination under `.concertino/runs/<TICKET_ID>/evidence/` — see the exact destination-naming rule in Decision 5 (it is derived from `persist-evidence.sh`'s own worktree-relative destination contract, corrected from an earlier flat `gate-chain-isolation-<n>.md` naming this design used before the round-2 REFUTE identified it as inconsistent with that contract and unbound to the specific script tested) — via the same `persist-evidence.sh` script, so it shows up in the dashboard's EVIDENCE panel like any other artifact, never only inside the worktree.

  **Re-persist note (fixes a gap the design-gate skeptic caught in round 1):** Decision 1 already establishes that a gate-chain script is typically *written during Execution*, not Planning — so `design.md`'s checklist section, if answered at all, is most often filled in or edited by the executor after Phase 1's one-time `persist-evidence.sh` call has already run and captured a stale (pre-checklist) copy. The Delivery-time check must not silently pass or fail against that stale copy. Fix: `core/roles/orchestrator.md`'s Phase 3 step 1 (immediately before the squash) gains one additional call — `persist-evidence.sh` on `$WORKTREE_PATH/openspec/changes/<CHANGE_NAME>/design.md` again, unconditionally, cheap and idempotent (it already tolerates being called once per artifact elsewhere in the workflow) — so the durable evidence directory always reflects `design.md`'s current, Execution-time content by the time `assert-phase.sh delivery` reads it. This is a role-doc change (task 4.2 below), not a new mechanical gate of its own — the *check* stays entirely in `assert-phase.sh delivery`/`check-gate-chain-change.sh`; this only fixes what evidence exists for that check to read.

Alternatives considered: checking `git show <commit>:openspec/changes/<change>/design.md` against a specific commit before the squash. Rejected — Phase 3 step 1 squashes the branch into one commit first, so per-commit history is not reliably available by the time `assert-phase.sh delivery` runs, and this would require passing the change name into `assert-phase.sh`, widening its contract for every call site. The durable-evidence-directory approach needs no such widening.

**4. Required checklist content, mechanically checked (not just "is the section present").**
`assert-phase.sh delivery` (once `check-gate-chain-change.sh` has classified the diff as gate-chain-touching) requires the persisted `design.md` evidence copy to contain a `## Gate-Chain Implications Checklist` heading followed by five specifically-worded sub-items (executes / environment-inherited / writes-outside-sandbox / linked-worktree-vs-main-checkout / first-run-behavior), each with non-empty, non-placeholder content (rejects literal `TBD`, `N/A` used as a dodge, or an empty line) via a small node/grep routine. This directly targets the ticket's second acceptance criterion (the linked-worktree question must be explicitly present, not just any prose).

Alternatives considered: freeform "answer these questions somewhere in design.md" with no structural check. Rejected — unstructured prose is exactly what a reviewer can skim past; a required heading + required sub-items is the smallest change that makes "did you answer the linked-worktree question" mechanically greppable.

**Correction (round-1 REFUTE):** `design.md` is not rendered from an `openspec`-owned template that this repo controls — `openspec` is an external npm dependency (`package.json`'s `devDependencies`), and nothing under `core/` generates its artifact templates. There is therefore no template file for this change to edit. The required heading is instead produced the same way every other section of `design.md` already is: the orchestrator (Planning, or the executor during Execution if the gate-chain script is written then) writes it directly into `design.md` by hand, following written guidance. That guidance — the exact heading text and the five required sub-item prompts, verbatim, so the mechanical grep in `check-gate-chain-change.sh` and the prose guidance always agree on wording — lives in `core/roles/orchestrator.md` (Decision 6) and is also restated in `core/roles/executor.md` (Decision 7's staging guidance) for the common case where the executor is the one adding the section. Task 4.1 below is corrected to reflect this: it adds the heading text as literal guidance in the role docs, not a template-file edit.

**5. Isolation-test helper: `scripts/concertino/test-gate-in-isolation.sh`.**
Revised from the original REFUTE'd design: the helper does **not** attempt to run the target script twice (once "unhardened," once with a hardening wrapper forcibly applied) — the skeptic correctly identified that (a) the helper cannot mechanically retrofit `lib/git-child-env.sh`'s `git_child` wrapper onto an arbitrary target script it doesn't own, and (b) requiring the two runs to "differ observably" makes the evidence unobtainable for a target script that is already safe (the common, desired case), since a safe script behaves identically — no corruption — whether or not the hazard is present. The corrected design separates *proving the harness itself reproduces the incident's failure class* from *testing the actual target gate*, and only the latter gates a real delivery:

Usage: `test-gate-in-isolation.sh <ticket-id> <path-to-gate-script> [<npm-script-name>]`. It:
  1. States, to stdout, in plain language, exactly what it is about to do and that it operates only inside a `mktemp -d` throwaway directory — never the real repo — before doing anything (the ticket's own verification-standard requirement, applied to the helper itself, not just to ad hoc manual probes).
  2. Creates a disposable fixture repo tree at `$(mktemp -d)` shaped like a linked worktree: a `.git` *file* (not directory) pointing at a fabricated `gitdir: .../worktrees/fixture` path, so a naive `git init` inside a hook run against it reproduces the exact `GIT_DIR`-inheritance shape from the incident.
  3. **Single hook-shaped run**: invokes the *actual target gate script*, exactly once, with `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` exported exactly as Husky's own hook-launcher exports them for a linked-worktree commit (documented inline, sourced from the same shape `git-child-env-hardening`'s own selftest already fabricates on the helio side). Captures before/after `git rev-parse --is-bare-repository`, `git status`, and a manifest of the fixture's `.git` entries.
  4. **Pass/fail verdict on that single run**: the fixture is asserted to be uncorrupted afterward (still non-bare, `.git` file/manifest unchanged in kind) — if uncorrupted, this run's transcript **is** the required passing evidence; if corrupted, the helper exits non-zero with the corruption evidence attached (a target gate that fails this is not yet safe to wire in — this is the intended, working outcome for a genuinely hazardous script, not a "test failure" to route around).
  5. Writes a markdown transcript (the run's exact command + captured before/after `git rev-parse --is-bare-repository` and `git status` output, plus the pass/fail verdict) to `$WORKTREE_PATH/.concertino/gate-chain-isolation-evidence/<target-script-path-with-/-replaced-by-__>.md`, then persists it via `persist-evidence.sh`, which (per that script's own destination-naming contract — it preserves the source's path relative to its worktree top-level) yields the durable, per-script, deterministic path `.concertino/runs/<ticket-id>/evidence/.concertino/gate-chain-isolation-evidence/<flattened-script-path>.md` — the exact path Decision 2/3's Delivery-gate check looks for, keyed to the script actually tested.
  6. Snapshots a small, fixed set of concrete invariants of the *real* surrounding repo (`git rev-parse --is-bare-repository`, `git rev-parse HEAD`, `git worktree list`) immediately before and immediately after the run, and fails loudly with the before/after diff if any changed. This is a deliberately narrower, implementable substitute for an unbounded "nothing outside the fixture was ever touched" claim — the helper has no OS-level filesystem tracing (`strace`/`inotify`) to observe every write; it instead directly re-checks the exact class of damage this incident caused (the real repo becoming bare / its `HEAD`/worktree list changing), which is the concrete risk this whole ticket exists to guard against.

**Proving the harness itself is real** (not a self-referential check that would rubber-stamp any target): the helper's own selftest (task 3.2 / Decision 5's own selftest below) — not the per-ticket invocation against a real target gate — bundles a small **known-bad reference script** (deliberately calls bare `git init` while `GIT_DIR` is exported, reproducing the incident's exact mechanism) and a **known-good reference script** (a no-op / one that only reads state), and asserts the helper's corruption-detection correctly flags the first as corrupted and the second as clean. This selftest is what proves the fixture-and-detection methodology is sound; it runs once, as part of `test/scripts/test-gate-in-isolation.test.sh`, never as part of an ordinary delivery run's evidence — the per-ticket invocation against the real target script only ever needs to produce one honest pass/fail verdict on that real script, which is now always obtainable for a script that is actually safe.

Alternatives considered: a lighter-weight "just run it in a subshell with GIT_DIR set" one-liner left to the executor to invent per-ticket. Rejected — this incident happened *because* nothing prompted anyone to invent that one-liner; a shared, tested helper is what makes the isolation-first rule cheap enough to actually happen every time, and is itself testable/selftest-able the same way every other `scripts/concertino/*.sh` is. Also considered (and rejected, per the design-gate REFUTE): forcing a red/green diff on every invocation — infeasible without a mechanical way to apply an arbitrary hardening fix to an arbitrary target script, and would make "the target script is already safe" — the desired outcome — impossible to prove.

**6. Planning-time signal, non-blocking, complementary to the Delivery-time block.**
`core/roles/orchestrator.md`'s Phase 1 (Planning) gains a short instruction: if the ticket description or an early file-touch plan (visible from the ticket text or an initial `git status`) suggests `.husky/**` or a hook-invoked script will be touched, note this explicitly to the human/self in the proposal, and remind the design-gate skeptic to specifically probe the implications checklist once `design.md` exists. This is advisory (it cannot yet see the real diff, since Execution hasn't happened) and does **not** replace the mechanical Delivery-time check — it exists so the checklist gets *drafted* during Planning/Execution rather than backfilled hastily right before Delivery.

**7. Staging guidance (script-first, wiring-second) — advisory text, not mechanically enforced.**
The ticket's item 4 explicitly frames this as "consider," with a named tradeoff (a worktree must never be left with a hook referencing a missing script). This is added as guidance text in the checklist template and `core/roles/executor.md` (recommend two commits: script alone first, wiring line second, only once the isolation-test evidence for that exact script already exists) — **not** mechanically enforced, because a mechanical single-vs-two-commit check would itself be defeated by the squash in Phase 3 step 1 (all commits on the branch are squashed into one before Delivery, so "were there two commits" is not observable at the point the mechanical gate runs, and enforcing it earlier would require a new, narrower gate at commit-time that this ticket's scope does not ask for). Stated explicitly here per the ticket's instruction to say so with reasoning rather than silently dropping it: **a mechanical check for commit staging order is not feasible given the existing squash-before-delivery design, so this item stays advisory.**

## Risks / Trade-offs

- **[Risk] The path/script-reference classifier has false negatives** (an unusual invocation style in `.husky/pre-commit` that isn't a plain `npm run <script>` reference) **→ Mitigation:** documented as a known limitation in the script's own header comment and `design.md`'s "Non-Goals"; the ticket's scope is the specific incident class (`.husky/**` + hook-invoked scripts), not a general live-infra detector. A follow-up ticket can widen coverage if a false negative is ever observed.
- **[Risk] Evidence persisted via `persist-evidence.sh` could itself go missing (script failure) →** Mitigation: `check-gate-chain-change.sh` treats "evidence file absent" as FAIL, not PASS — fail-closed, matching the ticket's "the rules are enforced ... rather than depending on an agent remembering" requirement; a `persist-evidence.sh` failure during Planning is already surfaced (non-blocking) per existing orchestrator conventions, and this gate is what makes a subsequently-missing artifact block Delivery regardless of why it went missing.
- **[Risk] A legitimate ordinary change to `.husky/pre-commit` (e.g. reordering existing gate invocations, with no new script) still gets flagged, adding process overhead →** Mitigation: accepted as intentional — the ticket's premise is that *any* gate-chain change deserves this scrutiny, not just ones adding new scripts; the checklist for a reordering-only change is genuinely quick to answer (no new script means "what does it execute" answers are unchanged from today).
- **[Risk] `test-gate-in-isolation.sh`'s fixture-shaping (fabricating a `gitdir:` pointer) could itself be wrong in a way that hides real bugs (a "self-referential check" per the ticket's own named failure modes) →** Mitigation: the helper's own selftest (`test/scripts/test-gate-in-isolation.test.sh`, task 3.2) proves the helper's fixture-and-detection logic against a bundled *known-bad* reference script (deliberately calls bare `git init` with `GIT_DIR` set) and asserts the run is detected as corrupting the fixture, and against a bundled *known-good* reference script and asserts the run is detected as leaving it intact — coupling the assertion to real fixture state each time, per the ticket's verification standard, not to a reimplementation of the helper's own logic. This selftest is what validates the methodology; the per-ticket invocation against a real target script only ever needs to produce one honest pass/fail verdict on that real script (see Decision 5).
