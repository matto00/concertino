## Skeptic Report — design gate (round 1, skeptic-design-1.md)

Base commit verified: `d792b42` (`git log --oneline -3` matches the artifacts' claimed base).

### What I verified (with evidence)

**Claim: `.concertino.env` and `speeds.json` are the only render products with no `core/scripts/` source.** CONFIRMED, and by two independent routes. `lib/cli/sync.js:39-40` writes exactly these two files into `scripts/concertino/` outside the `core/scripts` copy loop. `.gitignore:10-11` ignores exactly these two paths. `git ls-files scripts/concertino/` returns 21 tracked files, none of them these two. They are absent from the delivery worktree and present only in the main checkout — consistent with the design's account.

**Claim: `checkArtifacts()` already implements the same comparison.** CONFIRMED. `lib/cli/doctor.js:30-54` enumerates `listFilesRecursive(core/scripts)` and maps each to `out/scripts/concertino/<rel>`, byte-comparing with `readFileSync().equals()`, splitting results into `missing`/`differs`. Both are emitted via `r.warn(...)`, never a non-zero exit. The design's characterisation — comparison logic exists, enforcement does not — is accurate, and Decision 2's enumerate-from-core semantics genuinely mirror established in-repo precedent rather than inventing it. The comment at `doctor.js:50-51` is the source the design quotes for Decision 3; it quotes it correctly.

**Claim: no `.husky` directory.** CONFIRMED in both the worktree and the main checkout (`/home/matt/Development/concertino/.husky` does not exist), and `package.json` has no `prepare`/husky entry. The design's inference that no gate-chain isolation evidence is owed follows.

**Claim: the drift set is exactly four files, plus two missing.** CONFIRMED by `diff -rq core/scripts scripts/concertino`, which reports precisely `check-merge-readiness.sh`, `cleanup.sh`, `README.md`, `squash-branch.sh` as differing and `pricing-table.json`, `report-cost.sh` as core-only. `lib/` matches, as claimed. No file exists in the rendered tree without a core counterpart within tracked content, so Decision 2's blind spot is currently empty.

**Claim: the house bash-test shape resolves the script under test from `core/`.** CONFIRMED. `test/scripts/tui-attached.test.sh:15` sets `SCRIPT="$ROOT/core/scripts/tui-attached.sh"` despite its header comment naming the rendered path; the harness idiom (`set -uo pipefail`, `NO_COLOR=1`, `ROOT` from `BASH_SOURCE`, `PASS`/`FAIL`, `ok`/`bad`/`check`) matches task 1.1 exactly. The suite is therefore trustworthy evidence about core even while the rendered copies are stale — the design's central self-consistency argument holds.

**Scrutiny of Decisions 4 and 5 (the exemption).** I do not find it a quiet hole, on three grounds I checked rather than accepted. (a) Confining the exemption to the missing-counterpart case is load-bearing, not cosmetic: because the two files are byte-identical-and-present in the main checkout, the gate there passes them on content and the exemption never fires; it fires only in tracked-content contexts (worktrees, CI, fresh clones) where they genuinely are absent. Both contexts are green, so the exemption introduces no divergence in gate verdicts. (b) It cannot become a licence to drift — the moment either file is rendered, content comparison binds it. (c) Decision 5's refusal to run `concertino sync` in the worktree is correct and non-obvious: sync would write both unruled files into `scripts/concertino/`, and this branch would carry them to `main`, breaching AC 6. The direct-copy alternative is sound because Decision 2's own premise (verbatim copies) makes it byte-equivalent to what sync would write for those four files. AC coverage is complete: AC1→1.6, AC2→3.x, AC3→1.5, AC4→1.2, AC5→§2, AC6→2.7.

### Verdict: REFUTE

Two defects, both narrow and cheap to fix. The design is otherwise sound and every factual claim it makes checked out; I am refuting because finding 1 puts the change's one inviolable owner constraint (AC 6) at direct risk via an unguarded task instruction.

### Change Requests

1. **Task 3.4 instructs touching a file the owner declared untouchable, with no precondition guard.** `tasks.md` 3.4 says to "temporarily create `scripts/concertino/report-cost.sh` with content differing from core ... then delete the temporary file." In the delivery worktree that file is absent so the step is harmless — but in the main checkout at `/home/matt/Development/concertino/scripts/concertino/report-cost.sh` that file **exists** as the owner's protected untracked file, and the step as written would overwrite it and then delete it. That is precisely the deletion AC 6 and the standing instruction forbid, and the worktree lives under the main checkout's own path prefix, so a mistaken working directory is a realistic failure rather than a hypothetical one. Decision 5 already refuses `concertino sync` to avoid exactly this class of harm; task 3.4 reintroduces it. Revise 3.4 to either (a) assert the file does not exist before creating it and abort the step if it does, plus state explicitly that the step runs only in the delivery worktree, or preferably (b) demonstrate the same property — that an exemption cannot suppress a content mismatch — using a synthetic third exemption entry added temporarily to the table, so no real owner-protected path is ever written to. Option (b) proves the same requirement with no exposure to the protected files at all.

2. **"The exemption decays loudly" is asserted but nothing implements any decay.** `design.md` Decision 4 claims a written reason per entry "is what makes the list decay loudly rather than silently", and the Risks section repeats that the entries disappear "if the owner rules". But a comment in a shell script does not decay — it sits inert indefinitely, which is the identical silent-staleness failure mode this whole ticket exists to close, reproduced one level up in the gate's own configuration. Nothing in `tasks.md` creates a follow-up ticket, an expiry, or any mechanism that resurfaces the open question. Either add a task that files (or references) a real follow-up ticket for the owner ruling on `pricing-table.json` / `report-cost.sh` and cite that ticket id in the exemption reason text in place of the bare "owner has not ruled — CON-172", or drop the "decays loudly" claim from Decision 4 and the Risks section and record the exemption honestly as indefinite until the owner rules. A named, trackable follow-up is the stronger option and costs one task.

### Non-blocking notes

- The gate byte-compares content only, so a rendered `.sh` that loses its executable bit stays green while being unrunnable. `sync.js` has no `chmod` in its `write` path, and task 2.5 handles the bit for this change's four copies, so nothing is broken today — but the gate does not defend the property task 2.5 is careful to preserve. Comparing mode alongside content would be a small addition; leaving it is defensible since AC 1 is scoped to content divergence.
- Decision 2's accepted blind spot (a core file deleted without deleting its render) is currently empty — `diff -rq` shows no rendered-only tracked file — so the risk is genuinely latent rather than pre-existing. The trade-off reasoning is sound as written.
- `test/scripts/doctor-artifacts.test.sh` already exists in the `npm test` sequence but tests `checkArtifacts()`'s logic against fixtures, not this repo's actual trees. Worth a sentence in the new gate's header comment distinguishing the two, so a future reader does not mistake one for coverage of the other.
