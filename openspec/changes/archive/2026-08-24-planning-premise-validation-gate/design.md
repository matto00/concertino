## Context

Planning (`core/roles/orchestrator.md` Setup, step 1) fetches a ticket and proceeds straight to branch derivation (step 2) and worktree creation (step 3). Nothing checks the ticket's premise against the live tree first. Six 2026-08-22/23 instances (CON-128, CON-131, CON-127, HEL-805, HEL-633/634, HEL-637) show the cost: a stale ticket is not a loud failure, it is silently-correct-looking work against a premise that no longer holds, caught only by a human. CON-132 already established the precedent for this class of fix: a control that depends on an agent remembering to apply it has already failed as a control; the fix there was to make the *prompt* mandatory and mechanically enforced (a `## Gate-Chain Implications Checklist` section `assert-phase.sh` refuses to pass the Delivery gate without), while leaving the substantive judgment to the agent. This change applies the same shape to Setup, one phase earlier, because a stale ticket must be caught before the worktree — the vehicle for everything downstream — is even created.

## Goals / Non-Goals

**Goals:**
- A Setup step that runs before branch derivation and worktree creation, checking: (1) the ticket's stated premise (root cause for a bug/incident ticket; cited files/paths/symbols/counts for any ticket) against the live tree; (2) whether acceptance criteria are already satisfied on the base branch; (3) collisions with recently-merged sibling tickets.
- The step's existence is mechanically mandatory: a run that skips it fails a phase assertion, exactly as CON-132 made the gate-chain checklist mandatory rather than advisory.
- Material drift produces a real escalation (`ticket-drift`, a new seventh `gather-escalation-context.sh` kind) with what-was-claimed vs. what-is-true and options (proceed as written / proceed with a stated re-scope / halt). The escalation's having-been-raised is itself mechanically checked, closing the CON-30-shaped "recorded verdict, no durable action" gap.
- Minor staleness is re-derived and reported inline — no escalation, no additional gate, no sub-agent spawn. The no-drift case must be cheap: one read/verification pass plus a short evidence write.

**Non-Goals:**
- Mechanizing the *judgment* of whether a ticket's premise still holds. That is inherently semantic (does this root-cause claim still hold? does this bullet still describe unbuilt work?) and cannot be reduced to a diff check the way CON-132's `.husky/**` path match can. This change enforces that the question gets asked and answered in a fixed, checkable shape — never that the answer itself is verified for correctness by a script.
- Reworking `core/laws/ticket-drafting-escalation.md`. That law covers ambiguity present *at drafting time* (the ticket was never well-specified). This change covers a well-drafted ticket that has since become *untrue* (facts changed after filing). The two are adjacent, never merged; this design leaves that law's own text untouched beyond a one-line cross-reference.
- A general "is this ticket good" audit. Scope is bounded to premise (facts/root-cause), already-done-scope, and sibling collision — the three items CON-136's own acceptance criteria name, not an open-ended review.

## Decisions

### Decision 1 — where the check lives, why before the worktree, and where the mechanical backstop actually fires

The *prose* step runs in **Setup**, between step 1 (fetch ticket) and step 2 (derive branch name) — not folded into Phase 1 Planning, which today runs *after* the worktree already exists. The worktree is the expensive artifact (a branch, a port allocation, a running dev/backend server pair) every subsequent phase is built around, so the orchestrator is instructed to write and answer `premise-validation.md` before deriving a branch, exactly as written.

**Be honest about where the *mechanical* enforcement actually lands, though.** The only check that can fail a phase assertion is `assert-phase.sh setup`, and that assertion runs at Setup step 4 — *after* branch derivation (step 2) and `setup-worktree.sh` (step 3) — and cannot structurally run earlier: its `main_checkout()`/worktree-existence checks resolve against `$WORKTREE_PATH`, which does not exist until step 3 has run. So a run that skips the prose step is not caught until the worktree already exists — the "written before branch derivation" ordering is a prompt-level instruction to the orchestrator, not something the gate can enforce before the fact. This is the accepted residual (mirroring CON-132's own accepted residual for its checklist, Risks below): the backstop costs a worktree teardown on failure, not zero, but it still fires **before Planning or Execution ever begins** — every one of the six real instances this design responds to went undetected well past that point (CON-128/131 into full implementation, HEL-633/634/637 into Execution), so "catches it at Setup, before a single planning artifact or line of code exists" is still the real, and materially cheaper, improvement being claimed — just not the "costs nothing to unwind" framing an earlier draft of this design used.

Because no worktree exists yet when the prose step itself runs, the check reads the **live main checkout** (the directory the orchestrator itself is running in), not a worktree copy — consistent with how the Delivery gate's own `check-gate-chain-change.sh` resolves a "main checkout" from within a worktree, just without the worktree indirection since one doesn't exist yet.

### Decision 2 — evidence artifact and its fixed, checkable shape

**Source location, made explicit (this is what determines whether the gate can find the artifact at all).** `persist-evidence.sh` derives its destination by preserving the *source's* path relative to the top level of whichever git working tree contains it — it does not use the source's basename alone. Since no worktree exists yet, the "git working tree" in scope is the **main checkout itself**, so the source must be written at exactly `<main checkout repo root>/premise-validation.md` (bare filename, directly at the top level) for `persist-evidence.sh "$TICKET_ID" premise-validation.md` to land at the required destination, `.concertino/runs/$TICKET_ID/evidence/premise-validation.md`. Any other source location (a subdirectory, a temp dir elsewhere) preserves that relative path instead and lands at the wrong destination — a correctly-executed step whose evidence the gate then cannot find. **Concurrency, and why this is a real risk, not a hypothetical one.** Concertino is explicitly a fleet product — multiple orchestrators run unattended against one shared main checkout (every worktree hangs off it; `persist-evidence.sh`'s own `ROOT` resolution always lands there). A fixed bare filename at that shared root is a genuine cross-run collision surface if the write, the persist, and the cleanup are three separate orchestrator tool calls: a second orchestrator's write, or its `rm -f`, can land in the gap between this orchestrator's own steps, producing either evidence silently attributed to the wrong ticket or a spurious `FAIL` on a correctly-executed step — exactly the class of silent wrongness this ticket exists to prevent. `emit-event.sh`'s own analogous staging (`write_escalation_raised`'s escalation-context temp file) is not actually async either, but it still uses a collision-safe `mktemp -d` under `ROOT`, for exactly this reason, per its own comment ("concurrent or successive escalations on the same ticket never collide"). The orchestrator SHALL therefore issue the write, the `persist-evidence.sh` call, and the cleanup as **one shell invocation** (e.g. `cat > premise-validation.md <<'EOF' ... EOF && scripts/concertino/persist-evidence.sh "$TICKET_ID" premise-validation.md; rm -f premise-validation.md`, using the main checkout's absolute path, not a bare relative name whose resolution depends on the orchestrator's current working directory persisting across tool calls) — shrinking the collision window to one process's lifetime rather than several separate model turns. This does not eliminate the theoretical race (two orchestrators entering that one command at the literal same instant), and this design accepts that residual explicitly (Risks below) rather than asserting it away — a `SRC_REL`-driven fixed destination forces a fixed source name, so a temp-dir-per-ticket source (which would eliminate the race) is not available for this specific artifact the way it is for `emit-event.sh`'s own truncation-context files, whose destination path is not similarly fixed by the gate.

**A degraded-context escalation must not silently defeat the material-drift check (Decision 3).** `gather-escalation-context.sh`'s own documented fallback — if the script fails for any reason, raise the escalation without `context=` rather than skip raising it — means a `ticket-drift` escalation raised down that degraded path carries no `TICKET-DRIFT-ESCALATION` marker. `assert-phase.sh setup`'s material-drift check SHALL still fail closed in that case (it is not able to distinguish "no escalation was raised" from "one was raised without the expected context"), and the orchestrator role prose SHALL say so explicitly, so a future implementer is not tempted to loosen the check into an existence-only test just because a degraded raise is possible.

The orchestrator writes `premise-validation.md` via the existing `persist-evidence.sh` script into `.concertino/runs/$TICKET_ID/evidence/premise-validation.md` (main-checkout-durable, exactly where CON-132's Delivery-gate evidence already lives, and exactly where the dashboard's EVIDENCE panel already looks). Its required shape, mirroring the Gate-Chain Implications Checklist's own mechanism:

```markdown
## Premise Validation

**Claims checked:** <one line per cited fact/root-cause claim, each tagged CONFIRMED | STALE | UNVERIFIABLE, with what was found>
**Already-done scope:** <which acceptance-criteria bullets, if any, are already satisfied on the base branch — or "none">
**Sibling collisions:** <recently-merged tickets, especially epic siblings, whose scope overlaps or invalidates this ticket's enumeration — or "none found">
**Verdict:** no-drift | minor-staleness | material-drift
```

`assert-phase.sh setup` (extended, mirroring the Delivery gate's own `node` heading-scan exactly) requires: the `## Premise Validation` heading present; all three bullet fields present and non-placeholder (`tbd`/`n/a`/`na`/`todo`/empty, same placeholder set the Delivery gate already uses); and a `**Verdict:**` line whose value is one of the three enum values above. This is the "prompt mandatory" half: the section must exist and be substantively filled in, but the script never judges whether the *content* is correct — that stays exactly where CON-132 left analogous judgment, with the agent.

### Decision 3 — material-drift verdict requires an actually-raised escalation, detected via a fixed context marker (not a `kind` field)

Recording `**Verdict:** material-drift` in the artifact is necessary but not sufficient — this is the same gap CON-30's `followup-triage` closed for a `fold-in` verdict ("a recorded decision alone is not durable action"). `assert-phase.sh setup` additionally requires, only when the verdict is `material-drift`, evidence that a `ticket-drift` escalation was actually raised for this ticket.

**There is no `kind` field to check.** `emit-event.sh` deliberately drops any caller-supplied `kind=` (it is structural — always `escalation.raised` for this event — and re-allowing a caller override would let a stray `kind=` rewrite what the event means). So "an `escalation.raised` event carrying a `kind=ticket-drift` context block" is not something `assert-phase.sh` can check as literally stated; the discriminator has to live inside the `context` string itself. Concretely: `gather-escalation-context.sh ticket-drift`'s output SHALL begin with a fixed, literal marker line, `TICKET-DRIFT-ESCALATION`, as its very first line, before the `claimed`/`actual`/`options` content. `assert-phase.sh setup`'s material-drift check then requires an `escalation.raised` event for this ticket, tagged `role=orchestrator`, whose `context` field starts with that exact marker string.

**Why a leading marker survives `emit-event.sh`'s own truncation path.** An oversized `context` on `escalation.raised` is truncated to a byte-*prefix* of the original string (binary-searched to fit `MAX_LINE`), with the truncation marker and any `context_ref` appended *after* the kept prefix — it is never truncated from the front. Since `TICKET-DRIFT-ESCALATION` is the first line of a context block that is, in practice, orders of magnitude smaller than the 4000-byte line cap, the prefix that survives any realistic truncation always includes it intact; only a context so large that even its opening marker line alone couldn't fit would break this, which is not a case any of `claimed`/`actual`/`options` realistically produces for a ticket-scoped premise check. `assert-phase.sh`'s check is therefore a case-sensitive prefix match against `context` (`context` starts with `TICKET-DRIFT-ESCALATION`), not an exact-string match, so it is unaffected by a truncation marker appended later in the same field.

`no-drift`/`minor-staleness` verdicts carry no such requirement — the whole point is that the common case stays cheap.

### Decision 4 — `ticket-drift` as `gather-escalation-context.sh`'s seventh kind

Added to `VALID_KINDS` alongside the existing six (`dependency`, `api-change`, `budget`, `blocker`, `contradiction`, `ticket-ambiguity`). Required fields: `claimed` (what the ticket states), `actual` (what the tree/base branch actually shows), `options` (a short enumeration — normally `proceed-as-written`, `proceed-with-restated-scope`, `halt`). Its output SHALL open with the literal first line `TICKET-DRIFT-ESCALATION` (Decision 3), then the structured claimed/actual/options block in the same human-readable shape the other six kinds already use. This gives a `ticket-drift` escalation the same structured, non-improvised context block every other kind already gets, rather than falling through the "not one of the six kinds, raise without context" fallback the orchestrator role doc already documents for edge cases.

### Decision 5 — cost on a no-drift ticket

Explicitly stated in `core/roles/orchestrator.md`'s new step: on a ticket with no drift, this step costs one read pass over the ticket's own cited facts against the live tree (typically a handful of `grep`/`git log`/file-existence checks, no sub-agent spawn, no new escalation, no new loop) plus one short `persist-evidence.sh` write — the same order of cost as Phase 1 step 6's existing per-artifact evidence persistence, which already runs on every ticket unconditionally. This is the design's answer to the "keep cost proportionate" constraint: the fixed cost is one evidence write; the variable cost (actually investigating a claim) scales only with how many facts the ticket actually cites, and is bounded by the ticket's own content, not by this design.

### Decision 6 — sibling-collision check, scoped

"Recently-merged siblings" is resolved via: (a) the ticket's own Linear parent/epic relation, if any (`includeRelations` on the existing `get_issue` call — no new tool), cross-checked against the same repo's recent merge log (`git log --oneline -20 <base>` is enough to catch the HEL-633/634/HEL-637-shaped case of a same-epic sibling merged in the preceding days); (b) no attempt to detect collisions with tickets outside the current epic/parent — that would be unbounded scope with no natural stopping point, and is explicitly a Non-Goal.

### Decision 7 — verification fixtures must run the real check procedure, not hand-construct its output

AC5 ("demonstrated on a real stale ticket ... and shown to detect the drift") is about the *detection*, not merely the gate. A fixture that hand-writes a `premise-validation.md` already recording `**Verdict:** material-drift` demonstrates only that `assert-phase.sh` can read a correctly-shaped file — it assumes the answer the step exists to produce. Verification (tasks §5) SHALL instead run the design's own check procedure (Decision 1/Goals item 1) against a real stale ticket's verbatim original premise — CON-131's ("the helio repo root is a bare checkout") and/or CON-128's ("a stale globally-installed concertino silently downgrades rendered files") — using the actual commands the procedure specifies (e.g. `git config --get core.bare`, an inode/`readlink` comparison), and record the *derived* finding plus the command that produced it, not a pre-written conclusion.

## Risks / Trade-offs

- **A residual cross-run collision window remains on the fixed bare-root staging filename (Decision 2).** Issuing write+persist+cleanup as one shell invocation shrinks the window to one process's lifetime, but does not eliminate a same-instant collision between two orchestrators. Accepted: `persist-evidence.sh`'s destination derivation forces a fixed source name for this artifact, and the window is now small enough that the probability is in the same ballpark as other single-process filesystem races this codebase already accepts elsewhere, not a new class of exposure.
- **The mechanical backstop fires after the worktree exists, not before (Decision 1).** Accepted residual, not a defect: a run that skips the prose step is still caught at Setup step 4, before Planning/Execution/Delivery ever begin, which is materially earlier than any of the six real incidents this design responds to were actually caught (all well into Execution or later). The cost of a caught skip is a worktree teardown, not the "nothing to unwind" an earlier draft claimed.
- **A judgment-only check can be rubber-stamped.** Nothing prevents an orchestrator from writing `no-drift` without genuinely checking. This is the same residual risk CON-132 already accepted for its own checklist (its README states the prompt is mandatory, the answer is judgment) — mitigated the same way: mechanical enforcement of the *prompt*, plus this being visible, auditable evidence a skeptic or human can later inspect, not a silent internal thought.
- **False-negative on sibling collision** if the ticket has no Linear parent/epic and the collision is with an unrelated ticket. Accepted per Decision 6 — bounding scope to the epic/parent relation keeps this proportionate; a broader search is future work, not blocking.
- **Cost creep if `git log`/tree-checks are heavier than expected on a very large ticket.** Bounded by the ticket's own content (Decision 5) — a ticket that cites 40 files will cost more to verify than one that cites none, which is the correct, proportionate behavior, not a design flaw.
