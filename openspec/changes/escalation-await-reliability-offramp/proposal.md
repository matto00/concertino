## Why

Live runs (CON-35, CON-22, CON-30) exposed two related weaknesses in the escalation control plane.

First — Part 1, revised twice after the design-gate skeptic measured it against real event-log traces and live probes (round 1 and round 2 REFUTE; see `skeptic-design-1.md`, `skeptic-design-2.md`): the ticket's own premise ("killed at 450s/510s/990s — inconsistent with the documented 600s call-timeout") is false. The real logs show CON-30 (twice) and CON-35 all killed at **599.9s**, and CON-22 ran to completion at **+3600.5s from raise** — i.e. `timeout: 600000` *was* being honored every time; the harness cap was never the problem. The actual, measured defect, probe-verified against a real worktree (round 2's Probe A/B): `core/scripts/emit-event.sh` never sources `.concertino.env` (every sibling script — `assert-phase.sh`, `start-servers.sh`, `cleanup.sh`, `resolve-speed.sh`, `setup-worktree.sh` — does), so `CONCERTINO_ESCALATION_TIMEOUT_MIN` (rendered into `.concertino.env` as 8 minutes — `bin/concertino`'s own default, since this project sets no explicit override) never applies; `--await` always falls back to its 60-minute default — six times the harness's 10-minute call cap, guaranteeing the harness kills the call first. A naive copy of the sibling scripts' sourcing pattern would not have fixed this: `.concertino.env` is gitignored and is never copied into a worktree by this project's config, and escalations are raised from inside a worktree in real runs — round 2's Probe B confirms the fix actually needs (and works with) a fallback to the main checkout's copy, not just the sibling scripts' local-directory-only pattern.

Second, and independently — the role prose tells an orchestrator how to raise an escalation and how to record a chat-relayed answer, but never tells it when to *stop* doubting whether that answer is genuinely from the human. One orchestrator, resolving that exact pressure, kept re-litigating an answer Matt had already given directly, until he had to kill and respawn it. Unbounded skepticism with no defined stopping point isn't caution — it's a run that can never be told anything. The design-gate skeptic confirmed this half of the design sound in both rounds, with no change requests.

## What Changes

- `core/scripts/emit-event.sh`: source `.concertino.env`, checking (1) the currently executing script's own directory (matching the five sibling scripts' convention) then (2) the main checkout's `scripts/concertino/.concertino.env` (via the `ROOT` this script already resolves for its event-log path) as a fallback — so `CONCERTINO_ESCALATION_TIMEOUT_MIN` actually applies whether the script runs from the main checkout or, as it does in real runs, from inside a worktree. With the configured 8-minute value applied, `--await`'s own deadline (480s) lands safely inside the harness's `timeout: 600000` call cap, so the script's own natural timeout — not a harness-imposed kill — is what ends an unanswered wait in the ordinary case. Probe-verified working from a real worktree (round 2).
- `core/roles/orchestrator.md` ("How to raise one"): add an explicit off-ramp clause establishing when to stop treating an unverifiable chat-relayed answer with skepticism — corroborate against independently verifiable ground truth before recording an answer, then treat the moment of recording (`answer.json` or the documented `escalation.answered` fallback) as terminal for the run, never reopening it, while still requiring verification for any brand-new unsolicited claim with no standing escalation behind it. Placed immediately after the existing exit-code handling in "How to raise one", explicitly scoped to *answers* (never *timeouts* — "a timeout is never an approval" already stands unchanged) so it does not read as contradicting anything else in that section.
- Refresh the two touched tracked `scripts/concertino/` counterparts by hand, per file — not a full `concertino sync`, which would sweep in pre-existing, unrelated vendored drift already present in this repo's main checkout (see tasks.md section 4 for the exact per-file treatment and why): `emit-event.sh` is hand-copied in full (byte-identical to `core/` today, nothing unrelated to sweep in); `README.md` is hand-edited in the one relevant spot only, since a full copy would also reintroduce ~9 lines of pre-existing, unrelated CON-22 content the tracked copy doesn't have. There is no Codex-side orchestrator artifact to render: `concertino sync` never emits a `.toml` for the orchestrator role (only executor/evaluator/auditor get one; the Codex orchestrator prose is read live from `core/roles/orchestrator.md` into `AGENTS.md`), and this project renders `claude-code` only. `.claude/agents/concertino-orchestrator.md` (the file Claude Code actually reads) is gitignored and untracked — regenerating it locally is optional and never appears in the diff.
- Update `emit-event.sh`'s own usage header and `core/scripts/README.md` to document the `.concertino.env` sourcing.
- Extend `test/scripts/emit-event.test.sh` with `.concertino.env`-sourcing coverage, using isolated temp copies of the script (never touching `core/scripts/` itself, which the live test suite's other cases already source directly).

### Explicitly descoped

Two mechanisms were proposed across earlier design rounds and dropped after the skeptic found each unimplementable as scoped — this is now the second, narrower shape of Part 1, not a placeholder for either:

- **A `--resume`/re-issue-loop mechanism** (continuing an already-timed-out wait without re-raising): dropped in round 1. `on_kill`'s existing trap always records `escalation.timeout` as the ticket's most recent event after *any* kill, which is exactly the state the proposed "still open, safe to resume" trigger required to be absent — the trigger could never fire in the scenario it existed for. The dashboard reducer also nulls `run.escalation` and bounces the human off the escalation screen on that same timeout, so a resumed wait could never be answered from the dashboard even if it somehow ran.
- **A read-only "was it already answered?" safety-net check** (`check-escalation-answer.sh`, checking the event log for a recorded `escalation.answered` before falling back to chat): dropped in round 2 for the identical structural reason — by the time this check would run (after a non-zero `--await` exit), `on_kill` or the natural-deadline path has *always* already written `escalation.timeout` as the most recent event, so the check's "found an answer" branch is unreachable at its specified call site. Worse, the answer a kill actually loses lives in `answer.json` (written directly by the dashboard), never in the event log as `escalation.answered` — only `--await` itself ever promotes `answer.json` into that event, and it never got the chance to. A correct version of this idea would need to read `answer.json` directly with an explicit staleness rule (e.g. anchored to the escalation's `raised` timestamp, mirroring `emit-event.sh`'s own existing stale-answer discard logic) — real design work in its own right, better done as a follow-up once there's a concrete need, rather than bolted onto this ticket a third time.

Root-cause fix (Decision 1) and the trust off-ramp (Part 2) are independently sound and probe-verified without either dropped mechanism — that is the shape of this change.

## Capabilities

### New Capabilities
- `escalation-deadline-source`: `emit-event.sh` sourcing `.concertino.env` (local-then-main-checkout-fallback) so `CONCERTINO_ESCALATION_TIMEOUT_MIN` actually applies in the real (worktree) invocation context, not just when run from the main checkout.
- `escalation-trust-offramp`: the orchestrator role's off-ramp clause for when to stop doubting a recorded escalation answer, and how that differs from an unsolicited claim with no standing escalation.

### Modified Capabilities
(none — no existing capability's requirements change; `escalation-context`'s and `cross-screen-escalation`'s requirements are unaffected by either addition.)
