### Verdict: REFUTE

The core idea (content diff, not SHA equality; fail-closed on absent SHA; mechanical refusal + prompt remediation) is right, and Decision 2's defence against the precondition-guaranteed trap holds *for the emit side*. But the check as specified has two paths on which it fires spuriously on healthy runs, one path on which it can be vacuously green, a hardcoded path that breaks non-openspec projects, an unaddressed break of the existing test suite, and an internal contradiction between Decision 4a and task 3.3.

### Change Requests

1. **Condition 0's own reconciliation makes the new check refuse every BEHIND PR.** `check-merge-readiness.sh` (condition 0, the `PRE_STATUS = "BEHIND"` block) *itself* merges `origin/<base>` into the branch and pushes, then falls through to condition 3 in the same invocation. Under Decision 1 the diff `reviewed_sha → HEAD` now contains every sibling-merged path outside `openspec/`, so the script would reconcile and then declare its own reconciliation `STALE`, sending the run back for a re-review of changes nobody on this run wrote — and, because the base keeps advancing in a fleet, potentially repeatedly. Note that a three-dot `A...B` diff does **not** help here (`reviewed_sha` is an ancestor of the merge commit, so `...` degenerates to `..`). The design must decide and document how base-derived content is distinguished from run-authored drift (e.g. record the base tip at review time and diff only paths changed on the branch side, or re-derive against `git diff origin/<base>...HEAD` on both sides), or explicitly rule that a reconcile invalidates review and justify the cost. As written this is unimplementable without a per-executor guess.

2. **The refusal can be vacuously satisfied by a failing diff invocation.** Task 2.2's formulation `git diff --name-only <reviewed_sha> <HEAD> -- .` is CWD-relative in its pathspec and specifies only "refuse when that output is non-empty". Any invocation that errors (wrong cwd — the script never `cd`s globally, it uses `(cd "$WORKTREE_PATH" && …)` subshells; a bad pathspec; an over-escaped exclusion) prints nothing on stdout and therefore reads as "no drift" → PASS. That is exactly the CON-169/CON-170 shape, one layer inside the very defence Decision 2 claims to be written against (which covers only the *emit* side). Required: state in design.md that the diff runs as `git -C "$WORKTREE_PATH" diff --name-only …` with an explicit repo-root-relative exclusion pathspec (`':(exclude)<changeDirRoot>/*'`) and **no** `-- .`, that its exit status is checked, and that a non-zero exit or unexecutable diff **refuses** (fail-closed, same leg as Decision 3), never passes. Add a self-test asserting the failing-diff case refuses.

3. **`openspec/` must not be hardcoded.** `core/scripts/**` is copied verbatim by `lib/cli/emit.js` with no variable substitution (stated explicitly in `squash-branch.sh`'s header), and `specProvider.changeDir` is configurable — `kind: none` projects archive under `spec/`, not `openspec/` (`config/examples/generic.json:6`, `lib/cli/init.js:135`). A hardcoded `openspec/` exclusion means those projects refuse 100% of deliveries — the precise failure Decision 1 exists to avoid, relocated. Follow the established caller-passes-the-path convention: add the excluded prefix as an argument to `check-merge-readiness.sh` (or a documented env var with the archive root), pass it from `core/roles/auditor.md`'s invocation, and update the usage header and tasks accordingly. The spec's own wording ("the planning-artifact paths that the delivery archive step legitimately rewrites") is already provider-neutral; design.md and tasks 2.2 are not.

4. **The check reads local HEAD; the merge acts on the remote head.** `gh pr merge` merges the PR's `headRefOid`. The ticket's own incident records the merged SHA as `c42bada4`, an object the auditor obtained from GitHub, not from the worktree. If the worktree's HEAD and `origin/<branch>` diverge (a failed push, a push from elsewhere), the safety property is checked against a state that is not the state being merged. Decide and document which head is authoritative — recommended: compare against the PR's `headRefOid` (already fetchable via the `gh pr view` calls this script makes), or add an explicit assertion that local HEAD equals the remote branch head and refuse otherwise.

5. **Decision 3 turns the existing test suite red, and tasks.md does not acknowledge it.** ~20 fixtures in `test/scripts/check-merge-readiness.test.sh` (e.g. `EVAL_PASS`/`SKEPTIC_CONFIRM` at :95-96, used at :108, :120, :133, :149, :163, :174, :189, :201, :212, :226, :239, :274, :291, :304, :318, :332, :343) carry no `head_sha` and assert `PASS`. Under Decision 3 every one of them now refuses. Add an explicit task to update those fixtures (including giving the scratch repos real commits so `git cat-file -e` can resolve them), and state in design.md that this fixture churn is expected — otherwise the executor will meet a wall of red and may "fix" it by weakening Decision 3.

6. **Decision 4a contradicts task 3.3, and its symmetry claim is inaccurate.** Decision 4a justifies the exit-4 release with "the auditor may emit no verdict for a long time or never" — but task 3.3 *requires* the auditor to emit a distinct verdict on exit 4, and `emit-event.sh:323-325` releases on any `role=auditor` verdict, making the new release site redundant on the mandated path. The claim "every path that leaves auditor territory now releases" is also false as written: exit 1 (FAIL → auditor `ESCALATE`, orchestrator falls back to the human-merge flow) equally leaves auditor territory and does *not* release inside the script. And releasing at exit 4 opens a window CON-171 deliberately closed: the auditor is still alive and still has to write and persist its exit-4 report into the worktree after the script returns. Resolve this: either release on all non-PENDING exits (with the still-writing window addressed, e.g. by leaning on the live-cwd holder guard) or on none, and state the rule and its rationale in one place rather than asserting a symmetry the code does not have.

7. **Task 2.6 must be settled in design.md, not delegated.** The CON-152 owner-override leg is a *waiver path through the very gate this change hardens*; leaving "does an override also waive the SHA check" to the executor invites the cheapest answer (waive it), which reinstates the defect for the runs with the weakest review record. Decide it in design.md with rationale. (A defensible ruling: the override clears the skeptic *verdict* requirement only; the skeptic SHA leg is skipped because an `escalation.answered` event carries no reviewed SHA, while the **evaluator** SHA leg still applies unconditionally — and the override path prints a note saying the skeptic content check was not performed. Whatever is chosen, it must be written down and covered by a self-test.)

8. **Task 1.1 as written cannot go RED, and task 4.4 demands it does.** `emit-event.sh`'s argument loop already folds every unrecognised `k=v` into the event line generically (`core/scripts/emit-event.sh:280-281`), so "emitting `head_sha=X` records `head_sha` X" is precondition-guaranteed by today's script and will print `ok` against the pre-fix binary — the exact assertion shape CON-170 found three of. The genuinely new emit-side behaviour is `head_sha_source` (and the inference fallback). Say so in design.md and restate task 1.1/4.4 so the RED transcript targets `head_sha_source` and the inference/absent legs, not the passthrough.

### Non-blocking notes

- `write_line` (`emit-event.sh:353-366`) drops **all** caller fields to `{"truncated":true}` when a line exceeds the byte cap. A truncated verdict event then reads as `MISSING` on both the verdict and the SHA — fail-closed, so correct in direction, but worth one sentence in Risks so it is not later mistaken for a bug in this change.
- Decision 1's rejected alternative (recording the pre-squash tip at squash time) is dismissed for coupling two independent scripts. That is reasonable, but if change request 1 pushes toward recording base state anyway, revisit it — it may become the cheaper option.
- The `openspec/` exclusion does not hide real drift on a healthy run: the archive commit's writes are confined to the change dir and `openspec/specs/**`, both under that prefix, and the squash commit preserves the pre-squash tree exactly. The exclusion is exactly right in scope; only its hardcoding (request 3) is wrong.
