# CON-174: A spawned agent inherits the driver's cwd, so it can be pointed at another lane's worktree with no guard

## Description

A spawned agent inherits the spawning session's working directory. Nothing checks that the inherited cwd matches the `WORKTREE_PATH` the agent was instructed to work in. So an agent can be handed one ticket's instructions and one *different* ticket's directory, and the only thing standing between that and real damage is the agent noticing on its own.

Live instance, 2026-09-09: during the v0.7 batch, the driver session ran a diagnostic `cd` into lane 1's worktree (HEL-520) to investigate a stalled orchestrator. That changed the session's working directory. An executor spawned in that window for lane 2 (HEL-465) received the correct `WORKTREE_PATH`/`CHANGE_NAME`/`TICKET_ID` inputs but an actual sandboxed cwd resolving to lane 1's worktree instead — which had a live orchestrator working Evaluation cycle 3 in it at that moment. The executor stopped and escalated the mismatch on its own initiative rather than proceeding. No contamination occurred, but the safe outcome depended on agent judgment, not a mechanism.

This is the same class of defect as CON-165 (a bare npm/vite/sbt invocation silently inheriting ambient defaults instead of its pinned target), one layer up: agent spawn instead of dev-server startup. It is strictly more dangerous because a dev server is only read from — an executor writes.

## Corrections (from the ticket's own comment, found within an hour of filing)

1. The ticket body's suggested "confirm cwd resolves under WORKTREE_PATH as first action, BLOCKER-and-stop on mismatch" is **wrong as a default-state check** — the mismatch is normal at spawn, since spawned agents inherit the top-level driver session's cwd, not their own orchestrator's post-cd cwd. A bare pre-cd mismatch check would BLOCKER on essentially every spawn. The corrected shape: `cd "$WORKTREE_PATH"` unconditionally first, then verify `pwd -P` resolves under it and the branch matches the run's branch, and BLOCKER only if the `cd` fails, the path doesn't exist, or the post-cd check disagrees.
2. The worse half the original write-up missed: a mis-spawned agent that gets redirected then works invisibly to its own orchestrator, because the reporting address (`ORCHESTRATOR_AGENT_REF`) is bound at spawn time and does not survive a redirect. This is the direct sibling of CON-139 ("Sub-agent self-notify misdelivers to `main` because ORCHESTRATOR_AGENT_REF is not resolvable at spawn"). This delivery must decide explicitly whether the reporting-channel fix is in scope here or belongs to CON-139, and record that decision in design.md — not leave it ambiguous.

## Acceptance Criteria

(Revised across two design-gate rounds — see design.md Decisions 1/3 for why the originally-stated "unconditional `cd` as first action" shape is not implementable under this harness's per-Bash-call cwd-reset semantics, and Decision 1 for why a bare "ambient must be under WORKTREE_PATH" check is wrong: a correctly-spawned role's ambient cwd is normally an *ancestor* of `WORKTREE_PATH`, not a descendant of it, so that naive shape would BLOCKER on every normal spawn.)

- Every role that receives `WORKTREE_PATH` (executor, evaluator, skeptic, auditor) performs, as its literal first action before any other read or write: capture its own ambient/inherited cwd via a standalone `pwd -P`, then mechanically verify (via `assert-cwd.sh`) that this ambient directory does not resolve inside a *different* ticket's worktree under the same worktree-base directory, AND that `WORKTREE_PATH` itself is checked out to the run's expected `BRANCH`.
- This verification is implemented as a canonical script (mirroring the CON-165 `start-servers.sh` pattern) under `core/scripts/`, mirrored byte-for-byte into `scripts/concertino/` in the same commit (CON-173's drift gate has an empty exemption table), not left as a prompt-only obligation.
- On mismatch, the script fails loudly (non-zero exit, `FAIL <reason>`) and the calling role's prompt instructs it to BLOCKER-and-stop rather than proceed — BLOCKER triggers are: `WORKTREE_PATH` does not exist, the ambient cwd resolves inside a different ticket's worktree, or `WORKTREE_PATH`'s own checked-out branch disagrees with `BRANCH`. A normal spawn (ambient cwd is the driver/orchestrator's own root — an ancestor of every worktree, never inside a different one) must NOT trigger a BLOCKER.
- `BRANCH` is passed as a structured spawn input to every role that needs it for this check (executor, evaluator, skeptic — auditor already receives it), not inferred.
- Every ambient-cwd-relative `scripts/concertino/<x>` invocation already present in the four affected role docs (executor, evaluator, skeptic, auditor — 16 call sites total (executor 1, evaluator 6, skeptic 6, auditor 3 — including skeptic.md:93-94, the start-servers.sh/assert-phase.sh sites)) is made immune to ambient cwd (explicit `cd "$WORKTREE_PATH" && ...` in the same command, or an absolute `"$WORKTREE_PATH/scripts/concertino/<x>"` path), so a `READY` from the guard genuinely means the rest of the role's session is safe, not just the one checked moment.
- A deliberately-constructed failing case (a genuinely different, real, pre-existing worktree under the same base as the correct one) is demonstrated going red, alongside a case using the actual value a correct spawn produces (an ancestor directory, not `WORKTREE_PATH` itself) demonstrated going green — not just a fixture that starts in the right directory by construction.
- design.md explicitly states the scope decision on the CON-139 reporting-channel question (in scope here vs. left to CON-139) rather than leaving it implicit.
